## 一 先统一事项当前状态与主要操作

### 关联卡片必须实时更新

已定位到与现场现象吻合的代码断点：`core/actionable_results.py:449` 的 `preparation_source_task_ids()` 仅接受普通 `oa_pending_prepare` command；恢复子任务在 `core/oa_pending_recovery.py:447` 创建时只有 `oaPendingRecovery` 摘要，因而不产生来源查询更新列表。Workspace 的 `actionableSourceTaskIds` 及 `workspace_projection.mjs:45` 只消费这一列表。子任务完成后自己更新，历史来源卡仍可能停留于准备阶段；刷新重新执行跨来源映射后才读到完成状态。

应把经过服务端校验的恢复子任务、原任务和各来源查询纳入同一更新关系；只更新受影响事项，不重拉全部历史。事件丢失或浏览器从后台恢复时，补做有界的状态同步。不能信任前端提供的原任务关联来跨主体刷新数据。

验收必须包含：同一事项出现在至少三张来源卡、从旧 unknown 创建恢复任务、完成后不刷新页面全部关联卡收口；乱序事件、断线重连和另一端完成后仍一致，旧授权与操作数量不变。

### 区分当前事项结论和历史执行记录

当前恢复组件的核对结论、恢复任务入口主要保存在页面 Map，见 `workspace_recovery.mjs:28、78、116`；服务端虽保存可信事件，但当前任务投影主要只给出 `oaPendingRecoveryAvailable`。

建议提供受限的公开投影：当前结论、最近核对时间、证据有效期、关联的新任务和下一步。对于已有后续成功的事项，主摘要写“后续办理已完成”，历史区写“首次尝试回执未知，随后重新核对并完成”。对于过期核对，只能写“上次核对”，任何新动作仍需重新检查。成功后的入口排队观察应移入历史详情，避免与最终完成结论并列竞争。

### 按状态提供唯一主要操作

`workspace_cards.mjs:441、491` 对非 unknown 任务统一显示“继续任务”，实际在 `workspace.js:1314` 调 continuation 后进入模型聊天。后台可能拒绝不适合继续的终态，这不是重复提交的证据，但界面语义和用户预期不符。

| 当前状态 | 建议主操作 | 结果 |
| --- | --- | --- |
| 尚未选择 | 选择并打开办理页 | 当前卡显示准备进度，完成后直达可信表单 |
| 已有待填写表单 | 继续填写并确认 | 复用原表单，不重新调模型或准备任务 |
| 等待页面或执行中 | 查看进度 | 显示真实阶段和最近更新时间 |
| 已完成 | 查看办理结果 | 显示事项、意见和完成证据摘要 |
| 明确未提交的失败 | 按原因恢复 | 登录、材料读取等使用不同操作 |
| 结果未知 | 核对本事项 | 精确核对原事项，全量待办查询为辅助入口 |
| 已有恢复任务 | 继续新办理 / 查看结果 | 直接指向当前子任务的真实状态 |

恢复不可用也应返回受限原因和下一步。当前 `can_recover_pending()` 将多种原因合并成 false，UI 整体隐藏恢复区，容易形成无出路的卡片。应分别解释登录失效、身份不符、材料变化、已完成冲突、已有新任务等状态。

## 二 把正常办理收敛为一个连续界面

填写与授权在正常路径中已经合并为一次最终决定。现在仍显复杂，主要来自入口与展示：选择事项后准备任务，再找新任务，再开独立表单；恢复流程也要准备、查看新任务、打开表单。代码依据为 `workspace_actionable.mjs:74、93`、`workspace_cards.mjs:18、232`。

建议桌面使用稳定的办理区域，手机使用完整页面；查询列表保留位置，读取材料时在原入口显示状态，准备就绪后直接进入当前可信表单。若受认证域和 CSP 限制无法内嵌，保留独立可信页，但删除中间任务详情跳转，并提供可靠的来源返回入口。

页面首屏只回答四件事：办理哪一项、核心材料是什么、还需填写什么、确认后会发生什么。自动保存和预检作为轻量状态；编号、宿主、技术轨迹和完整历史放入详情。现有“本次确认后操作”在概览、核对区和底部重复，应收敛为一次清晰说明加具体按钮名称。

批次等待文案 `workspace_results.mjs:29` 仍是“等待填写或授权”，应统一为“等待填写并确认”。同意审批、知会阅办、会议回复、撤销、保存草稿各用准确动词，不能统一叫“确认本页操作”。

普通办理的目标是“选择事项 → 阅读和填写 → 一次明确确认 → 结果”。未知恢复保留其额外风险确认，在同一界面渐进展示；可以合并“准备”和“打开表单”的导航，不能把风险确认、旧授权或新审批默默合并成自动执行。

验收除正确性外，增加从选择到可填写的点击数、页面跳转数、返回成功率和重复询问次数。明确办理入口不得新增模型 dispatch。

## 三 让等待可解释并减少实际耗时

### 修正观测缺口

已确认 `workspace.js:1289、1308` 调用了 `quick_query_sent/quick_query_queued`，但 `workspace_performance.mjs:2` 的阶段白名单没有这两个值，调用会被忽略。只读注入时钟复现中，普通 `selection_sent` 正常，两条查询标记均缺失。

应将查询、选择、核对、表单就绪、最终确认和结果绘制纳入同一阶段合同，关联浏览器请求、任务和下游操作。只采集标识、状态和时钟，不采集意见或材料内容。运行期缺失阶段应可见，避免只看到成功样本。

已有真实样本中，查询任务为 6.329 秒，OA 操作为 2.665 秒，其余约 3.664 秒不能未经分段就归因于某一层。旧 39.352 秒为自然语言消息到最终正文，两者计时边界不同，不能直接计算提速比例。

### 显示真正发生的阶段

`workspace/application.py:1950` 将运行中的提交统一投影为 `preparing_submission`。前端虽有等待业务页面、结果核对等标签，当前未接入跨层实时观察事件。

应在实际跨过边界时记录：等待业务页面、最终材料校验、提交入口调用、核对业务结果。只在观察到请求时说请求已发出；只有完成核验证据成立才说已完成。显示真实已等待时间、最近更新和是否可以离开页面，不使用虚构百分比。

建议验收目标：本地点击后 200 毫秒内给出受理中的视觉反馈；阶段事件到达前端后 1 秒内更新；超过 5 秒仍能看见当前阶段及已等待时间。这些是待测试的目标，不是当前 SLA。刷新、切后台与回执丢失不能触发再次提交。

### 改善核验读取和超时预算

- 当前执行器外层约 60 秒 deadline，每轮固定等待 800 毫秒，但核验器不接收剩余总预算；底层已办导航还有独立等待。末轮可能越过外层预算，超出量需慢网络实验确认。应把统一 deadline 传到底层请求和读取，而非简单缩短等待时间。
- 当前无日期的 `list_workflows(done, limit=1000)` 只读取当前列表页面；只有日期路径走分页。增大 limit 并不自动读到下一页。应研究按精确 affair 获取完成证据，或可靠时间范围内的有界分页，使不在首页的已完成事项也能核实。
- 恢复核对在发现原事项已离开待办后，可能再次调用 verifier 重读 pending 与 done。可评估一次核对内部复用已验证快照，或将较长核对改成有持久受理回执的只读任务。最终确认与提交边界的材料、身份重查仍需保持新鲜。

依据：`seeyon_pending_execution.py:136`、`seeyon_pending_verification.py:23、50`、`seeyon_central.py:1253、1302、1313`、`oa_pending_recovery.py:152、164`。

性能对比应按渠道、业务类型和冷暖状态分组，在同一基线和计时边界下至少采集 30 个样本，保留失败分母；初步 P95 的稳定性须继续用更多样本验证。核验测试覆盖目标在首/次/末页、超过 1000 条、分页变化和同名不同事项，保持完整待办消失及精确已办身份的规则。

## 五 草稿与阅读过程需要连续

### 区分内容草稿和执行资格

当前自动保存存在，但 `business_drafts.py:121` 在到期时将 `values_json` 清为 `{}`。因此自动保存仅在原票有效期内可靠，长材料阅读、切后台或次日返回后仍可能失去输入。

分两步改善：先准确显示保存时间、保存有效期、尚未保存部分及到期后的实际行为；再设计独立的私有内容草稿，规定短期留存、账号隔离和主动删除。可执行票继续按原期限失效。重开必须重新读取身份和材料，字段结构兼容且用户主动选择时才恢复自己的内容；不得把恢复输入当作新授权。

原未知尝试的意见应作为历史只读信息。恢复新办理保持空意见或由用户明确重新输入，不默认继承“同意”。

### 保留筛选和阅读位置

选择列表的搜索、类型和勾选目前只存在 `workspace_actionable.mjs:14` 的内存状态。可按账号和来源保存视图状态；恢复时重新过滤不可办、已开始及过期项，保存勾选不代表提交授权。

普通卡片已有焦点保护，但 `workspace_progress.mjs:107、124` 和 `workspace.js:1139` 的模型流更新仍会滚到底。应只在用户原本贴底时跟随，否则保留阅读位置并提示有新内容。

过期表单应给出可信的“返回原事项”入口；120 秒恢复核对证据到期时，前端立即更新按钮和文案。后端当前已拒绝过期，这里改进的是可理解性和及时反馈。

## 六 专门界面应帮助用户核对业务

目前各类界面已有区别，费用、考勤、交接等已有专门字段；效能配置仍为 `family=document, keys=[]`，见 `auth/static/business_draft.mjs:388`。效能可以进一步结构化，但真实正文含统计图片，不能从标题或图片说明猜出数值。

| 业务类型 | 建议重点 | 来源约束 |
| --- | --- | --- |
| 效能与绩效 | 周期、部门、材料目录、指标表与原图并排、异常行定位 | 只展示源中明确取得的数值；识别不到时保留原图，推断标注为辅助 |
| 考勤、补签、加班、请假 | 日期/时段、异常记录、当前确认结论 | 保留原始时间与口径；不擅自合并相邻时间段 |
| 报销、结算 | 总额、费用归属、明细、收款对象 | 账面合计和辅助求和分开；不改变金额、账户或付款动作 |
| 出差、乘机、会议 | 时间线、地点/航段、冲突信息、参会选择 | 冲突必须来自当前可核验记录，缺数据不能推断无冲突 |
| 合同、离职、交接 | 期限、交接责任和未完成事项 | 只整理材料，不作人员评价或自动替用户决定 |
| 周报、知会、知识产权 | 阅读目录、相关对象、明细和来源定位 | 阅办与审批清楚区分，展示不等于用户已理解或核验 |

每个概览项目应能定位到原字段、原表或原图；缺失字段给出明确降级。验收按实际注册动作和数据形状自动生成清单，不能只验证标题和颜色。

材料工具已有 PNG/JPEG、PDF、ZIP 受控预览，但 PDF 主要是 canvas 翻页，缺少文本检索、选取和有效的读屏正文，见 `pdf_preview.mjs:16、74`。建议先补材料目录、搜索、缩放、适宽及阅读位置；扫描 PDF 明确没有文本层。再按真实附件频率评估 xlsx/docx 只读预览，保留行列和格式，不执行宏、脚本或外部链接。

## 七 批量要让剩余工作清楚可接续

当前逐项最终确认和遇错停止已经实现。下一步增加办理页内的批次清单：已完成、当前项、待核对、尚未处理；每项展示标题、类型和可执行下一步，手机使用可折叠抽屉。

批次停止后提供“重新查询并核对剩余 N 项”。服务器根据新来源重新判断资格，再形成新批次。已成功项不重提，unknown 单独核对，未处理项重新核对并逐项确认。不会把停止批次改成静默跳过未知继续执行。

代码依据：`core/tasks.py:987`、`workspace_cards.mjs:188`、`workspace_results.mjs:159`。Telegram 表单当前主要给出第 N/M 项及完成数，应同时补齐单项状态清单。

## 八 把用户旅程和视觉检查纳入每批验收

最近复选框宽度问题是在 Full 通过后由生产截图发现，已经修复，但说明逻辑测试数不能代表实际可用性。将以下检查作为每批受影响界面的必验项，最终再跑全范围：

- 桌面、390 像素窄屏、200% 字号；主动作可见，正文可读，表格局部横向滚动，页面无意外溢出。
- 正常办理、材料变化、未提交失败、unknown、新尝试成功、批次部分完成、过期、断网重连、并发双击与跨端状态。
- 不刷新页面验证来源卡、原任务和后续任务的同步；刷新再验证状态一致，不能只测刷新后的最终画面。
- 键盘导航、错误摘要定位、焦点恢复及状态播报；新状态不应强制抢焦点。
- Telegram 真实桌面及手机的主题、原生主按钮、返回与软键盘；实际未验证的环境明确列为未验收。
- 每轮页面结果对应决定数、授权消费数和真实/合成写入数。真实用户业务的最终确认仍由用户作出，合成提交结果不冒充真实办理验收。

W3C 建议状态变化可由辅助技术获得且不必抢焦点，见 [WCAG 状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。GOV.UK 的 [错误恢复模式](https://design-system.service.gov.uk/patterns/validation/)强调保留输入并给出错误摘要与字段定位；其[提交前核对模式](https://design-system.service.gov.uk/patterns/check-answers/)强调集中核对与明确提交。对本项目的应用是保留现有一次确认，并把关键摘要和具体后果放在同页，不据此再增加一个独立授权步骤。

## 原定分批顺序与实施收口

| 批次 | 交付重点 | 独立验收门槛 |
| --- | --- | --- |
| 一 | 关联卡实时同步、历史/当前结果分层、状态主动作、计时标记修复 | 恢复成功后原卡与多来源卡无需刷新一致；已完成无继续办理入口；既有表单无新模型调度 |
| 二 | 真实进度、端到端计时、核验覆盖、总预算和重复读取 | 同条件性能样本、慢网络故障注入、非首页已办；授权/材料/业务核验不退化 |
| 三 | Telegram 恢复入口、准确动作、返回层级、深色配色 | 单项/批次 unknown 和同主体双端恢复；真实原生控件与主题验证 |
| 四 | 选择到表单直达、输入草稿与到期接续、筛选及阅读位置 | 少中间导航；过期不复用授权；账号切换隔离；流更新不抢阅读位置 |
| 五 | 数据型专门界面、长材料工具、批次清单和剩余事项接续 | 全部当前动作映射；原材料可追溯；成功项不重放、未知项不自动跳过 |

原计划要求视觉和关键旅程门禁从第一批开始执行，每批独立 Workspace 测试并更新验收文档；每批开始前复核代码和线上现状，完成后沿用干净候选 Full、原生发布和发布后 Workspace 验收流程。上述五批已按此推进，首发与阅读追补分别绑定各自候选、Full 和 wheel；上线与真实用户业务完成分开记录。

最终范围为 **29 个有字段动作、3 个无字段照明动作、17 类 OA 协同待办及会议邀请回复、24 种材料布局**，这些属于不同维度。五批分别完成状态联动、真实进度与有界核验、Telegram 接续、内容与阅读接续、专门材料和剩余批次核对。性能没有全面提速结论；手机软键盘、安全区及部分原生事件仍未实测，8 个其他旧 OA 创建/撤销动作保留合成 prepare/commit、未做真实 OA DOM 的边界。原验收目标不因实施收口而自动变成全部环境已通过。
