# AgentBridge 命名统一与平台收敛方案

状态：0.2.0 已实施、验收并发布；0.3.0 兼容退役待后续版本。分析日期：2026-10-09；代码基线：`f5c2761`。初版为分析方案，后续实施状态见[实施记录](../验收记录/命名统一与平台收敛实施记录-2026-10-09.md)。

AgentBridge 应统一产品、仓库、Python 分发包、导入模块和命令行入口的命名，并彻底退出 Windows 运行与维护支持。两项工作属于同一迁移项目，按可独立验收的批次实施。最终维护目标为 macOS 开发及宿主、Linux 中心服务及 CI；历史交接证据保留，不再成为日常发布的运行依赖。

主要风险集中在制品与启动入口的一致性、Mac 宿主授权仍依赖旧交接材料，以及证书能力仍分散在 Windows CLI 和迁移脚本中。仓库网页上的改名操作本身较简单，不能代替这些工程调整。

## 目标命名

| 对象 | 当前名称 | 目标及处理 |
| --- | --- | --- |
| 产品展示名 | AgentBridge | 保留 |
| GitHub 仓库 | `guomxin/cli-helper` | `guomxin/agentbridge`，执行前确认目标名称可用和管理员权限 |
| Python 分发包 | `cli-helper` | `agentbridge` |
| Python 导入包 | `bscli` | `agentbridge` |
| 正式 CLI | `bscli` | `agentbridge` |
| 模块执行入口 | `python -m bscli.cli.main` | `python -m agentbridge`，保留明确的内部 `agentbridge.cli.main` 实现 |
| 默认本地业务数据目录 | `~/.bscli` | 新安装使用 `~/.agentbridge`；已有数据显式迁移 |
| 本地源码目录 | 当前为 `CLIExp` | 新克隆示例使用 `agentbridge`；已有目录最后单独迁移 |
| 原生维护入口 | `scripts/agentbridge-native` | 保留；它负责仓库维护，与产品业务 CLI 职责不同 |
| 服务及环境变量 | `agentbridge.service`、`AGENTBRIDGE_*` | 保留 |
| OpenClaw 插件 | `@guomxin/openclaw-agentbridge-interactions` | 保留，已包含产品及宿主语义 |
| 可信交互前端 | `@agentbridge/trusted-interaction-app` | 保留 |
| Reference Host | `agentbridge-reference-host`、`reference_host` | 保留独立组件身份，不能统一成与核心同名的包 |

分发包是安装时使用的名称，导入包是源码 `import` 使用的名称，两者在 Python 中没有强制对应关系。当前组合技术上合法，但本项目没有继续维护三套核心名称的必要。[PyPA 对两种包名的说明](https://packaging.python.org/en/latest/discussions/distribution-package-vs-import-package/)

当前发布流程构建并上传本项目 wheel，不以公共 PyPI 发布为前提。因此目标分发名可以先用于可信内部制品。若以后公开发布，必须另行确认 PyPI 名称所有权；不能因为模块改名就指导新人从公共索引安装尚未核实归属的同名包。

| 范围 | 文件数 | 文本命中数 | 主要含义 |
| --- | ---: | ---: | --- |

| `bscli` | 82 | 436 | 导入、CLI、包说明 |
| `tests` | 136 | 801 | 导入、mock 目标、制品与契约夹具 |

### 源码和包资源

[pyproject.toml](../../pyproject.toml) 同时定义分发名、CLI、包发现和六组包资源。必须整体迁移，不能只改 `name`。页面脚本、业务 Skill 清单、静态页面、样式、前端模块、图标和许可证仍须进入 wheel。

[核心 CLI](../../agentbridge/cli/main.py) 固定 `prog="bscli"` 和默认 `~/.bscli`。除 Python 导入外，还要更新字符串形式的 `mock.patch` 目标、测试夹具中的异常全限定名，以及按目录读取源码的测试。

[宿主契约检查](../../scripts/run_agent_host_conformance.py) 通过禁止 Reference Host 导入 `bscli` 检查宿主独立性。迁移时要同时禁止新核心包名；仅修改正向导入会使这项架构检查失效。

### 构建和发布

[制品工具](../../scripts/agentbridge_artifact.py) 将 `bscli` 写入必需资源清单、目录遍历和隔离安装探针，并通过 `importlib.metadata.version('cli-helper')` 读取版本。新包名必须覆盖这些校验，继续证明实际安装的是候选 wheel，而非当前目录里的源码。

[Linux 发布事务](../../scripts/agentbridge_release.py) 在候选虚拟环境中导入旧模块，并以旧模块入口执行备份。[原生验收](../../scripts/native/acceptance.py) 也使用旧入口。主服务和备份服务的 [systemd 模板](../../deploy/systemd/) 必须一起更新。

实际发布使用外置环境 profile 指定的 unit 文件，并校验其 SHA256，见 [原生发布器](../../scripts/native/publish.py)。修改仓库模板不会自动更新线上启动配置；实施时必须生成、审核并更新外置 unit 和对应哈希，不能去掉校验来让新配置通过。

现有发布事务为每个 Release 新建虚拟环境，这适合分发包更名。开发环境也应重建虚拟环境，避免旧 editable 安装、旧入口脚本或旧元数据残留。不要把 `pip install agentbridge` 视为会自动卸载 `cli-helper` 的升级操作。

### 前端和集成

[Vite 配置](../../integrations/mcp-app/vite.config.ts) 输出到 `bscli/mcp/static`，[输出归一化脚本](../../integrations/mcp-app/scripts/normalize-output.mjs) 也使用该路径。必须先修改生成目标，再执行前端检查和构建，确认不会重新生成旧目录。

OpenClaw 与 Reference Host 的协议、工具 ID、能力 ID、身份绑定、插件 ID 和 `agentbridge.*.v1` schema 不因 Python 模块改名而变更。它们属于外部契约，不是本轮名称替换目标。

### 仓库和 CI

本地 `origin` 当前拉取地址为 HTTPS、推送地址为显式 SSH。改名后应分别更新，保留既有认证方式：

```sh
git remote set-url origin https://github.com/guomxin/agentbridge.git
git remote set-url --push origin git@github.com:guomxin/agentbridge.git
git remote get-url --all origin
git remote get-url --push --all origin
```

以上是实施阶段命令，尚未执行。执行前应检查有无多条 URL，逐项处理；不可只改 fetch 地址。[原生发布器](../../scripts/native/publish.py) 的精确远端白名单以及相关测试也必须更新。旧迁移取代码脚本若按清理计划删除，就不必再为它长期维护新旧白名单。

GitHub 会重定向旧仓库网页和 Git 操作；项目 Pages 地址、其他仓库调用本仓库托管 Action 的路径有例外，旧名称也不应重新用于另一仓库。[GitHub 改名说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)

[CI workflow](../../.github/workflows/validate.yml) 当前使用第三方公共 Actions，未发现 `uses: guomxin/cli-helper/...`。这不能证明仓库外没有调用者。执行前仍需清点 Pages、webhook、部署集成、包索引及其他仓库引用。

[CI 范围选择器](../../scripts/ci_validation_plan.py) 根据仓库身份和成功历史决定是否缩小验证。改名后历史身份不匹配时允许退回完整验证，不能为复用旧结果而放宽可信历史判断。保留 `repository-validation` 检查名称，实际复核分支规则和改名后的首轮 CI。

### 数据路径和外置配置

Linux 正式部署显式传入 `--home <服务根目录>/data`，默认目录改名不要求搬迁服务器数据。已有 `~/.agentbridge/pki` 是证书默认目录；因此不能只根据 `~/.agentbridge` 是否存在判断业务数据已迁移，也不能覆盖整个目录。

迁移工具应识别业务配置及状态标记，先生成计划，再停用相关写进程、备份并迁移。源和目标都含业务状态时拒绝自动合并；路径重叠、符号链接、权限或内容冲突必须报错。迁移完成前，新入口检测到只有旧业务目录时应给出明确指引，不能静默初始化一套空环境。

迁移应检查配置、SQLite 及其一致性、加密会话、浏览器 Profile、报告与附件中的路径引用。会话密钥、用户与系统上下文保持原样。不能复制运行中的 SQLite 文件后直接宣称一致，也不能用空会话或新身份替代旧状态。

本地源码目录更名放到最后。先检查虚拟环境绝对路径、宿主插件链接、launchd 配置、IDE/工作区记录及私有 profile；优先在新目录重建环境，再更新已确认的路径。`CLIExp` 不是产品 API，可与 GitHub 改名单独完成。

## Windows 彻底退出的范围

基线包含 25 个受跟踪 PowerShell 文件，其中 21 个 `.ps1`、4 个 `.psm1`。清理还包括 DPAPI、Win32 进程检查、Windows 文件锁、迁移导出工具、测试分支和现行文档，详见 [实施清单与验收](./命名统一与平台收敛实施清单.md)。

### 先解除两个现役依赖

第一，[宿主生命周期](../../scripts/native/lifecycle.py) 的 `authorize → cutover` 仍要求 `windowsGatewayStopped` 等字段，并重新校验旧 final 交接材料。日常发布与宿主重启因此依赖历史 Windows 迁移过程。应以正式宿主登记和配置授权机制承接其安全保证，再删除迁移代码。

新登记记录建议使用独立的 `agentbridge.host-authorization.v1` schema，绑定宿主身份、审核后的 profile 哈希、当前状态目录、CA 指纹和接管核验结果。保留准备环境禁止激活、配置变化重新审核、唯一宿主和隧道所有权、私有文件权限等约束。旧证据只能通过一次性、显式的本机转换形成候选记录；转换不能凭空证明当前没有另一个活跃宿主。新记录正式启用前需重新核验实际进程、端口和协调状态。

第二，[主 CLI 的 PKI 入口](../../agentbridge/cli/main.py) 仅支持 Windows DPAPI，[可移植 CA](https://github.com/guomxin/cli-helper/blob/f5c2761d129d61c78d9dffb9811adcfd0fbe5d23/scripts/migration/portable_ca.py) 则仍在迁移目录。应将加密 PKCS#8 的加载、根证书校验和叶证书签发提升为正式 Mac/Linux PKI 能力，并提供正常 CLI 入口，然后删除 Windows 导出及 DPAPI 实现。验证既有根指纹和密钥匹配，错误口令、缺失根材料不得自动生成替代根；新建 CA 必须是独立显式操作。

### 最终删除与保留边界

| 类别 | 最终处置 |
| --- | --- |
| PowerShell 发布、部署、Guard、隧道、验收脚本及模块 | 从当前代码树移除；必要能力先迁入原生流程 |
| Windows DPAPI、Win32 API、`msvcrt` 锁、`taskkill` 分支 | 删除；保留并验证 Mac/Linux 对应实现 |
| Windows 到 Mac 导出、适配、接手工具 | 完成新宿主授权和 PKI 迁移后删除，不留在日常运行依赖中 |
| 已完成迁移的私有交接原件、收据、证书和密钥 | 原地保护；不因源码清理删除、重写或重新导出 |
| PowerShell 专属测试 | 删除或改写为原生行为测试；共享 Linux 发布事务测试继续保留 |
| 当前 README、运维手册、插件 README 中的 Windows 命令 | 替换为现行 Mac/Linux 流程 |
| 已完成的历史设计、迁移和验收记录 | 保留当时名称与命令，标记历史用途；必要时移入历史归档并更新链接 |
| 第三方许可证、浏览器兼容语义、SQL window 功能 | 不按 `Windows` 字符串误删 |

例如照明适配器中的浏览器 User-Agent 含 `Windows NT`，它是 HTTP 客户端标识，不能据此推断代码支持 Windows。先核实下游契约；除非另有契约验证，不在本轮改它。数据库测试名中的 `windows` 可能指窗口函数，也不属于平台遗留。

## 兼容策略

本方案用 R1 表示首个统一版本、R2 表示移除兼容入口的后续版本；实施前确定实际版本号和移除日期，不把占位符写进正式弃用提示。当前 Python 项目版本仍为 `0.1.0`，改名发布需要明确的新版本和变更说明。

| 兼容对象 | R1 处理 | R2 完成条件 |
| --- | --- | --- |
| 旧 `bscli` 命令 | 极薄转发到新 CLI，警告写 stderr，不污染 JSON stdout | 已知调用者完成切换后删除 |
| `python -m bscli.cli.main` | 仅保留该启动兼容入口 | systemd、备份、脚本及手册均切换后删除 |
| 任意 `import bscli.*` | 默认不提供全面兼容；内部和已知外部调用者同步修改 | 主代码只导入 `agentbridge` |
| 旧分发名 `cli-helper` | 不维护第二份核心分发包，重建虚拟环境 | 新环境没有旧元数据或旧 editable 链接 |
| 旧业务数据目录 | 显式迁移；兼容期可通过 `--home` 继续使用旧目录，新旧命令共用路径决策 | 所有活跃配置明确使用目标目录或指定 `--home` |
| 旧仓库地址 | 过渡期可精确接受同一 owner 的新旧地址，不接受任意 URL | 所有已知 clone 和自动化切换后收紧到新地址 |
| Windows 执行入口 | 不提供永久转发或模拟支持 | 当前代码树不再承担 Windows 运行与维护 |

不要复制一整套 `bscli` 包作为别名，也不要简单批量注册 `sys.modules` 别名。双重导入可能使异常类、注册表和单例获得不同身份。兼容测试必须证明旧命令只进入同一套新实现；确有第三方依赖 Python 内部 API 时，先列出实际用到的接口再决定迁移合同。

旧数据目录兼容需独立于代码回滚：指定 `--home` 永远优先。R1 若同时提供新旧 CLI，必须验证两者不会在用户不知情的情况下操作不同业务状态。默认无参数访问发现旧数据时，推荐要求显式选择或完成迁移，而非静默双写或自动合并。

## 实施顺序

1. **冻结基线和外部清单**：核验当前线上 Release、外置 unit/profile、活跃命令调用者、CA 与宿主登记材料，记录回滚目标；本分析基线不代表线上版本。
2. **承接 Windows 遗留能力**：完成正常 PKI 入口和宿主授权替代，验证 POSIX 锁、进程回收和测试能力；先准备新登记记录，旧证据保持只读。
3. **形成统一候选版本**：一起迁移核心包、分发名、CLI、资源构建、发布工具、测试和现行文档；删除已被承接的 Windows 代码。按功能分提交，候选版本必须整体可运行。
4. **完成仓库改名切换**：先准备兼容新旧地址的精确白名单及文档，再改 GitHub 名称、fetch/push URL，复核 CI 与外部引用。此步骤可独立于生产部署，但不能让发布器因地址不匹配而失效。
5. **验证并部署 R1**：固定候选提交，完整验证并构建 wheel；审核外置 unit；通过现有发布事务切换，完成服务、备份、宿主和协议验收。生产数据目录保持不变。
6. **迁移开发机默认目录与源码目录**：在各自停写窗口显式处理，与中心发布分开验收。
7. **收口 R2**：确认调用清单全部切换，删除旧 CLI/模块启动兼容层和远端旧地址白名单，执行残留扫描。

分批的目的在于让失败可以定位和回滚。不能把“Windows 清理”降为长期跳过测试，也不能以“同一项目实施”为由同时修改数据库结构、业务协议或下游接口。

## 回滚与完成条件

核心发布失败时，恢复上一 Release 的虚拟环境、unit 和 `release.env`，不能把新入口的 unit 指向只有旧模块的环境。新旧代码均须使用同一受保护的数据、密钥和协议配置；本轮原则上不做数据库 schema 迁移。若实现确需改变存储合同，必须另列兼容与恢复方案，不能声称是纯重命名。

源码目录和默认数据目录有独立的回滚记录。迁移后发生的新写入不得被旧快照直接覆盖。GitHub 名称是否回改另行决定，恢复代码通常只需使用更新后的远端；无需为了代码回滚再次改仓库名。

完成标准是新人从 README 到安装、导入、运行、验证都只需记住 AgentBridge；Mac/Linux 全链路不再执行或导入 Windows 专属实现；历史证据仍可追溯；兼容入口有明确截止版本；完整验收结果与部署结果分别记录。详细门槛见 [实施清单与验收](./命名统一与平台收敛实施清单.md)。
