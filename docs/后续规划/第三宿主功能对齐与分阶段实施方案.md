## 如何判定对齐

1. **用同题比三套宿主。** 每个样例记录主体、权限、端点、输入、期望的业务事实及副作用次数。隔离环境固定业务快照、时间与材料修订，可行时固定模型。生产只读串行抽查并注明数据时间。分别记录三宿主的实际结果、候选版本和回执类型。共有能力在同权限、同端点条件下三方比较。某一宿主独有的能力以该宿主为准，另一列标明“未提供”或“端点未获准”。模型措辞可不同，事实、权限、选择、文件、操作与投递次数的非预期差异须回到负责阶段。
2. **分开判定运行、业务和送达。** 一次 SDK 结束只证明这轮生成结束，权威业务状态查 Task／Operation，用户端送达查原端回执。用户取消排队时核对尚未接单。停止生成时核对原运行。取消业务时检查原任务仍可取消。管理员停止接单允许在途收尾，安全撤权立即阻止后续受保护操作。宿主离线、网络丢回执或 Telegram 限流都不能把请求转投其他宿主。
3. **契约与产品分别出证。** Pi 使用固定的真实 SDK，逐项运行 H01–H29，记录向量、探针和收据。H28/H29 的计划与重启证据另配组合写入、Telegram、助手和文件专项。Pi 微信专项列入 W。任何共用模块的改动同时运行两个原宿主对应回归。逐项标注“隔离通过”“生产只读通过”“经用户授权的真实办理”或“待验”。[等级与私有运行时权限](../架构设计/宿主无关化与标准远程协议接入一期详细设计.md) · [现有 NanoBot 契约门禁](../../scripts/run_nanobot_conformance.py) · [共享场景](../../schemas/agent-host/v1/test-vectors.json)
4. **在可比条件下看体验。** 记录网络、模型、输入大小、冷／热状态和样本数，分别计时到受理、首段用户可见答复、权威终态和原端送达。工具、模型、重复发送与业务副作用分别计数。阶段 1 用交错同题重测建立基线、约定回归容许范围。阶段 6 报告中位数，样本充足再报告 P95。无法观测的指标不填零。既有单笔审批耗时只作历史参照。[宿主性能验收](../验收记录/纳米机器人与中央底座性能优化-2026-11-25.md)
5. **上线与停用都可核查。** 默认关闭 Pi 新入口，预检固定 Node 包摘要、wheel、隧道、密钥引用、Bot 公开身份、空 webhook、唯一消费者和队列归属。按现行发布入口核验干净候选 Full、制品、恢复点、旧消费者与实际前驱兼容性。隔离工作台先做双账号长历史、过期、刷新和恢复验收。上线后用本人 Workspace 和第一账号 Telegram **桌面客户端**查同一条只读 OA，核对旧端点没有副本和新增写入。回退先停止 Pi 新接单及消费者，保留原请求、租约、投递账本及未知操作，按发布策略恢复。真实业务写入仍需该具体事项的一次性授权。[开发验证流程](../部署运维/开发验证与发布流程.md) · [发布操作手册](../部署运维/发布操作手册.md) · [开发安全策略](../部署运维/开发安全策略.md)
