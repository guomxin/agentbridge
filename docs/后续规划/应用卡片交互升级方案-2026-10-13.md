# 应用卡片连续办理与单次提交方案

日期：2026-10-13。状态：实施中。代码基线：`cfe4526`。本方案承接 2026-10-11 的交互调研，依据最新源码调整范围、实施顺序和验收门槛。各批实际进度与独立 Workspace 测试见[实施与验收记录](../验收记录/应用卡片分批实施与验收-2026-10-13.md)。

建议先把填写、核对、授权和结果收敛到一个持续存在的可信办理页，再对完成预检的短表单提供一个明确的授权提交按钮。Workspace 同时增加稳定的业务容器和批次逐项视图。后台继续保存独立的输入、授权和执行证据，沿用最新的提交与权威核验链路。

运行版本与部署事实以[项目当前状态](../项目当前状态.md)为准。本方案不将设计中的视图、预览接口或草稿存储记为已实现功能；以下新增字段及模块名称是建议命名。

## 产品目标与交互分层

把界面分为三个职责清楚的层次：

- **聊天中的业务容器**：展示任务对象、当前阶段、待处理事项和结果，保留一个主要操作入口；普通用户不必在字段卡和授权卡之间寻找下一步。
- **可信办理页**：在现有可信 Origin 内呈现业务字段、核对依据、明确授权和执行结果。完整字段、敏感资料和授权决定沿用可信数据通道。
- **任务详情**：保存交互记录、批次历史、业务核验摘要及故障依据；版本、技术编号等放在详情，不占据主卡首屏。

安全交互类型继续表达 `credential`、`business_input`、`execution_authorization`。另用展示类型表达表单核对、资源选择、审批核对、批次队列和结果回执，不让安全阶段决定所有业务的视觉结构。

小任务使用一个主要动作及必要的取消入口；长材料、批次和复杂选择展开到办理页。主卡避免深层导航及内部滚动。业务控件由服务端登记和选择，模型只能选择获准业务能力，不能生成任意可执行界面、动作名称或提交接口。

## 连续办理与合并提交

### 第一阶段同页衔接

第一阶段保留“提交字段”和“确认执行”两个明确动作，先消除返回聊天与重新找卡的成本：

```text
聊天业务容器
  → 打开可信办理页
  → 填写与提交字段
  → 原协调器续办并准备计划
  → 同一页面展示最终摘要和授权按钮
  → 已授权，等待执行
  → 执行与核验
  → 同页回执或待核对提示
```

新增可信页面的连续流程路由和受限状态查询。字段成功页保留办理容器，通过中心状态获取其后继授权交互。页面只负责展示与可信用户决定，仍由原任务的协调器处理 `resume`；不得让页面再调用一遍 prepare 或 commit，形成两个执行者。

现有宿主重启、租约和稳定幂等键继续承担恢复。协调器离线时显示“字段已保存，等待连接恢复”，页面关闭后重新进入同一办理过程。只能接续服务端证明属于同一用户、任务和业务操作的后继交互，不能选择该用户“最近的一张授权卡”。

第一批字段提交后先展示只读核对摘要；“返回修改”随第二批草稿修订交付。届时只有尚未批准的版本可以修改，并须生成新输入版本、使同一操作的旧待决授权失效，不原地改写已提交字段。修改与批准竞争时，由同一事务复核决定先后。一经批准，本期普通流程即锁定内容并关闭修改和取消入口，继续查看原操作结果。

### 第二阶段一次明确提交

只有在用户点击前，已展示与当前输入一致的有效预览，才允许一个按钮同时表达最终授权和提交意图：

```text
编辑字段 → 服务端预检 → 展示已验证内容和后果
                         ↓
                确认并提交当前版本
                         ↓
               既有单次执行与核验
```

按钮使用具体业务动词，例如“确认并提交日志”“确认并提交会议室申请”“同意并提交意见”。点击按钮前不再设置一个含义重复的“我已确认”勾选框。登录、验证码与账号连接仍是独立身份验证步骤，完成后恢复业务草稿。

| 条件 | 界面行为 |
| --- | --- |
| 输入完整、预览有效、目标和影响已展示 | 一次明确授权提交 |
| 预检进行中或有字段错误 | 暂停最终按钮，原位显示状态或字段错误，保留输入 |
| 项目解析、时间资源检查等产生新结果 | 展示解析后的对象与实际后果，就绪后允许提交 |
| 提交前发现目标、身份或重要业务内容变化 | 旧预览失效，展示变化，等待用户确认新版本 |
| 不可逆处置或尚未建立完整预检合同 | 保留专门复核；仍可在同一可信页完成 |
| 已进入提交边界但结果未知 | 停止写入，只提供查询与核对路径 |

当前 OA 执行器对额外业务确认并没有通用的暂停后安全续提交流程。出现未处理提示且无法取得权威成功证据时，必须保留未知；不能用“再确认一次”重放提交。只有能够证明尚未产生副作用、并有专门恢复合同的流程，才可另行设计继续执行。

## 业务视图与首批范围

| 业务 | 界面设计 | 首批实现边界 |
| --- | --- | --- |
| 泰华日志创建 | 日期、工时、项目、正文同页；预览显示真实项目名称与编码、查重结果和正式提交后果 | 首个单次提交试点；复用四字段校验、项目解析、二次查重与按日回读 |
| OA 已支持的单项待办 | 原申请依据只读展示，处理意见可编辑；航段或明细按结构排列 | 先同页填写与授权，再按能力逐项开放单次提交；批准、确认、已阅分别使用真实动作 |
| OA 会议室申请 | 时间范围与空闲房间联动选择，保留当前选择及失效原因 | 修改时间后重新查候选；不凭空绘制完整占用日历，不自动换房；申请与会议创建分开 |
| 现有批量待办 | 稳定批次容器、逐项队列、当前项办理区、逐项结果 | 复用现有批量支持范围及顺序执行；逐项授权，遇未知停止 |
| 照明告警备注 | 目标摘要、修改前后对比和结果 | 可在前述试点后接入；不可逆处置维持独立准入及真实样本要求 |
| 读取与文件交付 | 列表、表格、时间线、文件回执 | 沿用已有结果与下载组件；按业务价值补充，不重建通用仪表盘 |

泰华项目文本可能被解析为非精确但唯一的候选，因此最终按钮前必须展示真实项目标识。不能在用户点击后才静默选择项目。查看[泰华准备与提交](../../agentbridge/adapters/taihua.py)中的 `prepare_taihua_work_log_create`、`_resolve_project`、`commit_taihua_work_log_create`。

会议室申请只表达其注册的业务意图。会议创建当前的人员范围、已有乘机申请的审批性质、各待办允许动作都由能力合同决定；丰富视图不会自动增加选参会人、购票、驳回或撤销能力。

### 批次容器与独立事项

批次顶层稳定使用 `taskId + batchId`，每行使用持久的 `item_id`，序号只用于显示。当前事项内部仍引用自己的字段交互、授权交互和执行操作。历史事项可以展开查看，但旧按钮失效，下一项只有在当前项权威成功后才能进入办理。

父容器显示批次聚合状态，事项行显示该项账本状态，授权标签只反映相应交互。不能把父任务的 `outcome_unknown` 灌给所有历史行，使已经成功的事项也变成未知。

Workspace 当前详情以汇总及 `currentItem` 为主。可复用中央 `batch_response` 已有的安全事项投影，增加受身份与任务权限约束的逐项读取；较大列表按需加载。主卡使用紧凑摘要，完整队列放在展开视图，不在每张历史交互卡重复整批说明。

本期不增加整批一次授权、选中多项统一批准、跳过未知后继续等行为。若未来需要并行或批量授权，必须另行设计逐项冻结、范围证明和失败合同。

批次在允许取消的阶段取消当前事项，会按现有策略停止批次，不会跳过后自动进入下一项。操作文案明确“取消当前办理并停止批次”；折叠、关闭页面只改变展示，不取消业务。

批次候选选择与写后核验是两个完整性合同。冻结候选时的读取预算不能套用到写后核验。当前 OA 待办核验要求完整集合，现有来源尚无经验证的分页合同；超出已验证范围仍保留未知，不能为改善体验放宽成功条件。

## 状态与结果展示

界面复用当前任务和批次终态。仅为需要区分的在途阶段补充受控事件，不因 UI 需要而重写全局状态机。

| 用户看到的状态 | 事实来源 | 可用操作 |
| --- | --- | --- |
| 待填写或待核对 | 当前可信交互及草稿修订 | 按服务端允许动作编辑或决定；第一批已提交字段只读 |
| 预检中 | 当前修订对应的预检作业 | 修改将使旧预检失效 |
| 可以提交 | 有效预览及权限校验 | 批准显示的当前版本 |
| 已授权等待执行 | 授权决定已持久化，执行尚未越界 | 普通流程仅查询，不再修改或取消；计划与批次沿用各自既有合同 |
| 提交或核验中 | 执行器发布的真实阶段事件 | 查看进度，不重复提交 |
| 已核验完成 | 权威业务结果和稳定对象标识 | 查看结果，提供已注册的后续能力 |
| 提交前失败 | 明确尚未越过提交边界 | 修正后重新准备 |
| 结果待核对 | 操作账本的未知终态 | 查看原因、核对结果 |
| 批次部分完成 | 逐项账本与既有计数 | 查看已成功项及停止事项 |

当前执行器的 `verification` 和 `submission_evidence` 主要用于最终结果与诊断，并非完整的实时阶段事件接口。新增事件必须由实际执行位置产生，通过现有任务事件/SSE 传递安全摘要。没有可靠细分事件时，显示合并的“提交与核验中”，不使用计时动画伪造阶段或百分比。

Workspace、MCP App 和宿主摘要采用同一套可验证的状态映射合同。缺少明确业务结果时只显示“状态已更新”或对应交互完成，不默认成功。优先共享纯状态映射及合同测试；各宿主可保留自己的控件和布局，不要求共用整套前端。

未知原因可以区分“仍在待办”“已办证据尚未匹配”“来源不完整”等业务可读信息。不得把原始异常 JSON、接口地址、请求体或观察器资料直接显示在聊天中。

第一阶段的核对入口复用已有任务详情和只读业务查询，保持原未知账本。若增加“再次核验”，应另建只读核验记录，绑定原目标和原操作；不调用 commit，不自动改写历史结果，也不自动推进停止批次。对账后如何结案属于单独的状态转换合同。

## 草稿预览与授权实现

### 流程关联和存储

第一阶段扩展现有任务与交互关联，增加服务端生成的连续办理标识。普通操作按任务与业务意图区分；批次事项再绑定其持久 `item_id`。先后生成的输入、授权和执行记录映射到同一办理过程，底层 ID 与审计记录继续独立。

第二阶段增加专用业务草稿和不可变预览记录，不复用业务助手的技能草稿表，也不修改已冻结授权中的计划。

| 建议数据 | 用途 |
| --- | --- |
| `draftId`、`taskId`、业务操作标识、可选批次事项标识 | 隔离同一用户的并行办理 |
| `revision`、`inputHash` | 乐观并发检查，绑定用户编辑版本 |
| `previewId`、`semanticReviewHash` | 标识用户核对过的业务内容和后果 |
| `planHash`、能力及合同版本 | 授权绑定确切不可变计划 |
| 用户、系统、会话、原权限与技能绑定 | 预检和执行继续复核原身份与权限 |
| 有效期、目标指纹、预检依赖 | 判断候选、目标和会话是否仍适用 |
| 幂等请求键、最终决定和原操作引用 | 响应丢失后查询原回执，避免重复执行 |

当前字段与授权的替代范围由用户、能力和上下文哈希决定。泰华日志及会议创建的上下文为空，并行任务可能互相替代。应在引入反复编辑之前，明确同一业务操作内的替代范围，加入任务和草稿边界，并覆盖字段记录与授权记录。旧记录保持原校验规则，新范围通过版本标识区分，不全局重算历史键。

预览不能逐次调用现有 `authorization.create`，否则会制造授权记录并废止无关授权。将纯业务准备计算与创建授权记录分开，只有最终明确决定才能形成可执行授权。

### 预检调度

纯格式错误在页面立即提示，最终规则仍由服务端校验。项目解析、房间可用性等依赖停止输入或失焦后触发；昂贵的浏览器预检进入有界作业，只保留该草稿最新修订的结果。迟到响应不得覆盖新输入，也不得启用旧版本提交按钮。

预检执行必须携带原可信任务上下文，复核 scope、技能模式、用户会话和目标权限。不得把“预览”作为使用更大服务账号权限的通道。短期草稿值只进入获准的中心存储和可信页面，遵守过期清理及用户隔离；密码、验证码不进入业务草稿。

泰华计划包含每次改变的 `checked_at`。业务变化提示使用归一化的内容与后果摘要，不能因时间戳变化反复要求用户确认；最终授权仍绑定所展示那份不可变计划的完整 `planHash`。纯时间戳变化也不允许后台替换已授权计划。

### 最终决定与恢复

建议由同一中心事务完成以下本地动作：校验可信卡会话与 CSRF、核对草稿修订及有效预览、保存不可变输入快照、创建相应授权及交互、建立原任务和执行上下文关联、保存批准决定、记录幂等回执及待续办意图。对现有 Store 增加可参与同一事务的操作边界，不能连续调用多个各自提交的接口来假装原子性。

关联必须覆盖适用的 `interaction`、`task_interactions`、原 prepare operation、技能绑定、task-plan step 和批次 item，才能把批准记录设为可续办。现有技能及计划检查依赖这些关联寻找执行上下文；先批准、后补关联会出现检查缺席的窗口。发起上下文应要求存在而关联缺失时，整笔决定拒绝；不能把丢失关联当作“无技能或计划约束”。未绑定技能/计划的合法普通任务也须有明确的原始上下文事实。批次 item 在决定时须仍为当前可办理项，并在授权消费时继续复核。

网络提交在事务外执行，由原协调器及既有受控写执行器续办。一次性授权仍在实际提交边界消费，权限撤销和能力版本校验继续在既有边界检查。页面、模型和新增草稿服务都不能直接调用下游写接口。

普通任务当前的取消入口只接受允许取消的 pending 交互；字段已经 submitted 或授权已经 approved 时均不能仅因“尚未消费”而视为可撤回。第一、二批由服务端明确返回可用动作，保留批准后禁止取消的规则；计划和批次的取消沿用自身事务合同。若未来需要批准后、消费前撤销，必须新增与消费竞争的原子合同及相应 UI，不能仅增加一个取消按钮。

待续办意图通过现有持久恢复机制消费；若需要增加持久队列记录，应与决定一起落库，沿用原协调器租约及稳定幂等键。响应丢失时先按请求键查询回执；不能创建第二个授权或生成新幂等键重放。

同一草稿多端编辑发生版本冲突时，保留用户尚未提交的输入并提示重载差异；不能用最后一次写入静默覆盖。任一端批准后，其他端提交按钮立即失效。未执行的旧合同授权按能力兼容规则重新准备，不能迁移成自动批准。

## 宿主与隐私边界

可信字段页和授权页目前禁止 iframe 嵌入。首批在现有可信 Origin 内完成连续页面；不全局关闭 `X-Frame-Options`、CSP 或 Origin/CSRF 校验，不把受保护页面代理到普通聊天域。

建议在现有 presentation 中增加可协商的 `viewKind`、连续办理引用和状态修订信息。外部信封仍只传安全摘要、受限入口和不透明引用。完整字段、计划、授权控制值不放入模型上下文、普通时间线、技能反馈或分析埋点。私有 `_meta` 也不是自动获得可信授权能力的证明。

所有新增展示字段和能力在 Host schema、中央规范化逻辑及宿主适配器中同步定义。旧宿主继续得到其支持的 v1 字段卡/授权卡；声明支持新连续页的宿主才能使用新入口。新页面仍依靠原协调器续办，兼容策略从第一批开始交付。

后续若启用 Workspace 内嵌或 MCP Apps 原生业务视图，需单独定义受限资源、宿主证明、身份绑定和数据通道，并先验证一个真实宿主。Telegram 可复用现有 Mini App 生命周期；微信和其他终端保留可信链接。不能把 MCP App 源码存在解释为当前宿主已能嵌入办理。

业务助手的离开保护、修订冲突提示和差异展示可复用为界面组件，但业务办理值不自动进入技能沉淀。结果卡可后续增加折叠的“反馈本次结果”，绑定原任务的技能版本、模式和 binding，不能归因到目录最新版本。反馈和样例断言均不得改变业务核验结论。

### 验收矩阵

| 用例 | 预期 |
| --- | --- |
| 预填齐全的泰华日志 | 展示项目名称编码与查重结果，一次明确授权提交，取得真实回读 |
| 修改字段时旧预检晚到 | 旧结果不覆盖新输入，旧按钮不能提交 |
| 两个并行日志或会议草稿 | 字段和授权互不替代；同一草稿旧版本正确失效 |
| 刷新、关闭、宿主重启 | 恢复同一办理过程及原操作，不重新发起业务 |
| 双击、多端同时批准、响应丢失 | 最多一个有效决定；按原回执恢复，最多一次下游提交 |
| 取消、权限撤销与提交竞争 | 普通任务批准后禁止取消；计划/批次遵守各自事务合同；已提交不能伪称已取消 |
| 批次当前项取消 | 明确提示停止整个批次，后续项不自动推进 |
| 会话更换、能力版本升级、旧授权 | 重新验证或重新准备，不自动沿用旧批准 |
| 会议室时段改变或被占用 | 候选重新获取，失效选择明确标记，不自动替换目标 |
| OA 原生额外提示、核验读取故障 | 不盲目接受，不重放提交；按权威证据返回成功或未知 |
| 待办部分列表或已办标识冲突 | 不判成功；保持最新核验器的保守结果 |
| 批次两项成功后一项未知，另有两项未处理 | 各行保持自己的状态，总数一致，指向停止事项，后续项不执行 |
| 决定事务中任务、技能或计划关联缺失 | 整笔拒绝，不形成可续办的孤立批准；故障回滚不留下半份决定 |
| 宿主收到缺少业务状态的终态包 | 不默认 `succeeded`，不将交互完成当业务成功 |
| 无富 UI 能力的宿主 | 获得可工作的既有可信入口，不丢失授权及恢复语义 |
| 键盘、窄屏及状态推送 | 标签完整、错误可定位、无焦点丢失；状态更新不覆盖输入 |
| 隐私和历史任务反馈 | 字段值不进入聊天/反馈/技能样例；反馈绑定原执行版本 |

自动化优先覆盖事务竞争、迟到结果、恢复和状态投影等行为；真实页面验收通过 Chrome 扩展完成，真实业务写入只使用用户明确授权的具体事项。测试通过、发布成功、历史只读核验和新业务真实验收分别记录。

新业务草稿及决定记录进入现有存储迁移、备份和恢复验证。采用增加式结构并按能力灰度启用；关闭新入口只影响新建流程。在途已授权流程继续由兼容版本读取和完成，不能因回滚而重放或强制改成失败；旧程序不能理解新记录时不得直接回退接管。

运行代码变更按[开发验证与发布流程](../部署运维/开发验证与发布流程.md)执行定向与 Full，MCP App 有改动时执行其 check/build。各批保留独立发布及验收记录。纯方案文档检查不代替上述工程验收。

## 衡量方式与文档同步

先采集现有流程的完成时长、打开可信页次数、最终动作次数、校验失败重填率和中途离开率，再对同一业务比较。第一批目标是不返回聊天找下一张卡；第二批的合格日志目标是一次最终动作。减少步骤的指标只统计完成预检的适用场景，不能靠省略关键核对提高数字。

同时监测旧预览拒绝、跨端冲突、重复副作用、错误成功状态与未知结果比例。未授权写入、重复副作用和错误宣告成功属于发布阻断项。核验更严格可能增加未知比例，应按真实原因解释，不能放松成功条件。

实施时同步以下现行文档：

- [受控写入模型](../架构设计/受控写入模型.md)：明确独立的授权事实与用户点击次数，记录单次提交适用条件及事务边界。
- [智能体交互协议](../架构设计/智能体交互协议.md)：连续办理引用、展示类型、版本协商、数据投影、恢复归属及旧宿主兼容。
- [智能体工作台](../平台能力/智能体工作台.md)：稳定容器、批次逐项视图、办理页和结果行为。
- [批量受控任务编排设计](../架构设计/批量受控任务编排设计.md)：父容器与逐项授权、展示范围和停止语义；选择冻结与写后核验的完整性合同分别维护。
- [开发安全策略](../部署运维/开发安全策略.md)：新可信决定合同与真实样本授权要求，明确页面合并不减少提交边界检查。
- [后续增强事项](./后续增强事项.md)：校准旧版关于字段卡与授权卡独立页面语义的表述；保持身份验证、授权事实和秘密隔离边界。
- [项目当前状态](../项目当前状态.md)、[文档导航](../文档导航.md)及具体系统说明：只在实际交付后更新功能与验收状态；原有带日期的验收快照保留。

本方案的首个实施范围确定为第一批的连续办理及批次视图；完成后以泰华日志验证单次提交，再扩展业务与宿主。无需先更换前端框架、引入整套生成式 UI 协议，或重建当前已统一的提交核验执行器。
