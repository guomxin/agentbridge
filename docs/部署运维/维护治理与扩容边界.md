# 维护治理与扩容边界

## 代码边界

业务写入名称、字段 Schema、函数绑定和权限表集中在 `agentbridge/core/write_catalog.py`；中央服务不再通过自身全局符号查找业务函数。新增业务先注册绑定，再补模拟测试。

`controlled_write_executor.py` 承担可信字段准备与单次授权提交；它与中央服务共享同一组账本、锁和事务，不创建新的数据库提交边界。`login_recovery.py` 只恢复账本中原用户、原任务、原系统的读取与精确参数。OpenClaw 的 `read-continuation.js` 负责读取描述及展示，原任务事实仍由中央账本决定。计划执行继续由已有 `task_plan_runtime.py` 管理；通知领取、投递和确认仍集中在中央服务，后续可在同一回归保护下继续拆分，不以拆小文件为完成标准。

保护契约：取消不得穿过授权消费边界，结果未知不得重放，普通读取各有任务，登录恢复保留原任务，重复通知不得重复业务执行。M4 的真实 Node—Python—SQLite 测试与受控写边界测试共同保护这些行为。

## 当前事实和发布检查

执行 `python scripts/current_facts.py --write` 更新当前状态的生成区，`--check` 检测漂移。版本来自插件 package.json，数量来自实际构造的注册表与 MCP；不推断已经部署或已经通过真实业务验收。历史验收数字仍属于各自日期。

发布准备先核对实际运行 Release 与 `deploy/release-policy.json` 的 compatibleFrom，并审查数据兼容性；不能仅沿用上一轮声明。该声明和实际 SQLite schema 比较共同决定能否切换与程序回退，不允许为通过发布而使用任意版本通配。

正式发布门禁：本地固定候选全量验证成功 → 同一已验证 wheel 部署 → 在线验收 → 推送 main。发布脚本不再创建 `candidate/<完整提交号>` 或等待 GitHub Actions；main/PR 的 `repository-validation` 在推送后异步运行，不持有生产凭据，也不负责部署或发布放行。`-SkipValidation` 和 `-ResumeAcceptance` 都必须匹配本地完整回执。

main 继续禁止强推和删除；发布入口在推送后回读精确提交。`repository-validation` 不再设为 main 的必需状态检查，否则会重新形成“先远端检查、再允许推送”的循环等待。2026-09-21 曾启用的 `candidate-validation` 必需检查属于历史配置，取消时须单独读回规则确认；历史证据见[补验记录](../验收记录/主分支保护与历史材料盘点-2026-09-21.md)。

## GitHub 检查分级

异步检查名为 `repository-validation`。`scripts/ci_validation_plan.py` 在完整 Git 历史中确定比较基线，并通过 GitHub Actions API 核对前一 main 提交的检查证据；PR 比较与目标分支的共同祖先，main 推送比较事件中的前一提交。比较整个差异，不仅检查最后一次提交；重命名按删除和新增处理。

| 差异范围 | GitHub 检查 |
| --- | --- |
| 仅 docs 下 Markdown 或根 README.md | 文档结构、相对链接、当前事实一致性和既有公开内容检查 |
| 仅上述文档及 deploy/release-policy.json | 增加部署资产、发布事务与制品专项测试；按运行平台保留条件跳过 |
| 运行代码、测试、依赖、工作流、分级脚本、systemd 配置及其他路径 | 原有完整检查 |
| 基线没有成功证据、历史不完整、API 不可用、空差异 | 完整检查兜底 |

main 推送使用事件中的前一提交，PR 使用与目标分支的共同祖先；两者都只信任该基线提交在 main 上最新一次成功的 `repository-validation`，用于证明比较起点。当前流程不读取或复用候选分支运行。手工 workflow_dispatch 或重跑工作流一律强制全量，以便主动复核环境和依赖变化。

每次执行将 profile、基线、全部差异路径、依据运行链接写入 GitHub 步骤摘要及 `ci-plan.json` 产物。只赋予 actions:read 读取证据，不提供生产凭据。API 条件参见 [GitHub 工作流运行接口](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository)。

GitHub 异步检查继续按差异分级；正式应用发布保留本地固定提交全量、wheel 绑定、兼容性与在线验收门禁。Python 全量测试采用 4 worker 并行；局部运行代码尚无完备依赖映射，仍按全量处理，不声称已经自动精准选择全部相关测试。

## 环境配置与公开内容

`deploy/systemd` 是通用示例，使用回环监听及 `.example.test` 下游；默认 TLS，不继承照明明文例外。实际三个运行/备份单元放在仓库外，由 `agentbridge.environment.v1` 配置文件列出 host、root、各单元绝对路径和 SHA256。

发布必须显式传入 `-EnvironmentProfile <仓库外配置文件>`，也可由受控运行环境设置 `AGENTBRIDGE_ENVIRONMENT_PROFILE`。PlanOnly 展示配置路径及单元摘要；目标、文件位置或摘要不符立即拒绝，读取后固定本次使用的字节。配置含真实端点，不能提交仓库；私钥、会话密文、业务结果和完整运行日志也不得放入公开 CI 产物。

原环境配置迁移须先原样复制并核对哈希，再将模板脱敏。服务器仍通过原发布事务安装、核验、切换和回退。应用恢复点包含业务连接配置，不把它说成 systemd 单元的完整副本；外置发布清单与三个单元须独立备份。本轮已在既有独立备份节点保存一次副本并核对摘要（不含解密密钥）；配置变更后必须更新该副本。历史文档和运维辅助脚本尚含真实布局，不宣称整个 Git 历史已经脱敏，不重写历史。每次公开发布仍需人工复核业务内容；高置信凭据扫描通过不能替代此项。

## 资源预算及容量限制

| 层级 | 预算 | 超限行为 |
| --- | --- | --- |
| Auth/Admin/Workspace 每个 HTTP 服务 | 最多 64 个处理连接、每来源 IP 16 个、监听队列 64 | 在线程创建前拒绝新连接，不信任转发头改变来源 |
| TLS 握手 | 10 秒 | 关闭连接并归还额度 |
| 请求头/请求体读取、普通响应写入 | socket 空闲 30 秒；连接绝对寿命 360 秒 | 超时断开；慢速持续发送不能无限延长寿命 |
| 请求体 | Admin 64 KiB，Workspace 普通请求 128 KiB，聊天 18 MiB；Auth 沿用既有限额 | 沿用既有长度检查，认证/CSRF/Origin 边界不变 |
| Workspace SSE | 每已认证 user_subject 最多 6 路，写入超时 30 秒，连接寿命 360 秒 | 第 7 路返回 429；退出和断流释放额度；事件/时间线仍按既有 25 秒轮换重连 |
| MCP HTTP 协议 | 连接 128、每来源 64、队列 64、keep-alive 5 秒；请求头 10 秒、请求体 60 秒；写阻塞 30 秒 | 连接超额或输入/输出超时断开；不计尚未完成的 TLS 握手 |
| MCP 认证请求 | 每真实用户 8、全局 96 个活动请求；多个令牌共用用户额度；POST 最大 18 MiB | 超额 429，不排队；超大请求体 413，业务不执行；退出释放 |

连接额度不等于每用户业务执行预算。来源 IP 限制对共用 NAT 的用户合并计数，应在负载验收后调整。到达全局额度时健康检查也可能被拒绝；不能宣称抵御了分布式耗尽。MCP 已补请求头/请求体预算和按身份拒绝策略，不自动排队或重放。Windows/Linux 隔离容量基准与限制见[MCP 容量补验](../验收记录/协议资源预算与隔离容量补验-2026-09-21.md)。真实混合业务负载、TLS 握手入口容量和跨实例治理仍应在扩大试点前核验；新预算的隔离测试与生产健康验收分别记录。
