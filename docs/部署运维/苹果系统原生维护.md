# 苹果系统原生维护入口

当前代码维护目标为 macOS 开发及受管宿主、Linux 中心服务与 CI。命名统一后的 Python 分发包、导入模块和主命令为 `agentbridge`，旧 `bscli` 命令仅兼容到 `0.3.0`。本页描述新版本操作合同，实际部署状态以[实施记录](../验收记录/命名统一与平台收敛实施记录-2026-10-09.md)为准。

## 环境与验证

使用 Python 3.12 以上创建独立 `.venv`，从可信仓库安装本项目，不从公共索引猜测同名包归属：

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install 'setuptools>=77' pytest pytest-xdist
.venv/bin/python -m pip install --no-build-isolation -e '.[database-analysis]'
scripts/agentbridge-native validate --test tests/test_native_maintenance.py
scripts/agentbridge-native validate --full
```

入口也接受 `AGENTBRIDGE_TEST_PYTHON`。默认日志为 `~/.local/state/agentbridge/maintenance/`，可通过子命令前的 `--report` 指定仓库外私有路径。验证子进程使用临时会话密钥，不继承生产密钥。Full 需要干净、已提交的候选，收据绑定提交、环境、各阶段结果及 wheel。

## 宿主配置

外置 `agentbridge.mac-host.v1` profile 使用权限 0600，必需路径包括 `node`、`openclaw`、`stateDir`、`configPath`、`envFile`、`runtimeDir`、`caCertificate`；`tunnel` 包含 `host`、`user`、`identityFile`、`knownHostsFile`、`remotePort`。路径须为已核验的本机路径；状态和秘密不放在代码仓库内。

`preparationOnly=false` 只用于已审核的正式 profile。宿主固定 OpenClaw 2026.7.1，Gateway 认证不可关闭，保留 `stuckSessionWarnMs=30000`、`stuckSessionAbortMs=120000`。dotenv 按字面值读取，不执行 shell 展开。

受管配置必须明确设置 `plugins.entries.agentbridge-interactions.hooks.allowConversationAccess=true`。
2026.7.1 对非内置插件默认阻断 `llm_input`、`llm_output`、`agent_end`，仅显示插件已加载不能证明这些事件注册成功。
原生入口只校验，不自动修改外置配置；升级时先私有备份并原子更新该字段，再核验配置指纹、宿主登记与授权证据，沿现有条件重启及预热流程发布。
验收使用官方 `plugins inspect agentbridge-interactions --runtime --json` 检查原生模型、工具及结束事件的注册与权限，并核对当前 Gateway 启动后的受管输出未出现插件 typed hook 阻断。
这些证据证明注册可用；各模型执行器是否实际发出模型耗时或 TTFB，仍以实际事件为准，不能把注册或 TTFB 记成 TTFT。

插件加载路径指向固定提交归档时，宿主代码不随开发工作区的 main 或草稿变化。
下一次发布涉及宿主插件变更，须先从最终候选的 Git archive 准备新归档，逐文件核对字节与哈希，
私有备份配置后仅替换 AgentBridge 的加载路径，再由现有发布入口执行条件重启与预热。
当前发布入口不会自动搬运或更新该归档；其 `fingerprint` 哈希发布源码目录，不能单独证明加载目录的内容。
必须另存归档清单，并核对 `plugins inspect ... --runtime --json` 的实际 `source` 与归档一致，
不得把宿主加载路径切回带未验证草稿的目录。原 profile、身份、认证及授权绑定仍按既有流程核验。
本次配置切换与证据见 [历史查询发布验收](../验收记录/历史报告时间范围与接续修复-2026-11-09.md#正式发布与原提示词验收)。

## 宿主登记与授权

日常发布不再读取历史工作站迁移包。新授权绑定当前机器及登录用户、profile SHA256、状态目录和 CA 文件 SHA256，使用 `agentbridge.host-authorization.v1`。更换机器、profile、CA 或状态目录后必须重新登记。

在私有 `agentbridge.host-ownership.v1` 记录中填写：

- `bindings`：`hostId`、`profileSha256`、`stateDir`、`caSha256`，与审核配置的实际值一致。
- `checkedAt`：含时区的实际核验时间；登记时要求在过去 24 小时内。
- `gatewaySingleOwner`、`tunnelSingleOwner`、`identityBindingsReviewed`：只在核验唯一宿主、服务器反向端口和身份绑定后填写 true。

这些是本机操作人员的核验记录，不是远程数字证明。不能为了通过门禁预填 true；日常启动仍检查配置绑定和监听所有权。记录与授权文件都必须位于仓库外，属于当前用户，权限 0600，不允许文件符号链接。

可用原生 `host review` 输出 bindings 和现场只读观察，填写核验记录后登记：

```sh
scripts/agentbridge-native host review --profile /私有目录/mac-host.json
scripts/agentbridge-native host register --profile /私有目录/mac-host.json \
  --ownership-evidence /私有目录/ownership.json --destination /私有目录/authorization.json
```

`register` 不启动进程，不覆盖已有授权文件。旧迁移证据和加密材料保留为历史原件，不转换或修改其内容。

## 生命周期

```sh
scripts/agentbridge-native host render --profile /私有目录/mac-host.json --destination /私有目录/plist-review
scripts/agentbridge-native host status --kind gateway --profile /私有目录/mac-host.json
scripts/agentbridge-native host restart --kind gateway --profile /私有目录/mac-host.json --authorization /私有目录/authorization.json
```

`render` 只生成并校验 plist。`start`、`restart` 需要授权；`stop` disable 后 bootout，避免下次登录自动恢复。固定 launchd label 为 `ai.agentbridge.gateway` 和 `ai.agentbridge.workspace-tunnel`，只使用一套进程管理器。仅登录后恢复，不承诺 FileVault 解锁前运行。

Gateway 固定绑定回环；隧道使用严格 host key、BatchMode、ExitOnForwardFailure 和 keepalive，服务器仅监听回环。发现不属于已验证 Gateway 的监听者会拒绝操作，不抢占端口。安装后的 plist 字节变化时，先停用、核验并归档旧文件，再重新安装。

按内容指纹、PID/启动时间及 readiness 决定是否重启。启动前写入 pending；输入变化或预热失败时保留 pending。当前进程就绪、插件版本和冷/热预热通过后才完成验收。

## 发布

发布所需 `agentbridge.environment.v1` profile 绑定服务器 `host`、服务 `root` 以及三个 systemd unit 的外置文件路径和 SHA256。更改模块入口后须更新外置 unit 及审核哈希；仓库模板不是实际环境配置。

```sh
scripts/agentbridge-native publish --profile /私有目录/environment.json \
  --identity /私有目录/server-identity --known-hosts /私有目录/server-known-hosts --offline
```

默认计划；`--offline` 不联网并标记线上前驱未核验。正式执行添加 `--apply --host-profile ... --authorization ...`；SSH 推送还需 `--github-identity` 与 `--github-known-hosts`。身份隔离验收使用多个 `--identity-label` 和对应 `--expect-endpoint USER_SUBJECT=CLIENT_TYPE`。

发布先用正式校验器核对本机 Full 收据、候选及 wheel。有有效收据就复用，缺少收据或输入失效则执行一次 Full 并再次校验。正在运行或中断的 Full 需先完成。随后依次进行治理测试、复核候选与配置、上传可信 wheel、Linux 事务、条件重启、预热和在线验收，最后推送并回读提交。`--reuse-validation` 严格复用同一候选收据；`--resume` 只补已确认候选的完成与验收，不能重新安装或重启未核验宿主。

根 CA 的正常使用见[命名迁移与证书维护](./命名迁移与证书维护.md)。旧工作站流程仅用于追溯，见[平台迁移历史](../历史归档/平台迁移/苹果系统原生维护旧版-2026-10-09.md)。

## 并列 NanoBot 试点

试点沿用 `scripts/agentbridge-native publish`。Linux 运行中央服务和 Workspace。受管 Mac 上的 NanoBot 独立运行模型、Telegram 消费者和 SSH 回环反向转发。OpenClaw 保留自己的作业、端口和机器人。在正式部署之前，普通用户仍使用已有的工作台和渠道。

### 私有输入与只读计划

环境 profile 的 `nanoBotPilot` 指向外置 0600 配置，记录其绝对路径和 SHA256。普通发布不含此字段时沿用原流程。绑定试点的环境还需显式提供原 Mac 宿主 profile，使发布入口校验机器、SSH、CA 和原端口。新中央 unit 的 `Environment=AGENTBRIDGE_NANOBOT_ROUTES_FILE=...` 必须指向此次审核的私有路由文件，unit 文件及其摘要仍由原环境 profile 管理。

独立宿主配置使用 `agentbridge.nanobot-mac-pilot.v1` 格式，记录稳定的实例和连接 ID、适配器版本、两个已审核中央主体及各自不同的凭据引用、Mac 和 Linux 的独立回环端口、中央 HTTPS MCP 与可信卡来源。运行目录应为本机用户独占。SDK venv 固定 `nanobot-ai==0.4.2`。L3 使用单独锁定 MCP 1.23.2 的协调器解释器，必须具备该版本准确的中央兼容登记。管理员在保存私有环境 profile 时附上试点配置摘要。

模型使用独立、已获授权的服务账号。NanoBot 原生 OAuth 保留一个 0600 的模型身份文件，由宿主实例维护。个人 MCP 凭据、聊天、记忆、附件与操作状态按中央主体区分。独立 Telegram Bot 记录公开数字 ID、用户名和当前 Mac 登录钥匙串中的服务/账号引用。计划和收据仅展示核验结果。正式启用前通过同一作业解释器直接读取准确的钥匙串项，调用官方 `getMe` 核对机器人身份，并确认 webhook 为空。

已运行实例更名时，在新的私有试点配置中填写目标 `displayName`，并以 `displayNameChange.from`、`expectedRevision` 和 `fromRelease` 固定原显示名、目录版本及当前运行版本。使用新的环境 profile 固定这份配置的 SHA256，保留原私有配置和收据。正式计划只读核对实例类型、路由、用户范围、原名称和版本。发布在受管宿主与渠道就绪后更名，并重新读取目录核验结果。目录和管理审计各记录一次变更。显式回退或激活失败时，事务凭本次收据恢复原名称；遇到后续管理员修改时保留现场并要求核对。名称变更不签发个人令牌，不调整实例或渠道归属。

以含试点的 `--profile`、`--host-profile` 和已核验的 SSH 身份运行现有发布计划，会读取当前前驱、目标主体、端口占用及候选兼容级别。此步骤不启用宿主或开通账号。全功能试点要求正式候选支持 0.3.0/L3。0.2.0/L2 的收据仅用于可信交互能力。固定候选的 Full、审核与验收要求依然适用。

### 开通、验证和回退

正式 `--apply` 先复核私有输入。Linux 私有路由保存连接引用及已核验的 Telegram 公共标识，中心持有单独服务连接凭据。中央事务通过后，为明确列入试点的两名已有账号开通独立端点，各自签发单独的中央身份令牌。相同候选的重复开通沿用已核验材料。凭据不符、失效或被撤销时停止，由管理员通过现有令牌管理流程核对或续期。

对尚无 Workspace 账号、仅分配 NanoBot 的新主体，管理员须先核验本人的 Telegram 私聊数字身份并签发个人中央 MCP 凭据。中央私有路由的 `subjects` 登记主体与个人凭据引用，`enrollmentSenders` 登记主体与数字发送者字符串，`telegram.botId` 固定独立机器人。宿主私有配置提供同一 `enrollmentSenders`、`telegramPilot` 及每人一条专用开户身份记录，端点键为 `telegram:<botId>:<senderId>`，个人凭据文件、模型配置和主体分别校验。该实例可见范围须显式分配这些主体。宿主从收到的私聊消息提取发送者，首次开户记录由中央事务持久化。

新用户在 Workspace 选择「首次绑定」，把网页生成的指令发给已核验的独立机器人的本人私聊，回到原网页设置登录信息。中央核对个人身份、实例分配和一次性指令；已消费的开户证明连接到个人 Web 端点。后续撤销 Telegram 对话绑定只影响该渠道。只向用户开放一个可用实例时，工作台自动选作该用户的默认实例。现有试点的正式部署只授权两名原有账号。新用户验收采用隔离数据，命令为 `python -m tests.support.nanobot_enrollment_probe --sdk-python <独立受管测试解释器>`，追加 `--browser` 可打开独立本机环境进行浏览器验收。

Mac Host 从同一固定提交建立独立版本目录，并复用通过 Full 校验的中央 wheel。中央到宿主的请求走第二条严格校验 host key 的 SSH 回环转发。试点配置中的 `tunnelIdentityFile` 与 `tunnelPublicKey` 固定一对新 Ed25519 密钥。发布在 Linux 建立专用无登录账号，检查有效的 sshd 配置，只准该账号监听本次审核的一个回环端口，关闭本地转发、Unix socket 转发和会话；核对原维护账号的有效配置后才加载新策略和公钥。首次开通回退时同步撤下专用公钥。发布前后保留用户默认设置。首次启用要以两个实际 MCP 身份核对主体和兼容级别，并通过中央连接检查适配器版本、已开放能力。Telegram 消费者在此后启动。上线页面复验仍需分别检查账号、历史、卡片和真实渠道回执。

受管 Mac 切换版本与回退共用停服检查。发布依次停止 Telegram、隧道和宿主，按受管 plist 核对服务来源，先向内核登记原进程的退出事件，再等对应 launchd 服务注销。三个作业和监听释放共用 45 秒等待预算，外部命令另有超时。切换版本指针前，Mac 回环监听、Linux 反向端口和 Telegram 独占轮询锁均须释放。遇到其他进程占用资源时，发布保留事务记录。

启动顺序为宿主、隧道、Telegram。中央通过隧道认证宿主后才启动需要恢复的 Telegram 消费者。最终核对连续两次观察的进程号、宿主对指定回环监听的所有权、消费者对轮询文件的独占使用。自动补偿和显式回退按原记录恢复作业，使用相同的交接检查；回退仍受阻时，保留 `restoring`，查明占用后通过原生发布入口的 `--apply --rollback-nanobot` 恢复。


首次开通由发布器自动回退后，修正候选可沿用原正式发布入口。发布器先交叉核对本机回退收据、中央配置审计、原端点及两份已撤销的个人凭据，再为相同的两名主体签发新的凭据。原凭据继续失效。任何来自管理员的独立撤权、身份变更或凭据不符都需要管理员核对。

本机持久记录切换前运行版本与作业所有权。激活失败时恢复原指针和作业。首次开通失败时撤回新实例和专用个人令牌，保留先前 OpenClaw 用户、渠道与账本。需要主动回退时，对同一候选、同一私有 profile 提交 `publish --apply --rollback-nanobot`，保留原 Full 收据、宿主授权和 SSH 输入。中断的切换需要先核对该收据。`--resume` 只验收已确认的试点。中央程序与数据库的恢复继续遵守[独立版本发布与回退](./独立版本发布与回退.md)。

## 并列 Pi 宿主

Pi 在受管 Mac 上使用固定 Node 26.5.0 与 Pi SDK 1.6.0，Python 适配器和协调器随候选归档。相同 SDK 包名下的锁文件、完整依赖树、Node 二进制均受摘要约束。Pi 的模型授权、两个网页用户的 MCP 凭据、服务凭据、受限隧道和渠道账本各有独立归属。[宿主实现](../../integrations/pi-agentbridge/pi_agentbridge/server.py) · [发布配置核验](../../scripts/native/pi_release.py)

部署环境用 `piPilot` 固定仓库外 Pi profile 的路径和 SHA-256。可用 `--pi-profile` 显式核对。纯网页配置登记两名主体；启用 Telegram 时再配置专用 Bot 的钥匙串引用和第一账号的一条获准映射。所有者在 Telegram 桌面创建 Bot、在本人网页发起关联并在原私聊完成证明。账号序号用于人机确认，运行时检查中央主体、Bot、私聊发送者及本次配对。部署时先启动 Pi worker 和隧道，通过中央就绪检查后再启动唯一消费者。[首账号渠道设计](../架构设计/第三宿主与首账号电报私聊接入设计.md) · [本机事务](../../scripts/native/pi_local.py)

隔离开发可执行以下专项。两条 Python 路径分别指向仓库开发环境与 Pi 专用环境，输出文件位于仓库外的私有目录。

```sh
.venv/bin/python scripts/run_pi_conformance.py --node /受管目录/node \
  --sdk-dir /受管目录/node_modules/@earendil-works/pi-coding-agent \
  --engine-python /受管目录/pi-engine/bin/python --level L3 --output /私有目录/pi-contract.json
```

在固定候选上运行[真实模型探针](../../scripts/native/pi_model_observation.py)，按受管配置指定获准服务的 HTTPS 来源。探针向 Pi 发送一次随机回显请求，核对模型、来源与返回值，使用零业务工具。正式上线通过 `scripts/agentbridge-native publish`，核验固定候选 Full、wheel、Pi 精确版本契约、真实模型调用及网页和 Telegram 端点证据。回退 Pi 时由同一入口使用 `--rollback-pi`；只处理事务记录中本宿主的作业、隧道和身份，保留未知业务结果及投递账本。中央数据库结构变化遵循[程序与数据回退规则](./独立版本发布与回退.md)。[分批记录](../验收记录/第三宿主分批接入与验收-2026-11-25.md)

### 固定候选的端点实测

通过 Full 和 wheel 校验后，分别为两个网页账号及已启用的首账号私聊运行 `pi_client_observation.py begin`。每次用返回的新标记，在相应端点发送一条无副作用的个人查询。网页使用 Chrome 扩展，首账号使用 Telegram 桌面客户端。分别把客户端实际显示的本条问题和完整回复保存到仓库外本人独占的文件，再用 `finish` 关联原 Pi 运行。私聊同时比对独立消费者账本里的入站消息、回复消息与送达状态。禁止写入短期卡片链接、登录凭证及无关聊天。两份网页观察须来自各自的端点。第二账号使用单独的拒绝用例，可注入一个未经准入的私聊更新，记录零次派发；在报告中标明注入方式。[客户端观察器](../../scripts/native/pi_client_observation.py)

```sh
.venv/bin/python scripts/native/pi_client_observation.py begin \
  --case telegram_first --output /私有目录/首账号开始.json
.venv/bin/python scripts/native/pi_client_observation.py finish \
```
