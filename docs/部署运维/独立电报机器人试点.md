# NanoBot 独立 Telegram 私聊试点

## 用户怎么用

管理员为现有 Workspace 用户指名开通 NanoBot 实例后，打开工作台的「端点」页查看试点 Telegram 连接。每条业务回复会回到发起查询的私聊。用户保留中央业务权限，并可在 Workspace 单独选择默认宿主。

- 页面显示「已绑定」且来源为现有 Telegram 身份时，使用本人原 Telegram 账号打开试点机器人，私聊发送 `/start`，收到连接回执后发送「查我的待办」。
- 页面显示「未绑定」时，在本人已登录的 Workspace 发起连接。用本人 Telegram 账号打开该试点机器人的私聊，发送页面提供的 `/start` 命令。将机器人回给本次私聊的八位确认码填回原 Workspace 页面并确认，随后即可查询。请求五分钟有效，最多可尝试五次。重新发起会替换旧请求。用户可以在同一页面撤销这次配对。
- 在私聊发送 `/pending` 或「找回原卡」可查看当前任务。回复机器人原业务消息并发送「继续」会重新核对原任务并展示有效入口。出现多项时，回复机器人列出的任务清单并输入编号；清单五分钟有效。
- 回复原业务消息并发送「停止」可让中央取消仍可停止的任务。也可单独发送「停止」，核对列表后回复编号。已提交事项、结果未知事项和过期业务材料继续按原状态处理。审批、提交仍须在对应可信卡内由本人确认。回复原消息并发送 `/status` 仍用于查投递状态。

入站和送达都按 Bot API 提供的机器人、私聊和数字发送者核验主体与授权。沿用旧映射时，中央还检查原 OpenClaw Telegram 端点、路由与中央身份凭据。首次配对要求同一人分别控制已登录 Workspace 和 Telegram 私聊；姓名及转发消息均不能作为身份证明。确认码和私聊启动码应留在上述本人私有界面。[中央配对](../../agentbridge/workspace/telegram_pilot_links.py) · [渠道处理程序](../../integrations/nanobot-agentbridge/nanobot_agentbridge/telegram.py)

## 管理员配置

使用独立 Bot，并为它保留唯一的 `getUpdates` 消费者。现有 OpenClaw 2026.7.1 的 `message_received` 是观察钩子，插件绑定失效后的私聊可回到默认处理。如果两类宿主将来共用 Bot，需要改造一个能持久认领更新、锁定原任务所有者、异常时停止派发且可恢复消费位点的单一入口。独立 Bot 的停止与恢复只影响本试点。[Telegram 获取更新规范](https://core.telegram.org/bots/api#getting-updates) · [设计基线](../架构设计/工作台并列智能体宿主与默认实例设计.md)

在安装候选 AgentBridge 和配套 NanoBot 宿主适配器的私有 Python 环境运行渠道。网关客户端从中央 wheel 提供。宿主 HTTP 服务只监听 IPv4 回环端口。在中央宿主目录为允许的主体分别启用同一实例并创建个人 Web 绑定，将真实 Bot 公共身份配置为路由项的 `telegram.botId`、`telegram.username`。在宿主私有配置写入相同的 `telegramPilot.botId` 和 `telegramPilot.username`，在下方渠道配置启用 `allowWorkspacePairing`；两个服务会从已核验主体导出单独的 Telegram 端点及会话。已有明确管理的私聊可选择配置静态五元组，配置值须与宿主完全一致。个人 MCP 凭据只由宿主读取。[NanoBot 本地网关](../../agentbridge/workspace/nanobot_gateway.py) · [宿主配置与绑定](../../integrations/nanobot-agentbridge/nanobot_agentbridge/server.py)

以下是外置配置的示例，使用合成的账号、ID、端口和路径。真实文件只交给服务用户，配置与服务凭据文件可用模式 0600，状态目录使用 0700。每个系统授权的每一份个人 MCP Token 分别保管。渠道配置只引用服务凭据和 Bot 密钥来源。

```json
{
  "instanceId": "nanobot-office",
  "botId": 8001,
  "botUsername": "example_pilot_bot",
  "botCredential": {"kind": "macos-keychain", "service": "Example Telegram pilot", "account": "example_pilot_bot"},
  "hostUrl": "http://127.0.0.1:8011",
  "hostTokenFile": "/private/example/host-service.token",
  "dataDir": "/private/example/telegram-state",
  "allowWorkspacePairing": true,
  "bindings": {}
}
```

macOS 使用服务进程所属登录用户的 login keychain generic password。由启动进程按配置中的 service 和 account 读取，密钥只进入进程内存。Linux 可在服务 unit 中配置 `LoadCredentialEncrypted=telegram.bot:/etc/credstore.encrypted/telegram.bot` 并将 `botCredential` 改为 `{"kind":"systemd","name":"telegram.bot"}`。systemd 在服务环境提供 `CREDENTIALS_DIRECTORY`。密钥只能向 Telegram 官方 HTTPS Bot API 发送。[凭据读取实现](../../integrations/nanobot-agentbridge/nanobot_agentbridge/telegram_credentials.py)

```sh
/path/to/private-venv/bin/python -I -m nanobot_agentbridge.telegram --config /private/example/telegram.json
```

渠道启动时核对官方 `getMe` 返回的机器人 ID、已配置的用户名和空 webhook。必须使用试点 Bot 的专属凭据。运营者以已有宿主进程管理方式维护唯一消费者。正式上线遵循[固定发布入口](./发布操作手册.md)。正式开放前，分别核验两人的私聊回执与原有权限，记录试点人员自发消息的真实回执。普通聊天、按钮与回复均不能消费中央执行授权。

已绑定的用户可在私聊中直接发送照片，或以文件发送 PNG、JPEG、WebP 截图与静态 WebP 贴纸。可随附件填写问题。机器人还能阅读 UTF-8 文本、CSV、Markdown、JSON 等文本文件和含可提取正文的 PDF。单件最多 6 MiB，文档最多向模型提供前 24,000 个字符。扫描件可以截图发送，语音可先转为文字。每条附件消息独立处理。Workspace 时间线显示随附问题或附件提示，附件原件只在本人宿主的临时目录参与本次处理。[入站媒体处理](../../integrations/nanobot-agentbridge/nanobot_agentbridge/telegram_media.py)

## 状态与回退

- `working` 表示已识别原运行。原受理回执丢失后，消费者凭原消息号只查询该运行。结果能核对时回复原会话。
- `admission_unknown` 表示无法找到对应的受理记录。该消息重送或重启后均不会再触发业务调用。
- `delivered` 表示 Bot API 确认了机器人、目标私聊、回复消息号及送达消息号。`delivery_unknown` 表示发送可能已完成但缺少可核验回执；消费者记录未知并停止重发。用户可回复自己的既有机器人消息并输入 `/status` 查询原消息的投递状态。
- 已通过 L3 协商的试点接收原私聊任务的中央终态。发送前再次核验该数字账号、端点、会话及原消息，并核对中央任务与本地主机记录。多个终态事件共用一次私聊送达。回执丢失后停止再次发送，只向中央对账；即使中央最终将投递标为失败，原业务终态仍可在 Workspace 查阅。自动订阅不会把其他宿主的任务广播到这个 Bot。[终态消费者](../../integrations/nanobot-agentbridge/nanobot_agentbridge/notifications.py)
- 回退时停止独立消费者，保留其私有 SQLite 账本、服务配置和原请求归属，必要时再撤销试点绑定。只把新会话默认值改回 OpenClaw。恢复时沿用原 Bot ID、同一状态目录及原消息编号。

## 0.3.0 的跨端任务与文件

本轮候选使用 NanoBot SDK 0.4.2 和 AgentBridge 宿主适配器 0.3.0。中央登记并接受该宿主的 L3 能力后，用户可从试点私聊发起获准的业务，在同一实例的本人 Workspace 打开原生授权卡。短期卡链接只呈现在对应的私有界面。中央协调器将授权关联到原 Telegram 任务、租约与会话，业务核验后将公共结果返回原私聊。Workspace 可主动查看本人的任务、文件与投递状态。Workspace 发起的任务不会自动通知该用户的其他宿主或 Telegram 私聊。[跨端授权探针](../../tests/support/nanobot_telegram_write_probe.py) · [中央任务订阅](../../agentbridge/core/tasks.py)

证书 PDF 与查询 CSV 可从原任务的 Workspace 文件栏续取。宿主重新签发时，中央核对当前主体的下载权限、制品与原任务，以及实例、端点和租约。原租约到期后，用户仍可在本人 Workspace 通过中央原生下载流程按当前权限重新申请。该操作不会续活已过期的业务租约，也不会重做业务。撤回权限后，中央拒绝对应 PDF 的下载与重新签发。在注册为 L3 的 NanoBot 私聊中，用户可准备本次查询中的单份或多份证书，或按当前权限导出 OA 通讯录和照明报表。证书由本轮查询的选择项定位，导出沿用中央对来源、报表类型与可见数据的约束。[四个入口的原任务回归](../../tests/test_nanobot_file_generation.py)

针对从 NanoBot 本人 Telegram 私聊发起、已在中央原任务登记的 PDF 或 CSV，宿主在发送前复核当前配对、制品有效期和权限，再逐件上传至来源私聊。中央文件栏的附件投递状态以 Telegram 返回的对应私聊消息回执为准。发送中断且无法确认时，记录结果未知并停止自动重发。此回执无法确认手机已显示或用户已打开文件。短期下载地址不进入模型或通知正文。[私聊文件投递回归](../../tests/test_nanobot_telegram_artifacts.py) · [文件验收实现](../../tests/support/nanobot_b4_files.py)

在已绑定的私聊里可要求「汇总已办和已发，生成工作日志供我确认」。中央按同一任务执行读取与转换，最后一步可使用本人已获准的受控准备能力。选用业务助手时继续使用原助手的版本、模式及数据源权限。涉及写入时，在本人可信卡核对并确认。中央的原计划和末步业务核验证据共同决定是否显示成功。[计划工具](../../integrations/nanobot-agentbridge/nanobot_agentbridge/plans.py) · [原任务卡](../../integrations/reference-host/reference_host/bound_plans.py)

## 可重跑的验收

[Telegram 专项](../../tests/test_nanobot_telegram.py)覆盖双私聊、撤权、重放、身份歧义、消息位置和回执不确定性。可在独立新目录启动[中央夹具](../../tests/support/nanobot_mcp_fixture.py)的 `--telegram-bindings`，再用装有 NanoBot 0.4.2 的解释器执行[端到端探针](../../tests/support/nanobot_transport_probe.py)的 `--telegram` 或 `--telegram-console`。Chrome 页面提供两个独立用户入口。宿主、SDK、中央 MCP、授权与收据运行实际代码，Telegram、模型和 OA 样本使用本机合成服务。运行此验收不需要真实 Bot Token。

从仓库根目录运行以下两条命令。前一个 Python 环境需安装当前中央项目依赖，`NANOBOT_PYTHON` 指向装有上述 SDK 的独立解释器。两个探针都会自行建立隔离环境。

```sh
python -m tests.support.nanobot_b4_contract --nanobot-python "$NANOBOT_PYTHON"
python -m tests.support.nanobot_telegram_write_probe --nanobot-python "$NANOBOT_PYTHON"
```

- H13 核对同一原任务 PDF、CSV 的实际字节和跨用户拒绝，另核对 PDF 撤权及已过期租约维持原状。Chrome 在本人 Workspace 续取并点击 CSV 下载，工作台下载器完成 HTTP 200 响应，29 字节。Chrome 扩展没有回传下载事件，浏览器本地落盘未核实。[文件与通知契约探针](../../tests/support/nanobot_b4_contract.py)
- H14 模拟 Telegram 已收到发送请求但应答丢失。原业务仍为 `succeeded`，本地渠道记录 `delivery_unknown`，向 Telegram 仅发送一次，中央五次对账后将通知记为 `failed`。另一主体状态未变化，自动跨宿主投递数为零。另一个跨端探针用合成私聊发起请假草稿，在本人 Workspace 消费授权，原私聊运行获得业务核验结果，合成下游只写一笔。[终态通知探针](../../tests/support/nanobot_b4_notifications.py) · [当轮验收记录](../验收记录/工作台并列宿主与纳米机器人试点-2026-11-23.md)

## 真实试点的证据边界

2026 年 11 月 23 日，受管 Mac 的服务解释器通过钥匙串读取独立凭据，向 Telegram 官方只读调用 `getMe` 核对试点用户名 `ag_nanobot`，并通过 `getWebhookInfo` 确认当时无 webhook。中央生产只读核对的两个活动 Workspace 账号中，一个已有可复用的 Telegram 数字身份，另一个账号只使用 Workspace。上述双私聊和异常回执均已使用合成渠道验证。正式发布后，两个账号均已获得 Workspace 访问权。原有 Telegram 账号本人确认收到了试点 Bot 的验收回复，渠道账本核实了一个私聊中与模型运行对应的送达回执。[当轮验收记录](../验收记录/工作台并列宿主与纳米机器人试点-2026-11-23.md)
