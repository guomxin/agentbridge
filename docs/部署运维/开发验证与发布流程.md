# 开发验证与发布流程

当前支持 macOS 开发及宿主、Linux 中心服务与 CI。项目安装、宿主登记和发布参数见[原生维护](./苹果系统原生维护.md)。行为变更执行定向测试和完整回归；纯文档变更执行文档检查。

## 小改动执行流程

适用于局部功能、缺陷和交互修正。按影响范围判断风险，不能因为需求描述简短或修改行数少，就把认证、公共布局、授权、材料校验或发布链路视为低风险。目标是尽早暴露问题、形成一次合格候选，减少返工；不是限制必要测试次数或压缩发布门禁。

### 1. 先限定范围与验收结果

开始实现前，在任务记录中简要列明：用户问题、已确认原因、预期行为、预计触及的模块、必须保持的安全边界，以及定向和实际页面验收场景。先检查现有能力是否能恢复故障，再决定需要修改的代码；恢复操作与产品修复分别记录结果。

优先复用现有组件和流程，不顺带重构、升级依赖或调整全局布局。新增提示条等局部功能，先验证能否在原布局约束内实现；若必须修改公共容器、滚动、高度或定位，须说明必要性并扩展相关页面验收。新发现的问题按“阻塞本次交付”和“独立后续改进”区分；阻塞问题必须解决，独立改进记录后续，不混入当前候选。

保留用户原有未提交修改，不因追求干净候选而自动提交、覆盖或清理这些文件；通过隔离候选准备验证与发布。

### 2. 按依赖关系并行，不共享可变状态

| 可以合理并行的工作 | 前提与边界 |
| --- | --- |
| 代码和日志只读检查、验收场景设计、文档草稿 | 先明确同一问题与目标，避免重复调查；检查线上状态不产生业务写入 |
| 后端与前端定向测试、独立页面验收准备 | 使用隔离测试 home、数据库、端口、输出目录和账号；不得互相改写夹具或构建产物 |
| 固定候选 Full、文档整理、发布只读预检 | Full 的源码与制品输入保持不变；预检不执行部署或修改宿主配置，发布前仍须重新核对线上前驱和相关指纹 |
| 正式发布后的独立 CI、线上只读验收、验收文档整理 | 发布事务已成功；CI 与浏览器验收均针对已发布候选，记录各自结果 |

同一 OA 会话的操作、同一浏览器标签的操作、同一文件的编辑、共享数据库变更和发布事务必须串行。并行不代表绕过授权或启动多个真实业务请求；有依赖的步骤必须等前置结果确认后执行。只在预计能缩短总耗时且资源可隔离时并行，不为并行本身增加协调成本。

### 3. 在 Full 前完成有代表性的验收

先完成实现与定向回归，再在隔离 Workspace 验证真实使用规模下的行为，修复发现的问题后才固定正式候选。实际浏览器操作默认使用 Chrome 扩展；合成下游与真实业务的证据分别标注。

- 页面及布局变更须覆盖长历史/长文本、空状态和多条结果，以及新增提示出现、更新、消失的过程。长历史必须足以触发内部滚动，不能只用几条消息证明布局正确；2026-10-26 的 160 条长消息夹具可作为复现参考，并按当前生产规模调整。
- 检查导航、输入框、滚动位置、按钮和表单可用性；涉及高度或滚动时，结合截图和页面边界测量验证。修改响应式规则时覆盖受影响窗口尺寸，涉及移动端安全区或软键盘时单独记录实测与未测边界。
- 状态反馈须覆盖成功、认证/权限失败、超时、恢复、刷新及长时间停留；确认提示及时更新，终态或已有业务操作不被旧诊断覆盖，不诱导重复提交。
- 根据改动影响覆盖账号隔离、材料有效期、授权消费、未知结果不重放和业务核验。不得用视觉测试代替安全与业务回归，也不得通过放宽校验使验收通过。

验收失败先分析根因并修复；只有实际修正、原测试失败或仍有未解决风险时，才追加或重跑对应检查。无新增证据不机械重复已通过的同一组测试。

### 4. 固定候选后保留完整门禁

行为变更仍执行下文要求的干净候选 Full、制品验证和正式发布流程，不因“小改动”降为仅定向测试。定向及独立页面验收不能替代 Full；Full 也不能代替实际页面验收。

同一候选且全部绑定输入有效时，按正式入口复用已通过的 Full 收据，避免发布时无条件再跑一遍。候选源码、构建输入或工具环境改变时，须由正式收据/制品校验判定是否仍有效；失效必须重新执行所需门禁，不能手工修改收据或拿旧候选通过结果代替新候选。修复生产回归的补发也遵守此规则。

### 5. 发布后验收与文档收尾

按[发布操作手册](./发布操作手册.md)完成事务、版本核对和线上验收。线上验收必须重看本次涉及的页面及关键状态，不能只以健康检查成功作为交互验收通过；发现回归按影响决定修复或回退，不把它留给用户发现。

推送后 CI 与线上验收可并行，文档在等待期间整理。若后续文档提交会取消同分支正在运行的候选 CI，应先等该轮完成，再校验和推送最终文档；只保留一轮必要的文档收尾，避免零散提交反复打断检查。最终文档提交按 docs 流程验证，不重新部署或重启服务。文档 CI 的最终回执可保存在外部验收证据中，避免为回写自己的 CI 结果制造无休止的新提交。

### 6. 记录耗时与返工原因

验收记录注明候选、测试和发布回执，并分别记录诊断、实现、定向/页面验收、Full、发布、CI 和文档阶段的实际耗时或起止时间，标明并行重叠，不能把并行阶段时长相加当作总耗时。发生补发时写明缺陷、为何未提前发现、增加的验证场景和额外等待；不能将实现缺陷或测试样本不足造成的返工笼统归因于“流程严格”。

等待外部检查时使用有界、适当间隔的状态读取，优先完成不依赖该结果的工作；没有新状态时不反复触发相同检查。时间估计用于暴露阻塞和改进执行顺序，不作为跳过验证的截止线。交付时准确区分已实现、已验证、已发布和仍未验证的事项。

本流程依据[2026-10-26 凭证修复复盘](../验收记录/凭证续期与查询等待修复-2026-10-26.md#执行效率复盘与规范改进)制定；现行授权、材料校验、业务核验、备份和回退要求不变。

## 定向验证

```sh
scripts/agentbridge-native validate --test tests/test_central_service.py --test tests/test_documentation.py
scripts/agentbridge-native validate --plugin
```

MCP App 修改还须在 `integrations/mcp-app` 执行 `npm run check` 和 `npm run build`，生成资源位于 `agentbridge/mcp/static`。

## 完整验证

```sh
scripts/agentbridge-native validate --full
```

共享计划包含浏览器依赖准备、公开内容和当前事实、全量 Python、编译、依赖检查、Workspace Node、OpenClaw 测试与打包、固定 Git 提交 wheel 和隔离安装。前端修改可通过 `.venv/bin/python scripts/validation_plan.py full --root . --mcp-app` 把前端验证加入正式收据。

Full 要求已提交的干净候选，收据绑定输入、工具版本、执行结果和制品。定向检查不创建 Full 收据。测试使用临时密钥，不继承生产会话密钥。真实浏览器与业务验收单独记录，不能把 opt-in 跳过项写成已验收。

## 发布与线上验证

使用[固定发布入口](./发布操作手册.md)。本地可信 Full 和制品验收是发布门槛；GitHub `repository-validation` 为推送后的独立回归记录。CI 按可信历史选择 docs/release/full，历史身份无法核实时退回完整验证。

发布修改运行代码、unit 或运行行为时，保持前驱兼容、备份、回滚、宿主实际版本和身份隔离门槛。真实业务写入仍遵守[开发安全策略](./开发安全策略.md)，不能因发布回归自动提交、审批或撤销。

历史工作站流程与当时的授权记录保存在[旧流程快照](../历史归档/平台迁移/开发验证与发布流程旧版-2026-10-09.md)，不作为当前命令入口。
