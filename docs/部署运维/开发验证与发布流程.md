# 开发验证与发布流程

## 小改动执行流程

每批围绕用户要求的行为完成实现、定向测试和功能验收。优先验证原失败路径和本次改动可能影响的相邻行为，保留用户指定的逐批验收端（例如 Chrome 扩展和 Telegram 桌面）。集中修复阻塞项，随实现更新受影响的夹具、验收脚本和版本登记，独立改进留待后续。

按实际影响选场景。例如，布局可能影响滚动时，用足够长的历史记录触发滚动。改重试时验超时、恢复与未知结果不重放。改身份或队列时，用符合生产的凭据关系或旧记录验证隔离与交接。涉及页面或状态时，通过隔离环境的实际入口核对用户可见结果。已有结果仍适用时直接复用，修正、失败或风险尚未覆盖时只补验相关场景。

并行测试隔离账号、数据库、端口和输出目录。共用的会话、标签、文件编辑及发布事务串行。

普通任务在现有任务说明或 PR 中写清改了什么、怎样验证、还剩什么，附测试或发布回执。区分合成验证与真实验收，按实际结果标明发布状态。异常耗时、返工或回退时，再补原因和关键时间点。

## 定向验证

本机默认运行 `scripts/agentbridge-native validate --changed`，检查相对 HEAD 的暂存、未暂存及未跟踪文件。已提交的改动通过 `--base` 指定已核实的祖先提交。暂存与工作树同一路径不一致时先对齐，混有其他人的草稿时在隔离工作区验证本次改动。

纯文档变更走文档检查，随 wheel 发布的业务技能 Markdown 按运行代码处理。具体分级以[分流脚本](../../scripts/ci_validation_plan.py)为准。遇到 `full_required`，开发阶段先运行受影响功能的定向测试，例如 `scripts/agentbridge-native validate --test tests/test_central_service.py`。MCP App 改动还须在 `integrations/mcp-app` 执行 `npm run check` 和 `npm run build`。

## 完整验证

多批合并发布时，在各批功能验收通过后，将待发布改动固定为一个干净提交。只有某批独立发布、约定的验收确实依赖固定制品，或用户明确要求时，才提前固定相应候选。

行为变更发布前须取得该候选的本机 Full 收据和对应 wheel。完整验证入口为 `scripts/agentbridge-native validate --full`。涉及 MCP App 的前端改动可用 `.venv/bin/python scripts/validation_plan.py full --root . --mcp-app` 将专项加入收据。可选浏览器用例的跳过项与实际页面验收分别记录。本机 Full 与 GitHub 检查的分工见[验证分级说明](./维护治理与扩容边界.md#github-检查分级)。

## 发布与线上验证

按[发布操作手册](./发布操作手册.md)核验候选、执行发布，并从受影响的真实入口复验。线上只读验收与独立 CI 可并行。文档收尾集中一次；若推送会取消候选 CI，先等其结束。纯文档提交只做文档检查，无需重新部署。
