# AgentBridge 运行治理操作手册

> 适用范围：当前内网试点部署 `10.10.50.213`
>
> 更新日期：2026-09-06
>
> 原则：先判断副作用边界，再决定恢复方式；任何已经尝试业务提交但结果未知的操作都不得自动重试。

## 1. 日常入口

管理员使用 `https://10.10.50.213:8782`。运行治理主要位于两个页面：

- **链路追踪**：回答“这次请求走到哪一步、哪一步耗时、是否触及业务系统”；
- **事件治理**：回答“现在有什么需要处理、严重程度、是否已确认、允许采取什么恢复动作”。

无需登录的探针：

```bash
curl --cacert /path/to/root-ca.crt https://10.10.50.213:8782/healthz
curl --cacert /path/to/root-ca.crt https://10.10.50.213:8782/readyz
curl --cacert /path/to/root-ca.crt https://10.10.50.213:8783/readyz
```

`healthz` 只证明 HTTP 进程存活；`readyz` 还检查运行数据库和治理表，Workspace 就绪还要求
OpenClaw Gateway 已配置。发布和恢复接流量必须看 `readyz`。

## 2. Trace 怎么看

一个 Trace 代表一次用户请求或一次可关联的后台运行。优先按以下顺序检查：

1. 核对 `userSubject`、宿主、任务 ID、系统和能力，防止把另一用户或另一轮请求混进来；
2. 看 Trace 状态是运行中、等待用户、成功、失败还是结果未知；
3. 展开 Span 时间线，定位宿主受理、MCP、能力编排、适配器、可信交互、业务提交、回读和投递；
4. 找耗时最长或最后结束的 Span，不把“通知失败”误判成“业务失败”；
5. 最后确认“最远副作用边界”，再选择恢复动作。

Trace 只保存运行元数据、耗时、错误码和对象关联，不保存聊天正文、密码、Cookie、业务字段值
或可信卡片 URL。

## 3. 副作用边界

| 边界 | 已发生的事实 | 可采取的动作 |
| --- | --- | --- |
| `B0_NO_EFFECT` | 尚未访问业务系统 | 可以有界恢复宿主或重新受理 |
| `B1_READ_ONLY` | 只发生读取 | 可按读取策略重新查询 |
| `B2_INTERACTION_CREATED` | 已创建可信卡片 | 等待用户处理；不要重复生成同一轮卡片 |
| `B3_PREPARED_AUTHORIZED` | 已准备或已授权，尚无提交证据 | 核对冻结计划、卡片状态和过期时间 |
| `B4_COMMIT_ATTEMPTED` | 已尝试业务提交，结果可能未知 | 停止自动重试，进入人工对账 |
| `B5_VERIFIED` | 权威业务状态已回读确认 | 只恢复通知或文件交付，不重做业务 |

最重要的分界是 `B4`。例如 OA 已收到“提交出差申请”的请求，但网络在响应前中断，系统无法
证明成功或失败。此时重复提交可能产生两条流程，必须先查看 OA 已发事项或详情，再人工结案。

## 4. 事件处理

### 4.1 严重程度

- `P0`：跨用户隔离、未经授权副作用等安全底线异常，立即暂停相关能力并人工处置；
- `P1`：结果未知写入、持续不可用或可能影响较多用户，需要优先核对；
- `P2`：卡住任务、持续投递失败、会话保活连续异常，需要当班处理；
- `P3`：退化、短时积压或观察信号，可在工作时段处理。

### 4.2 生命周期

```text
open -> acknowledged -> investigating -> resolved
                          `-> suppressed
```

- **确认**：表示管理员已经看到，不代表故障消失；
- **调查中**：已开始排查，并记录原因；
- **已解决**：有明确恢复、对账证据，或负责人明确接受开发遗留事项并记录结案原因；不代表业务提交成功；
- **已抑制**：规则在已知窗口内不需要继续提醒，必须写明原因。

检测器使用稳定指纹合并相同症状。瞬时卡住、积压等可在证据消失后自动解决；结果未知写入不
自动结案，必须保留人工对账结论。

### 4.3 历史事件与重复检测

事件页默认展示“当前异常”；超过 24 小时的未结案结果未知事项进入“历史待核对”，解决或抑制后的记录进入“已结案”。历史分类并非自动结案，顶部未结案计数仍包含历史事项。

“最近检测到”表示后台刚检查过这条记录，不表示用户刚执行过业务；“累计检测次数”也不是业务执行次数。应结合关联操作发起时间判断实际业务发生时间。

对开发遗留事件，必须确认范围、留下原因并保留审计，不能删除原始 Operation 或把 `unknown` 改成成功。已解决或抑制的 `write_outcome_unknown` 按不可变的操作 ID 记住处置结论，后续检测不再重开；新操作 ID 仍正常产生事件。卡住任务、投递积压等其他规则保留原有恢复和复发检测行为。

## 5. 允许的恢复动作

管理台只允许以下治理动作：

| 动作 | 适用条件 | 不会做什么 |
| --- | --- | --- |
| 重新投递通知 | 投递状态为失败、延期或归档，业务结果已确定 | 不重新调用业务能力 |
| 归档投递 | 投递失败或已确认，不再需要继续发送 | 不删除任务和业务审计 |
| 立即运行评估 | 需要立刻刷新事件和 SLO | 不访问下游业务系统 |

每次动作必须填写原因，生成幂等恢复账本和管理审计。同一个幂等键在执行中或结束后再次提交都
只返回原记录，不重复执行。

以下动作不在管理台提供：重新提交业务写入、替用户批准、撤销业务流程、修改服务器文件、查看
凭据或清除其他用户会话。

## 6. 常见排障顺序

### 6.1 用户看到“智能体暂时不可用”

1. 查看 Workspace/Gateway 是否就绪；
2. 查对应 Trace 是否只有 `host.accepted`，还是已经进入 MCP；
3. 若停在 Gateway 前且边界为 `B0`，检查反向 SSH 隧道和 OpenClaw；
4. 若已进入能力或适配器，按系统会话和错误码继续定位；
5. 不因宿主超时自动重做已经越过 `B4` 的业务动作。

若 OpenClaw 日志出现 `AgentBridge MCP is unreachable`，同时中央服务前后都有正常请求，优先
检查同一条工具调用的 `transportCode`。当前宿主只对幂等只读和 `prepare` 入口使用 0.5 秒、
2 秒的同键短重试；`ECONNRESET`、`UND_ERR_*`、HTTP 502/503/504 等根因会保留在日志里。
短重试成功后业务继续，不向用户重复显示中间失败。`commit`、`MCP_TIMEOUT`、已尝试提交或
`RESULT_UNKNOWN` 不自动重试，仍按副作用边界对账。

### 6.2 业务成功但 Telegram、微信或网页没收到

1. 先找 Trace 的业务回读是否达到 `B5_VERIFIED`；
2. 再看 `delivery.claimed`、`delivery.result` 和 Task Hub 投递状态；
3. 网页端是 SSE 拉取，Telegram/微信是通道直推，分开判断；
4. 业务已确认时只重投通知，不重新调用业务能力；
5. 微信缺少活动消息令牌时保持 `deferred`，等待用户下次活动后恢复。

Workspace 的聊天响应和任务更新使用 SSE 长连接。浏览器刷新、切网或主动离开页面时，服务端
可能收到 `ssl.SSLEOFError`、`BrokenPipeError` 或 `ConnectionResetError`。这些错误只表示该次
响应连接已断开，不等于 OpenClaw、MCP 或业务失败；服务端应安静结束写流，浏览器随后从中央
时间线恢复已经入账的结果。

### 6.3 卡片一直等待用户

核对交互状态和有效期。只有 `pending`、`claimed` 或 `processing` 才是当前等待；已经完成、过期、
取消或被替换的旧卡片不应计入未决事件。不要通过重复创建卡片绕过状态判断。

### 6.4 会话失效

只检查对应用户、对应系统。保活资格表示仍在活动租约内，不等于目标系统永不失效；下游主动
注销、令牌不可刷新或身份不匹配仍会要求重新登录。不得清除其他用户或其他系统会话。

## 7. SLO 与观察期

事件治理页展示最近 24 小时的试点指标：

- 已终结 Trace 的成功率；
- 结果未知写入数量；
- 卡住操作、任务和投递数量；
- 跨用户隔离违规数量；
- 未授权或重复副作用数量。

等待用户和仍在运行的 Trace 不进入成功率分母。当前指标用于影子观察和阈值校准，不等同于
企业生产 SLA。零容忍指标一旦非零，应停止相关写能力并调查。

七天影子观察由中央治理线程按小时采集运行摘要、24 小时 SLO 和事件数量，并按 UTC 日期生成
日汇总。重复启动同名活动观察不会创建第二批。启动、查询命令和零业务副作用边界见
[本机宿主自愈与可靠性演练](./本机宿主自愈与可靠性演练.md)。

## 8. 备份与校验

M2 的四库一致恢复点、密钥依赖、短期状态失效和隔离演练，以[完整恢复基线操作手册](./完整恢复基线操作手册.md)为准。旧单库备份仅保留兼容校验，不满足 M2 验收。

### 8.1 自动备份

服务器由 `agentbridge-backup.timer` 每日触发 `agentbridge-backup.service`，默认保存到：

```text
/home/guomao/agentbridge/backups
```

备份使用 SQLite 在线备份 API，将四个运行库、系统配置和凭据密文纳入同代压缩包；固定快照时的提交冲突、数据库替换或必要文件变化会整批重试，固定快照后的 WAL 正常提交不影响复制。生成包含成员 SHA-256、大小、时间和 Release ID 的清单。部署验收
检查 timer 已启用、最近一次服务结果成功。默认保留 30 天。

### 8.2 手工创建与验证

```bash
sudo -u agentbridge env AGENTBRIDGE_SESSION_KEY_FILE=/home/guomao/agentbridge/config/session.key /home/guomao/agentbridge/venv/bin/python -P \
  -m agentbridge.cli.main --home /home/guomao/agentbridge/data \
  diagnostics backup-create --output-dir /home/guomao/agentbridge/backups

sudo -u agentbridge env AGENTBRIDGE_SESSION_KEY_FILE=/home/guomao/agentbridge/config/session.key /home/guomao/agentbridge/venv/bin/python -P \
  -m agentbridge.cli.main --home /home/guomao/agentbridge/data \
  diagnostics backup-validate --backup /path/to/manifest.json
```

验证包括哈希、SQLite `quick_check`、必要表和用户主体关联隔离。验证过程只读，不替换线上数据库。

### 8.3 恢复边界

M2 演练在 `data/restore-drills` 新建隔离副本，校验四库、成员摘要、主体关系、授权和凭据解密；
仅在副本中将旧会话与短期交付状态置为过期，再以只读模式打开四库并证明写入探针被拒绝。
没有自动覆盖线上数据库或启动恢复出的服务。正式切换仍须在维护窗口保存现状、审查待执行任务
并人工执行；数据源凭据依赖匹配密钥，旧业务登录会话一律重新登录。

恢复演练使用上面的原生 CLI，在固定服务身份和已审核密钥环境中执行。

## 9. 故障注入

本地安全验证：

```sh
scripts/agentbridge-native validate --test tests/test_runtime_governance.py --test tests/test_runtime_backup.py --test tests/test_recovery_bundle.py
```

这些验证使用临时数据和测试密钥，不访问真实下游或执行业务写入。需要真实备份演练时使用上文 CLI 并显式选择业务目录。

Gateway 和反向隧道由 launchd 管理，恢复合同见[本机宿主自愈](./本机宿主自愈与可靠性演练.md)。验证唯一 PID、回环监听、当前进程插件注册及 pending 预热，不抢占未知端口，不自动重放业务请求。

## 10. 发布后检查

原生发布器自动执行 readiness、TLS、MCP、当前版本、备份、宿主和回环转发验收。双用户验收通过 `--identity-label` 与 `--expect-endpoint` 显式选择，参数见[发布操作手册](./发布操作手册.md)。

完成后在管理台确认：

1. 新请求能形成 Trace 和 Span；
2. 事件评估可以运行，恢复账本可见；
3. 两个用户的 Trace 只能显示各自 `userSubject`；
4. 没有新增 P0/P1 安全事件；
5. 最新备份清单验证通过。
