## 重构目标与现有基础

主要扩展成本是能力定义与规则跨入口分散、中央服务依赖隐含，以及多个生命周期混在同一模块中。
保留模块化单体，通过明确合同和事务逐步划分职责，使新增一个业务能力不必同步修改多个无关生命周期。

现有能力注册与执行器、`write_catalog`、受控写执行器、登录恢复、持久计划、宿主 Schema 和共享向量、
用户隔离、配置外置、资源预算、固定提交制品、备份恢复均继续复用。业务技能二期已具备结构化创作、
持久生成与评测、审批发布及固定版本绑定，不重新列为待建设能力。

## 必须保持的行为

- CLI、MCP、Workspace 和现有宿主公共名称、身份归属、业务参数及既有合法调用保持兼容。
- 写入继续执行准备、可信字段、独立授权、私有提交和权威回读；权限、会话、目标及版本仍在提交边界复核。
- 计划取消、技能撤销检查与授权消费共享既有 SQLite 事务，不能因服务拆分而分别提交。
- 已受理宿主请求只观察同一 run；结果未知不重放，来源不完整不执行派生写入。
- 多用户的消息、任务、附件、会话和回复路由保持隔离；重复通知不重复执行业务。
- 迁移要兼容已有持久记录；旧终态、明确后续操作及登录恢复按既有规则处理。
- 发布仍绑定干净固定提交、实际输入与同一个已验证 wheel；开发测试不能冒充正式发布回执。

## 分批实施策略

第一批先修正已复现的一致性窗口并补齐验证保护网，不引入新的业务能力、数据库表或宿主。
完成定向失败注入后，再运行全量离线回归和安装包验证。

2026-10-04 用户在第一批完成后明确取消后续 Windows 使用。此后的验证、发布工具和文档以 macOS 开发及宿主、
Linux 中心服务和 CI 为目标，不为重构继续投入 Windows 兼容或实机补验。上表的两类旧入口是评审时的历史事实；
共享计划继续服务原生本地入口与 CI。已有 Windows 迁移材料按历史证据保留，不能因平台退役删除交接校验。

第二批保持外部接口，通过小范围先行迁移验证结构：例如先迁一个泰华写流程，再扩展注册描述；
新旧校验先做差异对比，适配器既有默认值与归一化不能因统一 Schema 而被突然拒绝。

第三批先提取可测试的纯状态决策、结果投影和宿主接口，再逐步迁调用方。Reference Host 继续保持独立实现，
通过共享行为用例证明协议，而不导入中央业务实现。

## 扩容触发条件

当前中央运行时按单活设计。启动恢复清理认领、进程内计划锁以及按进程启动时间判断旧步骤，
不能直接用于多个中央执行实例。增加多进程、滚动部署重叠或独立执行器之前，须先建立实例所有权、
可续租执行租约与拒绝旧持有者写回的版本检查，并验证提交后恢复不重放。

多数据源已经支持 PostgreSQL。只有确需异构数据库时才增加新驱动；SQL 方言的只读策略不能直接复用到其他引擎。
分布式队列、全面前端框架替换和完整 DAG 引擎不属于本次默认工作。性能改进以连接次数、锁等待、
排队时间、峰值内存和撤权发现延迟的实测为依据。
