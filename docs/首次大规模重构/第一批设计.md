# 第一批设计

本批解决两个问题：工作台消息与投递记录分次提交造成受理不完整，以及验证清单与成功回执缺少完整执行证据。
工作范围限于请求受理、验证工具及相关测试；公共 HTTP 和 MCP 接口、下游业务、用户权限、任务执行与发布目标保持原有合同。

## 工作台请求原子受理

### 现有问题

原 `send_chat_stream` 先追加时间线，再创建 `agent_host_dispatches`。后一步因队列配额、幂等冲突或异常失败时，
前一步已经提交。进程在两次提交间退出，也会留下没有投递记录的用户消息。
原[可靠投递设计](../架构设计/工作台请求受理前可靠投递详细设计.md)已经要求时间线与 queued 同事务，本批补齐实现。

### 事务所有权

由 WorkspaceStore 专用受理入口拥有 SQLite 连接和 `BEGIN IMMEDIATE`。账号绑定、请求幂等与配额检查、
附件登记、时间线及其通知 outbox、dispatch 与初始事件必须通过同一连接完成。任一环节失败整体回滚。
事务提交后应用层才启动或唤醒 dispatch worker；事务内不调用宿主、模型或下游业务。

TaskHub 保留原有独立追加消息接口，在内部增加接收现有连接的写入原语。只有原子受理入口使用该原语，
其他调用保持原有自管理事务语义。既有 `create_host_dispatch` 接口继续兼容。

附件大小及类型先按现有规则校验。附件文件与数据库登记须有明确失败清理边界：只清理本次新建且未成功受理的文件，
重复请求重用的文件不得被删除。进程异常退出后遗留的受控缓存由维护路径安全回收，清理不得与正在提交的请求竞争。

### 幂等与失败处理

同一用户、宿主和幂等键对应的有效载荷保持一致时，返回原 dispatch，时间线、附件引用与通知不重复。
同键不同正文或附件必须拒绝，原消息、投递及附件保持不变。幂等检查与写入在同一事务内，不能靠提前查一次代替。

旧数据读取和已有投递状态机保持兼容。本批不自动重发历史无投递消息，不因受理事务变化重新消费授权或执行业务。
队列拒绝仍使用原错误合同；已经受理的请求仍遵守回执核对与受理后不重投规则。

## 共享验证计划和阶段回执

### 计划与入口

新增共享验证计划，统一 Full 阶段和 Workspace Node 测试分类。2026-10-04 用户明确后续不再使用 Windows，
维护目标收敛为 macOS 开发和宿主、Linux 服务及 CI；本地原生入口与 CI 复用同一执行器。
已有 PowerShell 委托入口保留历史兼容，不再追加 Windows 适配或要求 Windows 实机补验。
Workspace 六组 Node 测试包含新增遗漏的查询分组；扫描到未登记的测试文件时拒绝执行。
浏览器专项显式分类，继续按现有开关执行，不把跳过误记为通过。MCP App 专项保留现有触发方式。

### 证据链

一次正式 Full 运行绑定唯一运行标识、固定提交、跟踪文件字节、环境和验证计划摘要。
每阶段由实际执行命令的共同执行器写出状态、命令、退出码、用例集合、输出或报告摘要，以及必要跳过记录。
阶段开始前失效旧证据，失败不得继续写成功回执。证据必须属于同一次运行和相同输入。

安装包构建与安装后资源检查是共享计划的最后一个必需阶段。`finish` 验证所有必需阶段均有匹配成功证据，
核对 Python 与 Node 测试报告及制品后才生成最终成功回执。`verify` 同样验证完整证据和制品绑定。
旧回执缺少新增证据时明确要求重跑 Full，不能补写静态阶段名把旧证据升级为成功。

外层回执继续使用 `agentbridge.validation.v1`，新增 `evidenceVersion=2`、本次计划和阶段证据索引。
继续保留发布消费者依赖的 manifest、wheel 和 SHA256 结果字段。可选 MCP App 检查加入同次计划，完成后才允许 `finish`。
失败阶段的原始输出只保存在仓库外受限临时日志，回执记录诊断位置；成功输出保存摘要而不复制原始内容到 CI 制品。
Targeted 不产生 Full 成功回执，
输入变化、缺阶段、失败阶段、旧运行报告、报告被修改及测试文件未分类均拒绝。

## 测试矩阵

| 范围 | 场景 | 应保持的结果 |
| --- | --- | --- |
| 原子受理 | 正常消息和图片请求 | 消息、附件引用、outbox、dispatch 和初始事件一致提交 |
| 回滚 | 队列满、写消息后异常、创建投递后异常 | 没有本次部分受理记录，宿主未被调用 |
| 幂等 | 同键重试、同键异正文或异附件、并发同键 | 一条有效请求；冲突不改变原记录和文件 |
| 附件 | 普通异常、事务失败、进程中断后的受控缓存 | 新文件可清理，既有有效附件保留 |
| 隔离 | 两用户使用相同幂等键 | 记录及附件不串用 |
| 原有恢复 | 受理前等待、受理回执丢失、终态事件排空 | 复用原请求，受理后不重投 |
| 清单 | 查询分组用例、新增未分类文件 | 前者自动纳入；后者明确失败 |
| 回执 | 成功、缺阶段、非零退出、旧运行报告、报告篡改 | 只有本次全部必要阶段通过才成功 |
| 发布保护 | 未提交工作树、输入变更、Targeted、wheel 哈希变化 | 不能生成或使用正式 Full 成功回执 |

## 开发验证与交付

开发阶段使用临时数据库、合成业务和独立临时会话密钥运行定向测试，随后运行全量离线回归。
正式 Full 要求干净固定提交；验证未提交的开发内容时，可复制本批源文件到独立临时 Git 快照并提交，
从该快照运行新入口和安装包检查。该回执仅属于临时快照，不可用于发布原工作树。

本批预期不改变数据库表结构，因此没有新增业务数据迁移。回退仍须遵守现有发布兼容声明与实际 Schema 检查；
验证回执格式增强要求重新运行验证，不会修改运行中的业务账本。实际结果填写到[实施与测试记录](./第一批实施与测试记录-2026-10-04.md)。
