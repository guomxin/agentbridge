# 首次大规模重构

本目录集中保存 2026-10-04 启动的首次大规模重构的评审、分批设计、实施和测试证据。
目标是在保留现有功能、业务权限和受控写入边界的前提下，降低新增系统、能力、技能和宿主的修改成本。
继续采用模块化单体，按小批次推进，每批独立验证。九月已经完成的职责拆分、发布和恢复治理是本次工作的基础。

2026-10-04 用户确认后续不再使用 Windows。本次及后续重构以 macOS 开发和本机宿主、Linux 中心服务及 CI 为维护目标，
Windows 兼容与实机验收不再作为完成条件。现行验证使用 Python 共享计划；既有 Windows 脚本和迁移证据作为历史兼容材料保留，后续按依赖逐步清理。

本次实施 **2B：照明告警备注修改类型声明与兼容回归**，范围为
`smartlight.alarm.remark.update.prepare` 和 `smartlight.alarm.remark.update` 两项能力。
该流程与现有声明结构相容，同时覆盖泰华试点没有的 `context_fields=(alarm_id,)` 和 `reversible_write`，
可检验类型声明在另一系统、固定目标和可回滚修改中的适用性。继续保留参数、字段卡、scope、权限和动态函数解析合同。

本批交付要求：

1. 固定迁移前的完整能力、字段卡及目录合同，并为照明声明生成原形状投影。
2. 检查泰华与照明的能力、写目录、scope、用户权限及规划描述之间的一致性；外围映射仍按实际来源维护。
3. 验证目标告警不能被字段提交替换，备注留空仍表示清除，并发修改会阻止提交，权威回读、回滚信息、
   单次授权及提交后未知结果不重放保持原行为；取消/撤权测试继续覆盖共享执行器。
4. 完成固定提交 macOS Full、Ubuntu Full、原生发布验收并记录实际证据；无需为静态重构提交真实业务修改。

2B 阶段，其他照明动作的旧目录为 `field_schema=None` 且没有 `field_message`，当时类型声明要求非空字段提示，
因此另批设计 2C 可选字段卡合同后迁移。OA 还包含预检、动态字段与批量反向映射等变体，按形状分别迁移。
之后先对普通调用与计划调用做参数校验差异清单和兼容样本，再统一可共享部分；
随后推进中央服务显式依赖、存储初始化与维护分离、技能动作请求合同。各工作包分别验证，
保留授权消费、计划取消和技能撤销的共享事务及复核时点。

## 第二批后续：照明无字段卡流程

2026-10-04 在 2B 完成后，以 `943a1e5` 复核代码形成 **2C** 建议。用户已确认开始，开发基线为 `dcf68ff`。
已发布 `dd986b88a0ca`，七文件定向回归 276 项、34 个子场景通过；macOS 与 Ubuntu Full 均为 Python 1338 项通过、31 项跳过，
Workspace 38 项、OpenClaw 215 项通过，基础发布验收成功。完整证据见[2C 实施记录](./第二批照明无字段卡流程实施与测试记录-2026-10-04.md)。
一次覆盖照明剩余三个同形流程，共六项准备/提交能力：

| 现有流程 | 必须保持的行为 |
| --- | --- |
| 告警提交工区 | 核对告警、等级和所属工区；提交后回读；撤回仍须另行授权 |
| 撤回工区提交 | 核对已提交状态；已提交告警缺少工区名称时仍允许撤回；重新提交仍须另行授权和复检 |
| 处置告警 | 保留不可撤销提示、独立授权、状态 3 的权威回读和无回滚结果 |

这三个流程均绑定 `alarm_id`，无需填写字段卡即可生成授权卡；迁移前旧目录含 `field_schema=None`，
但完全没有 `field_message` 键。2C 对类型声明的最小扩展是允许显式 `field_message=None` 表示无字段提示，
兼容投影在此情形省略该键，保留 `field_schema=None`；不把缺键改成空串或值为 None 的键。
有字段卡的泰华、照明备注继续要求非空字段提示，所有流程继续要求非空授权提示；保持现有构造参数顺序。

实施前已固定六项能力、三个目录和 scope/权限/规划合同，再迁移声明。已完成测试覆盖：

- 三个流程都直接进入授权，目标冻结正确，授权前不写入；保留原工具可见性和动态函数解析。
- 目标 RTU、工区或状态变化的拒绝规则，以及“目标已达到预期状态时不重复写入”的既有分支。
- 授权仅消费一次，提交/回读异常归类为未知，同键和换键重试都不能再次写入。
- 可撤回流程的恢复入口与不可撤销处置的提示/结果分开核对；2A、2B 的字段卡路径继续回归。

原适配器用例覆盖提交/撤回、资格拒绝、并发状态与 RTU 变更、不可逆处置和部分未知结果；
2C 已补齐中央服务三个无字段卡入口的授权、已完成及未知不重放链路，以及逐入口变化拒绝断言。
交付继续采用固定提交 macOS/Ubuntu Full 和原生发布验收。照明真实业务、图片实机验收仍按用户安排延期。

2C 完成后，照明现有四个写流程的静态声明已全部统一；下一步评估 OA 动态字段/预检/批量变体，
再推进兼容参数校验与中央服务依赖拆分，避免在同一批同时改变声明和执行事务。
