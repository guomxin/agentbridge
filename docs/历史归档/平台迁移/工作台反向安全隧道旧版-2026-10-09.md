# Agent Workspace 反向 SSH 隧道

> 历史快照：保存平台收敛前的流程，不作为当前操作入口。现行流程见[原生维护](../../部署运维/苹果系统原生维护.md)。

本文记录 AgentBridge Linux 中心端与 Windows OpenClaw 工作站之间的当前连接方案，
用于解释运行原理、进程边界、切网恢复、安全限制和日常排障。本文描述的是当前
内网 PoC 基线，不把该隧道扩展为 VPN、远程桌面或通用端口代理。

## 1. 目标与边界

Agent Workspace 部署在 `10.10.50.213`，OpenClaw Gateway 运行在 Windows 工作站的
`127.0.0.1:18789`。工作站可能在有线、无线、家庭或度假网络之间切换，局域网 IP
不能作为 AgentBridge 的稳定配置。

当前方案由 Windows 主动连接固定的 213 服务器，并通过 SSH 反向端口转发，在服务器
回环地址建立 `127.0.0.1:18789`。AgentBridge 始终连接该回环地址，不再感知工作站
当前 IP。

该隧道只承载 AgentBridge 到 OpenClaw Gateway 的 WebSocket 流量：

- 浏览器仍直接访问 213 上的 Agent Workspace，不经过 SSH 隧道；
- 可信卡片、MCP、管理端和目标系统会话仍由 AgentBridge 中心端负责；
- Telegram 和微信由本机 OpenClaw 通道独立接收消息，不依赖 Workspace 浏览器；
- 隧道中断时，已经落库的任务、时间线和文件记录仍保留，但 Workspace 暂时不能
  发起新的 OpenClaw 运行。

## 2. 数据流

```mermaid
flowchart LR
    B["用户浏览器"] -->|"HTTPS :8783"| A["213 AgentBridge Python"]
    A -->|"ws://127.0.0.1:18789"| R["213 sshd 反向监听"]
    R ==>|"SSH 加密连接 :22"| S["Windows ssh.exe"]
    S -->|"TCP 127.0.0.1:18789"| O["Windows OpenClaw Gateway"]
    O --> S --> R --> A --> B
```

工作站执行的核心参数是：

```text
-R 127.0.0.1:18789:127.0.0.1:18789
```

三个地址从左到右分别表示：

1. 在 213 服务器上只监听 `127.0.0.1:18789`；
2. 收到连接后，通过现有 SSH 会话把字节送到 Windows；
3. Windows `ssh.exe` 再连接本机 `127.0.0.1:18789` 的 OpenClaw Gateway。

AgentBridge 的对应参数是：

```text
--workspace-gateway-url ws://127.0.0.1:18789
```

AgentBridge 和 OpenClaw 之间仍执行 Gateway Token 校验及已配对设备校验。SSH 隧道只
提供网络可达性，不替代应用身份认证。

## 3. 两端进程

### 3.1 Windows 工作站

任务计划程序在当前用户登录时启动：

```text
Windows Task Scheduler
└─ powershell.exe
   └─ ssh.exe
```

各进程职责如下：

| 进程 | 来源 | 职责 |
| --- | --- | --- |
| `powershell.exe` | `Start-AgentBridgeWorkspaceTunnel.ps1` | 单实例运行；接管已存在的同目标 SSH，SSH 退出后等待 5 秒并重新启动 |
| `ssh.exe` | Windows OpenSSH | 维持到 `10.10.50.213:22` 的连接并提供反向端口转发 |
| `node.exe` | OpenClaw Gateway | 独立监听本机 `18789`，不属于隧道子进程 |
| `OpenConsole.exe` / `conhost.exe` | Windows 控制台宿主 | 承载 PowerShell 或 OpenClaw 控制台；不参与业务协议 |

进程 PID 会随重启变化，不应写入配置或监控规则。当前任务使用
`-WindowStyle Hidden`，但 Windows Terminal 被配置为默认控制台宿主时仍可能创建一个
可见 PowerShell 窗口。关闭该窗口会终止当前隧道，不应把它当成重复 OpenClaw 关闭。

### 3.2 Linux 中心端

```text
systemd
└─ AgentBridge Python

sshd 主进程
└─ sshd: root
   └─ 监听 127.0.0.1:18789
```

AgentBridge Python 继续监听 `8780`、`8782`、`8783` 和 `8790`。每条工作站 SSH 会话
由一个 `sshd` 子进程维护；反向端口属于该子进程。实际 Workspace 请求到达时，sshd
在同一 SSH 连接中建立转发通道，不会在 213 上启动 OpenClaw、Node.js 或第二个
AgentBridge。

## 4. 启动与恢复机制

安装入口：

```powershell
.\scripts\Install-AgentBridgeWorkspaceTunnelServer.ps1
.\scripts\Install-AgentBridgeWorkspaceTunnel.ps1
```

第一条命令在 213 上安装
`/etc/ssh/sshd_config.d/90-agentbridge-workspace-tunnel.conf`，先执行 `sshd -t`
验证，再热加载 `ssh.service`/`sshd.service`。当前隧道使用 `root` 专用密钥，因此配置只在
`Match User root` 下启用 `ClientAliveInterval 5` 和 `ClientAliveCountMax 2`，文件末尾用
`Match all` 结束作用域。以后迁移到受限隧道账号时，应同步修改该 `Match` 主体。

安装脚本创建当前用户级任务 `AgentBridge Workspace Tunnel`，配置为：

- 当前 Windows 用户登录时启动；
- 同一时刻只保留一个实例；
- 使用专用 AgentBridge SSH 私钥和仓库内固定 Host Key；
- 不交互读取密码；
- 守护器每 2 秒比较一次活动网卡、IPv4 地址和网关指纹，检测到切网后立即终止旧 SSH 并重连；
- 守护器发现两次轮询间隔超过 60 秒时，把它识别为盒盖待机或系统长暂停；即使网卡名称和 IP
  没变，也主动废弃睡眠前 SSH，避免继续使用半死 TCP 会话；
- SSH 每 10 秒发送一次保活，连续 2 次无响应后退出，覆盖网卡指纹未变化的静默断线；
- 213 的 SSH 服务每 5 秒探测一次客户端，连续 2 次无响应即回收旧 `sshd` 子进程和它占用的
  `127.0.0.1:18789`；这覆盖笔记本合盖后没有机会发送 FIN/RST 的场景；
- SSH 退出后 PowerShell 等待 5 秒重新连接；
- 任务异常退出时，任务计划程序还会按 1 分钟间隔重启。
- 启动器使用按用户、主机和端口命名的互斥锁，避免两个包装器同时重连；
- 若更新任务时遗留的同目标 `ssh.exe` 仍然健康，新包装器等待该进程退出，不再重复绑定远端端口；
- 安装器重启任务时只清理参数完全匹配的 AgentBridge 隧道 SSH，不影响 Codex 或其他 SSH 会话；
- 安装器先停止并精确清理旧包装器，再覆盖任务定义，避免旧 PowerShell 因任务重登记而脱离管理；
- SSH 标准错误按尝试追加到 `%LOCALAPPDATA%\AgentBridge\logs\workspace-tunnel-ssh.log`，保留
  `remote_forward_conflict`、`authentication_failed`、`network_unreachable` 等退出分类，不弹出重试窗口；
- 当前状态写入 `%LOCALAPPDATA%\AgentBridge\workspace-tunnel-status.json`，连接期间每 15 秒更新
  心跳，并记录包装器 PID、SSH PID、连续失败数和最近连接时间；
- OpenClaw Guard 同时检查任务状态、包装器进程和隧道心跳。心跳超过 60 秒或包装器消失时，
  只精确重启隧道任务，不重启正常的 OpenClaw Gateway。

换网时的恢复顺序是：

1. 活动网卡、IPv4 地址或网关发生变化；
2. 守护器在下一次 2 秒轮询中写入 `network_change_detected` 并终止旧 `ssh.exe`；
3. PowerShell 最多等待 2 秒后从新网络主动连接 `10.10.50.213:22`；
4. 若旧服务器会话尚未释放监听，新会话以 `Address already in use` 快速失败并继续退避；
5. 新 `sshd` 子进程成功绑定服务器 `127.0.0.1:18789`；
6. AgentBridge 的宿主握手通过后，后续 Gateway 请求使用新隧道。

盒盖待机后恢复的顺序是：

1. Windows 恢复调度，PowerShell 发现轮询时间跳变超过 60 秒；
2. 状态写入 `resume_detected/system_resume_or_long_pause`，本机旧 SSH 被精确结束；
3. 若睡眠前连接没有正常关闭，213 的服务端保活在约 10 至 15 秒内回收旧 `sshd` 和反向监听；
4. 包装器按最多 2 秒的快速退避重新连接；网络尚未就绪时继续按 5 秒退避，不修改 IP、VPN或代理；
5. 新连接成功后恢复 15 秒状态心跳，Workspace 顶部离线轮询自动切回“OpenClaw 已连接”。

若无线漫游、VPN 内部重连等情况没有改变网卡指纹，客户端和服务端 OpenSSH 保活共同兜底。
服务器旧 `sshd` 尚未释放 `18789` 时，新连接虽然可以完成 SSH 认证，但会因
`Address already in use` 快速失败；错误会保留在日志中，包装器继续退避。服务端保活会主动缩短
旧监听占用时间，不再依赖 Linux 默认的长 TCP 超时。此时服务器即使显示 `18789` 正在监听，也仍需
用 `readyz` 判断旧监听背后的数据通道是否可用。

## 5. 安全边界

- 服务器反向端口固定绑定 `127.0.0.1`，不允许内网或公网直接访问 `18789`；
- 传输经过 SSH 加密，不发送 SSH 密码，私钥保留在 Windows 用户目录；
- `IdentitiesOnly=yes` 固定使用专用密钥，`UserKnownHostsFile` 固定校验 213 Host Key；
- `ExitOnForwardFailure=yes` 保证新会话的端口未成功建立时 SSH 立即失败，不把该新会话报告为
  健康；它不能替代服务器对旧残留监听的数据通道检查；
- `-N -T` 表示本隧道不执行远端命令、不分配交互终端；
- Gateway Token 和 OpenClaw 设备配对仍是第二层应用认证；
- 当前 PoC 使用现有 `root` 专用 SSH 密钥。生产化时应改为只允许该反向转发的受限
  服务账号和受限公钥，避免让隧道密钥具备通用远程管理能力。

## 6. 日常检查

### 6.1 Windows

```powershell
Get-ScheduledTask -TaskName "AgentBridge Workspace Tunnel"
Get-ScheduledTaskInfo -TaskName "AgentBridge Workspace Tunnel"

Get-CimInstance Win32_Process |
  Where-Object {
    $_.CommandLine -like "*Start-AgentBridgeWorkspaceTunnel.ps1*" -or
    $_.CommandLine -like "*127.0.0.1:18789:127.0.0.1:18789*"
  } |
  Select-Object ProcessId, ParentProcessId, Name, CommandLine
```

任务运行时 `LastTaskResult=267009`（十六进制 `0x41301`）表示“任务仍在运行”，不是
失败代码。

需要重新建立隧道时：

```powershell
Stop-ScheduledTask -TaskName "AgentBridge Workspace Tunnel"
Start-ScheduledTask -TaskName "AgentBridge Workspace Tunnel"
```

### 6.2 Linux

```bash
systemctl is-active agentbridge
ss -ltnp '( sport = :18789 )'
curl -sS --max-time 8 http://127.0.0.1:18789/ -o /dev/null -D -
```

正常状态应满足：

- AgentBridge 为 `active`；
- `127.0.0.1:18789` 由 `sshd` 监听；
- 服务器访问该地址可获得 OpenClaw HTTP 响应；
- `https://10.10.50.213:8783/healthz` 返回 Workspace `ok`。

`ss` 只证明某个 `sshd` 进程持有监听，不能单独证明请求能够穿过 SSH 会话到达 Windows。必须把
监听归属和有界 HTTP/宿主协议响应一起判断；监听存在但 `curl` 超时、复位或无响应时，仍按隧道
路径不可用处理。

## 7. 故障定位

| 现象 | 优先检查 | 说明 |
| --- | --- | --- |
| Workspace 页面完全打不开 | `8783/healthz`、AgentBridge systemd | 这是 Workspace HTTPS 或中心服务问题，不一定与隧道有关 |
| 页面可打开，但发送任务失败 | 213 的 `127.0.0.1:18789`、Windows 计划任务、OpenClaw Gateway | 常见于隧道或 Gateway 不可用 |
| TG/微信可用，Workspace 发送失败 | 反向监听和 Workspace Gateway | 消息通道独立可用，进一步指向隧道链路 |
| Windows 切网后短时不可用 | 状态中的 `network_change_detected`、SSH 进程和计划任务 | 网卡变化通常数秒内重连；静默断线由 20 秒保活兜底，不修改服务器 IP |
| 盒盖后回家或回公司，页面显示智能体不可用 | 状态中的 `resume_detected`、`observedAt`、服务端 `ClientAlive` 配置 | 唤醒后主动换掉睡眠前 SSH；服务端回收未正常关闭的旧监听，Gateway 不重启 |
| 213 没有 `18789` 监听 | Windows `ssh.exe`、22 端口可达、密钥和 Host Key | 隧道未成功建立 |
| 213 有监听但不能访问 OpenClaw | Linux `sshd` 会话、本机 OpenClaw `18789`、Gateway 进程 | 可能是旧监听背后的 SSH 路径失效，也可能是 Windows 目标服务未监听，不能直接判定“SSH 正常” |
| `remote port forwarding failed for listen port 18789` 或服务端 `Address already in use` | 查找遗留的同目标 `ssh.exe`，并核对 Linux `ssh.service` 日志 | 旧会话仍占远端端口，新会话已认证但无法接管；等待旧监听释放后重连 |
| PowerShell 窗口关闭后网页任务失败 | 重新启动计划任务 | 当前窗口承载隧道守护脚本 |

不要通过修改代理、防火墙、OpenClaw 对外监听地址或把 `18789` 暴露到内网来绕过故障。
先按“Workspace HTTPS、服务器反向监听、SSH 数据通道、本机 Gateway”四段逐一定位。调查端口交接
冲突时可只读查看：

```bash
journalctl -u ssh --since "10 minutes ago" --no-pager \
  --grep='18789|Address already in use|cannot listen'
```

Workspace 在 OpenClaw 尚未受理任务、且连接阶段返回 `GATEWAY_CONNECTION_FAILED` 等可恢复错误时，
会按 `2、5、10` 秒做三次有界等待。该机制用于覆盖工作站刚开机、刚切网或反向隧道刚重连的
短时端口交接中断；一旦任务已被 OpenClaw 接受、已经发送工具调用或出现真实进展，就不做自动重放，
避免同一业务动作被执行两次。刷新 Workspace 不是恢复手段，它至多只是碰巧给隧道留下了恢复时间。

Workspace 页面会独立刷新 Gateway 状态：在线时每 30 秒检查一次，离线时每 5 秒检查一次；页面
重新获得焦点或用户刷新对话时也会立即检查。这样隧道恢复后，页面顶部会自动从“不可用”恢复为
在线，不需要刷新整个网页。该状态检查只调用 OpenClaw 的 `system.info`，不读取或写入任何业务系统。

## 8. 当前验证基线

2026-08-18 至 2026-08-19 已完成：

- Windows 计划任务和 SSH 子进程持续运行；
- 213 上 `127.0.0.1:18789` 由对应 `sshd` 子进程监听；
- 213 通过隧道访问本机 OpenClaw 返回 HTTP 200；
- 工作站 IP 变化后不再修改 AgentBridge systemd 参数；
- 同时建立 12 条不完成 TLS 的客户端连接时，Workspace `healthz` 仍返回 200；
- 释放故障连接后 `8783` 监听队列恢复为 0，AgentBridge 无 error 和异常重启。
- 隧道刚进入 `connection_started` 时提交任务，应用层连接失败会按有界退避等待，隧道恢复后沿用
  原幂等键受理同一任务。
- 2026-08-25 从公司有线网切换到无线网后，守护脚本识别网卡指纹变化并重建 SSH 子进程；受控终止
  当前 SSH 子进程后，新隧道自动恢复，`businessCalls=0`、`businessListReads=0`、
  `businessWrites=0`。页面端同时增加离线快轮询和在线低频确认，避免链路已恢复但顶部状态仍停留在
  `GATEWAY_TIMEOUT`。
- 2026-09-01 针对笔记本频繁盒盖、跨地点换网补充恢复收口：本机增加 60 秒唤醒时间跳变检测和
  15 秒状态心跳；213 对隧道账户启用 `ClientAliveInterval 5/ClientAliveCountMax 2`；Guard 能识别
  “任务仍是 Running、但隧道心跳失效”；安装器修正为先停止旧任务再覆盖定义。现场精确终止隧道
  SSH 后，包装器换用新 PID 自动恢复，213 的 `readyz` 返回 `ready=true`，OpenClaw Gateway PID
  始终保持不变，全程业务调用和写入均为 0。

最后一项同时依赖中心 HTTPS 服务的“TLS 握手在线程内限时执行”修复。它解决的是
客户端换网后半开连接堵塞 Workspace 接收线程的问题，与 SSH 隧道断线重连属于两个
不同层面的可靠性机制。

## 9. 受理前可靠投递

为避免较长的切网、VPN 重连或旧远端监听释放过程直接导致用户请求失败，中心端已按
[工作台请求受理前可靠投递详细设计](../../架构设计/工作台请求受理前可靠投递详细设计.md)
实现持久化宿主受理等待区、语义就绪门控、单次受理和回执丢失核对。当前默认等待上限为 60 秒，
连接前失败按 `1、2、3、5、8、10...` 秒退避；浏览器刷新、SSE 断开和 AgentBridge 重启不会删除
等待请求。收到 `accepted(runId)` 后永久关闭再投递资格，只观察和核对同一运行。

2026-08-30 已在 Release `08d7ac09341a` 上受控停止本机守护器与反向隧道，确认服务器
`127.0.0.1:18789` 无监听后从 Workspace 提交无业务工具请求。页面显示“请求已保存”和
“恢复后会自动继续”，隧道恢复后原请求自动完成；后台 `retry_count=6`、`attempt_count=1`、
`host_accepted=1`、`host_dispatch_completed=1`，没有产生第二个宿主运行。详细证据见
[工作台受理前可靠投递验收](../../验收记录/工作台受理前可靠投递验收-2026-08-30.md)。
