# AgentBridge 固定发布入口

> 历史快照：保存平台收敛前的流程，不作为当前操作入口。现行流程见[原生维护](../../部署运维/苹果系统原生维护.md)。

M5 起，发布前须显式选择仓库外的真实环境配置（下列赋值仅对当前 PowerShell 会话生效）：

```powershell
$env:AGENTBRIDGE_ENVIRONMENT_PROFILE = Read-Host "请输入已复核的 environment.json 绝对路径"
```

也可逐次传入 `-EnvironmentProfile <绝对路径>`。配置绑定目标及三个 systemd 单元的 SHA256；仓库中的单元已是默认 TLS 的通用示例，不能直接用作现网配置。完整说明见[维护治理与扩容边界](../../部署运维/维护治理与扩容边界.md)。

运行发布只使用本机固定提交的完整验证收据，不再创建候选分支或等待远端 CI。线上验收后推送 main；main/PR 的 GitHub Actions 仅作异步回归记录，不是部署门禁。`-ResumeAcceptance` 自动复用并核验原完整收据，不重新部署，也不会启动新的全量验证。纯文档修改仍不部署。

## 结论

开发机发布只使用一个入口：

```powershell
.\scripts\Publish-AgentBridge.ps1
```

它固定执行以下顺序：

1. 校验当前仓库必须是 `.gitrepo` 主工作区或 `.git` 隔离工作树、`main` 分支和 `git@github.com:guomxin/cli-helper.git`；隔离工作树可保持 detached HEAD，但必须精确指向本地 `main` 当前提交；
2. 拒绝发布尚未提交的跟踪文件；
3. 在耗时验证开始前检查两把 SSH 私钥是否能被子进程读取；
4. 以 4 个 pytest worker 执行一次全量验证，再运行治理故障注入、wheel 部署和远端 MCP 冒烟；
5. 执行管理端/Workspace 就绪、systemd、每日备份、近期错误和 OpenClaw 的治理与发布验收；
6. 仅在部署及治理验收成功后推送同一个提交到 `origin/main`；
7. 从 GitHub 回读远端提交，确认与本地提交完全一致。

只预览，不访问服务器或 GitHub：

```powershell
.\scripts\Publish-AgentBridge.ps1 -PlanOnly
```

本轮已经跑过同一提交候选的全量验证时：

```powershell
.\scripts\Publish-AgentBridge.ps1 -SkipValidation
```

`-SkipValidation` 现在必须复核 `output/release-validation/full.json`：同一提交、跟踪文件内容、
Python 包版本、Node/npm 版本与已安装 Node 锁清单均需匹配，且检查完整、无跳过项。
清单或 wheel 哈希不符时在上传前拒绝。治理故障注入仍执行。该清单是本机可信执行流程的
复用证据，不是签名证明；仓库侧异步检查也不能替代本地制品门禁。清单不防御恶意改写或手工篡改依赖包文件。

GitHub 不再运行发布前候选分支，也不向发布脚本提供放行结论。main/PR 上的
`repository-validation` 在推送后异步运行，可发现干净托管环境中的回归，但失败不会让发布脚本
回滚已经通过本地制品、运行治理和在线验收的版本。

全量验证从固定提交导出源码构建 wheel，并在新虚拟环境中、源码目录外加载两个 OA 页面脚本。
部署复用该 wheel，不再次从工作区构建。远端安装前核验 SHA-256，保存制品与验证清单，
安装后再次加载脚本。本项仅检查资源入口，不执行 OA 写入，也不代表完整业务验收。
纯文档改动只执行文档检查、提交和推送，不调用部署入口。

中央程序采用[独立版本发布与回退](../../部署运维/独立版本发布与回退.md)：新环境先安装检查，切换前创建恢复点，再通过 `current` 启用版本。每次发布需审查 `deploy/release-policy.json` 中的前一版本和无迁移契约；失败不会自动覆盖业务数据库。不要继续向根目录旧 `venv` 安装新版本。

发布默认比较当前 Gateway 的已验证输入指纹。中央 Python、Workspace 页面、文档和
插件测试改动不重启 OpenClaw，也不重复执行重启后的两轮模型预热；插件 `index.js`、
`lib/`（含工具目录）、插件清单、依赖锁文件、宿主配置、环境文件或启动器变化才重启。
保留 `/readyz`、当前进程插件注册及完整发布验收，不把“省略重启”当作省略健康检查。

输入指纹按逻辑文件名和内容计算，绝对路径仅用于诊断，因此干净发布目录与主工作区
不会因为目录不同而触发重启。已知 UTF-8 插件源码、清单和锁文件统一 CRLF/LF 后比较；
宿主配置、环境变量、启动器及未知/二进制文件仍按原始字节比较。
旧基线兼容转换必须先核验原始哈希：当前文件原始字节相同，或旧路径文件仍与已保存
哈希相符，才允许转换。无法核验时仍要求重启，不会用当前修改后的文件重新证明旧进程。

旧命令仍兼容，但现在也按指纹决定是否需要重启：

```powershell
.\scripts\Publish-AgentBridge.ps1 -RestartOpenClaw
```

需要修复宿主状态、升级 OpenClaw/Node 或手工改变已安装依赖时，可明确强制重启：

```powershell
.\scripts\Publish-AgentBridge.ps1 -ForceRestartOpenClaw
```

`-PlanOnly` 输出 `restartOpenClaw`、`openClawRestartReason` 和 `openClawChangedInputs`，
只读检查本地 Gateway，不访问远端服务器或 GitHub。相同输入重复发布时原因是
`inputs_unchanged`；`-ResumeAcceptance` 自动复用完整验证收据，并补齐已确认版本的发布后步骤，不能强制重启。

指纹保存在 `%LOCALAPPDATA%\AgentBridge\openclaw-runtime-inputs.json`，绑定 Gateway PID
和启动时间。首次使用没有可信基线时需要一次受控启动；不根据版本相同或文件时间戳推断
内存代码已经更新。生命周期入口在启动前后核对内容并通过插件运行验证后才记录基线；
启动期间文件变化会拒绝记录。重启判断在生命周期锁内再次复核，另一个发布已启动相同
输入时复用该进程，不重复重启或预热。文件新增、删除、同版本源码变化都参与判断。

发布引起的预热在重启前记录待验收标记，成功后才清除；预热失败或发布中断后，
`-ResumeAcceptance` 会先核验原完整收据和线上精确版本，再续接发布后备份、宿主输入检查与待完成预热。
中央 `deployment.json` 的 `completion` 保存备份计时器与发布后备份的运行、失败、成功状态；成功阶段不重复执行。
宿主是否需要重载由保存的输入指纹、进程身份决定：先前已正确加载则复用，若中断在加载前则补做。
不会重新上传、安装、切换中央版本或重放业务操作。切换尚未确认的中断仍需按事务恢复流程检查，不能使用此入口越过。
也可单独执行 `scripts/Test-AgentBridgePendingOpenClawWarmup.ps1` 补跑预热。

备份先在短暂的无提交区间固定各数据库读取快照，再从固定快照复制；复制期间允许正常数据库提交。
固定快照时的提交冲突、数据库替换和配置文件变化仍拒绝该轮快照，并在统一时间预算内退避重试。
备份清单记录快照方法与重试冲突，错误指明变化的资源而不输出配置或凭据内容。

当前范围是本项目固定的 `index.js`、`lib/` 和运行清单，不自动跟踪 OpenClaw 安装目录、
手工修改的 `node_modules`、宿主配置引用的外部包含文件或额外插件目录；这类宿主维护
继续使用强制重启。保存的环境和配置证据只有文件路径与 SHA-256，不保存秘密值。

需要把双用户、四端点隔离也纳入本次发布门禁时：

```powershell
.\scripts\Publish-AgentBridge.ps1 -IdentityLabel "辛国茂","李世玉"
```

OpenClaw CLI 启动时可能受 Telegram、微信等外部通道网络探测影响。发布验收为每条
OpenClaw 只读命令保留 90 秒，并使用一次性插件装载检查；不使用会启动后台轮询的
`plugins inspect --runtime`。Gateway 深度 RPC、CLI/Gateway 版本一致性和插件版本漂移
仍由独立检查覆盖，因此这项调整只消除诊断进程无法按时退出造成的误报，不降低发布门禁。

## Codex 执行约束

### 本机较慢时的预热门槛

2026年9月8日用户明确要求放宽预热时间。`Test-OpenClawGatewayWarmup.ps1` 的热请求总耗时默认上限由60秒调整为180秒，可通过 `HotPathMaximumSeconds` 设置。计时范围是整条CLI命令，包含本机模块加载、连接、Gateway执行及结果返回，不是单纯模型生成时间。输出中的 `durationBasis=cli_end_to_end` 和 `hotPathMaximumSeconds` 明确记录口径与本次门槛。

仍要求命令正常退出、返回 `ok/completed` 且答复严格为 `READY`，超时和失败不会记为通过。模型单次热请求的90秒超时保持不变。此次实际失败样本总耗时112.575秒，而会话记录中用户消息至回复约5秒，支持按慢速开发机放宽端到端门槛；不据此声称所有耗时都已定位或解决。

已运行的Gateway可以直接复测预热，不必为了重跑检查再次重启。

两把私钥只允许真实 Windows 用户读取，Codex 文件沙箱中的 `ssh`、`scp` 和 `git push` 子进程必然失败。因此，Codex 必须从第一次尝试起就在获准的非沙箱执行通道运行上述入口，不再先普通执行，也不再临时改 SSH 参数反复试探。

私钥继续保存在用户目录，不进入仓库。仓库只保存已核验的非秘密主机公钥：

- `deploy/ssh/agentbridge_known_hosts`
- `deploy/ssh/github_known_hosts`

除诊断这个固定入口自身之外，不再手工拼接 `scp`、`ssh` 或 `git push` 命令。

发布后的 Trace、事件、恢复动作和备份处置见[运行治理操作手册](../../部署运维/运行治理操作手册.md)。

## 已有授权与执行平台拒绝

同范围日常发布的长期授权已经记录在[开发验证与发布流程](../../部署运维/开发验证与发布流程.md#日常发布授权)。
目标、分支和操作范围没有变化时，不再由开发助手重复要求用户确认提交、推送、部署或必要重启。
这条协作约定不等于修改或覆盖执行平台的权限。

2026-09-07 的发布在进程启动前被 Codex 独立审核器拒绝，不是 GitHub、SSH 或发布脚本运行失败。
同日核验：本机配置文件有 `approval_policy = "never"`，但当前任务明确启用了托管的
`auto_review`；不能仅凭配置文件推断当前任务的实际权限，更不能修改保护设置来放行。

遇到此类拒绝时：

1. 保存精确命令、固定目标、候选提交和审核原文；明确代码、部署、推送分别完成到哪里。
2. 只读 `-PlanOnly` 可以核实目标，但不能证明实际发布获准。
3. 已有授权未被审核认可时，报告“执行平台拒绝”，不要描述为“用户尚未授权”。
4. 不反复执行同一被拒命令，不拆成 SSH、部署、Git 推送来达到相同结果。
5. 继续不受影响的本地验证和浏览器修复。没有正式放行结果前，保持“未部署、未推送”。

官方说明：独立审核器看到的是精简记录；其拒绝不是普通沙箱错误。
参见 [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)。
本地项目文档不能修复审核器的上下文选择或授权判断，本项目也不添加自动改写审核策略的脚本。
