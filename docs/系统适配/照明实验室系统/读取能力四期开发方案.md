# 照明实验室测试系统读取能力四期开发方案

## 一、文档状态

本文最初定义照明系统读取四期的开发范围、业务语义、工具契约、实施顺序和完成标准。
2026 年 8 月 21 日已按真实页面证据完成实现，当前已发布能力仍以
[照明实验室测试系统适配说明](照明实验室系统适配说明.md)为准。

实现阶段对原十项计划作了证据驱动的范围调整：正式落地八项工具。`RTU替换`、`PLC单灯替换`
和`集中器替换`页面实际包含“开始执行”等设备写动作，不作为设备履历读取；检修详情请求只传
设备类型和设备 ID，没有稳定检修记录 ID，因此暂不注册统一记录详情。巡检日志页面实际返回
巡检组统计，工具和文档均按该口径命名，不冒充逐条巡检事件。

本方案基于以下现状形成：

- 一期至三期已经覆盖静态概览、资产、运行状态、RTU 告警、单灯告警、RTU 巡测和巡检任务；
- 目标系统页面已经确认存在用电量、单灯巡测、真实支路漏电、设备替换、设备日志、巡检日志和
  检修记录等入口；
- 上述入口的业务名称已经核实，但正式开发前仍需逐页固定接口、参数、分页、排序和字段口径；
- 本期只建设读取能力，不执行设备控制、主动抄表、告警处置、巡检确认或其他业务写入。

## 二、建设目标

四期的主题是“运行追溯与能耗运维闭环”。前三期主要回答：

- 系统里有什么设备；
- 设备现在是否在线；
- 最近发生过什么告警；
- 某台 RTU 的基础遥测怎样。

四期要继续回答更接近运维工作的五类问题：

1. 一段时间用了多少电，哪些 RTU 用电较高；
2. 单灯在某个时间段上报过哪些运行数据；
3. 真正的 RTU 支路漏电发生在哪里，变化趋势怎样；
4. 一台设备是否被替换过、发生过哪些设备事件；
5. 巡检人员检查过什么，后续做过哪些检修。

完成后，智能体应能把“当前状态、历史遥测、告警、巡检统计和检修”串在同一设备上下文
中，而不是只返回互不相关的页面列表。

## 三、范围与优先级

### 3.1 本期正式能力

本期原计划新增十项正式 MCP 工具，最终按证据上线八项，全部复用 `smartlight:read` 权限。

| 波次 | MCP 工具 | AgentBridge capability | 页面依据 | 业务用途 |
| --- | --- | --- | --- | --- |
| 甲 | `smartlight_energy_record_list` | `smartlight.energy_record.list` | `智能监控管理` → `查询统计` → `用电量记录` | 查询有界时间段内的 RTU 用电记录 |
| 甲 | `smartlight_energy_analysis` | `smartlight.energy.analysis` | 同上 | 汇总用电趋势和设备排行 |
| 甲 | `smartlight_lamp_survey_records` | `smartlight.lamp.survey.records` | `单灯节能管理` → `查询统计` → `单灯巡测记录` | 查询单灯历史遥测 |
| 甲 | `smartlight_rtu_leakage_alarm_list` | `smartlight.rtu.leakage_alarm.list` | `漏电管理` → `RTU漏电查询` → `RTU支路漏电报警记录` | 查询真正的 RTU 支路漏电报警 |
| 甲 | `smartlight_rtu_leakage_analysis` | `smartlight.rtu.leakage_alarm.analysis` | `支路漏电统计`、`漏电电流曲线`和报警记录 | 分析漏电趋势、集中设备和支路 |
| 甲 | `smartlight_off_hours_current_list` | `smartlight.rtu.off_hours_current.list` | `漏电管理` → `RTU漏电查询` → `关灯时间段电流` | 查询关灯时间段仍存在的电流记录 |
| 乙 | `smartlight_inspection_log_list` | `smartlight.inspection_log.list` | `巡检管理` → `数据统计` → `巡检日志` | 查询巡检组维度统计 |
| 乙 | `smartlight_maintenance_record_list` | `smartlight.maintenance_record.list` | `巡检管理` → `数据统计` → `检修记录` | 查询检修结果和处理记录 |

未注册的原计划项：

| 工具 | 证据结论 |
| --- | --- |
| `smartlight_equipment_history_list` | 所谓替换入口是设备执行流程，没有找到独立历史列表接口 |
| `smartlight_operation_record_detail` | 检修详情没有传稳定记录 ID，不能保证“第 1 条详情”对应所选记录 |

甲波次补齐能耗、历史遥测和真实漏电。乙波次按证据补齐巡检统计与检修列表；设备替换和统一详情
因安全边界或标识不稳定被明确推迟。

### 3.2 本期扩展现有能力

现有 `smartlight_report_export` 增加以下报告类型，不新增另一套导出工具：

- `energy_records`；
- `energy_analysis`；
- `lamp_survey_records`；
- `rtu_leakage_alarms`；
- `rtu_leakage_analysis`；
- `inspection_logs`；
- `maintenance_records`。

报告必须继承原查询的筛选条件、时区、截断信息和单位，不允许在导出时重新扩大时间范围。

### 3.3 暂不纳入

以下页面保留为后续候选，不在四期一次性包装：

| 候选域 | 暂缓原因 |
| --- | --- |
| `RTU用电量读取` | 页面名称中的“读取”可能触发设备主动抄表。正式确认其仅查询历史数据前，不归入只读能力 |
| 光敏管理 | 业务价值和字段口径尚未确认，且可能涉及阈值配置 |
| 气象站数据 | 需要先确认是否有稳定历史接口和明确的设备归属 |
| 智能锁管理 | 页面通常混合状态读取、开锁和授权，需单独做安全边界研究 |
| 控制策略、开关灯、参数配置 | 明确属于设备控制或配置写入，不属于本方案 |
| 巡检打卡、审核、检修提交 | 会改变下游业务状态，必须另走受控写入模型 |

## 四、统一读取契约

### 4.1 公共输入

所有列表和分析工具尽量使用同一组业务参数：

| 字段 | 规则 |
| --- | --- |
| `start_time` / `end_time` | 显式时间范围，按 `Asia/Shanghai` 解释 |
| `last_days` | 与显式时间范围互斥，由 AgentBridge 计算，不要求智能体先查系统时间 |
| `keyword` | 设备名称、编号、道路或控制箱的页面原生模糊条件 |
| `device_id` | 已经完成消歧时使用的精确下游标识 |
| `work_area` / `group` | 页面真实支持时下推，不在本地假装筛选 |
| `page` / `size` | 页码和页大小，单页最多 100 条 |
| `sort_by` / `sort_order` | 只开放已验证的服务端排序字段 |

当关键词命中多台设备时，列表读取可以返回候选；需要汇总、详情或跨页面串联时必须先完成消歧，
不能默认选择第一条。

### 4.2 公共输出

每项能力统一返回：

- `scope`：当前身份和页面的业务范围；
- `filters`：实际下推到目标系统的筛选条件；
- `observedAt` 和 `timezone`；
- `page`、`size`、`downstreamTotal`、`returnedCount`；
- `truncated`：分析或导出是否因安全上限截断；
- `sourcePage` 和 `sourceKind`：结果来自哪个业务页面和数据类别；
- `items`、`summary` 或 `analysis`；
- `warnings`：单位缺失、时间不完整、数据质量异常等说明。

目标系统明确返回空列表时使用成功空结果，不写成“系统错误”；登录失效、网络失败、权限不足和解析
失败分别返回稳定错误码，不能用空列表掩盖失败。

### 4.3 时间、排序与数量边界

| 数据类型 | 默认范围 | 单次最大范围 | 分析上限 |
| --- | --- | --- | --- |
| 用电记录 | 最近 7 天 | 92 天 | 最多 500 条明细 |
| 用电趋势 | 最近 30 天 | 366 天 | 最多 366 个日粒度点或 24 个月粒度点 |
| 单灯巡测 | 最近 24 小时 | 7 天 | 最多 500 条 |
| 漏电报警 | 最近 30 天 | 366 天 | 最多 500 条参与分析 |
| 漏电曲线、关灯时段电流 | 最近 24 小时 | 7 天 | 最多 500 个点 |
| 巡检日志、检修记录 | 最近 30 天 | 366 天 | 列表分页，导出最多 500 条 |

如果页面本身限制更严格，以页面限制为准。超过范围时要求缩小范围，不自动拆成大量请求，不在后台
进行全库扫描。

## 五、分域工具契约

### 5.1 用电记录与分析

`smartlight_energy_record_list` 支持：

- RTU 精确标识或关键词；
- 工区、分组、道路等经接口确认的范围条件；
- 日期范围和页面支持的统计粒度；
- 分页和服务端排序。

标准化字段至少包括：

- RTU 名称、编号和下游 ID；
- 统计周期开始、结束时间；
- 起始读数、结束读数、期间用电量；
- 单位；
- 数据生成时间和页面原始状态；
- 数据是否由下游直接给出，还是由两个累计读数计算。

`smartlight_energy_analysis` 返回总用电量、按日或按月趋势、RTU 排行和缺失数据说明。只有在目标
接口明确给出期间用电量，或累计读数顺序完整且没有回绕、换表和重置迹象时，AgentBridge 才能
计算差值。遇到负差、单位不一致或换表记录时保留原值并给出警告，不能把异常差值当成负用电量。

### 5.2 单灯巡测记录

`smartlight_lamp_survey_records` 支持灯杆、单灯控制器、道路、控制箱和时间范围。标准化字段按
真实响应确定，优先包括：

- 灯杆、灯具和单灯控制器标识；
- 所属道路、控制箱和 RTU；
- 设备采集时间与服务器接收时间；
- 在线状态、开关状态；
- 电压、电流、功率、功率因数等真实存在的电气字段；
- 原始异常或告警内容。

巡测记录是设备遥测历史，不是巡检人员的任务记录。OpenClaw 路由和工具说明必须明确区分
“单灯巡测”与“巡检任务、巡检日志”。

### 5.3 RTU 支路漏电

`smartlight_rtu_leakage_alarm_list` 只读取“RTU支路漏电报警记录”页面的真实支路漏电数据。
标准化字段包括：

- RTU、控制箱和支路；
- 漏电电流和单位；
- 阈值，仅在下游明确返回时提供；
- 首次发生、最近发生、解除或处置时间；
- 当前状态和原始告警类型；
- 页面备注和工区提交状态等只读快照。

`smartlight_rtu_leakage_analysis` 在有界记录上给出：

- 按日趋势；
- RTU、控制箱和支路排行；
- 当前未解除数量；
- 最近事件；
- 漏电电流曲线摘要；
- `analyzedCount`、`downstreamTotal` 和 `truncated`。

它不能复用已经弃用的 `smartlight_leakage_*` 单灯告警兼容入口。实现后，自然语言“漏电”应优先
进入新的 RTU 漏电工具；旧入口继续保留一个兼容周期，但不再由智能体主动选择。

### 5.4 关灯时间段电流

`smartlight_off_hours_current_list` 返回目标页面认定的关灯时段、电流采样、RTU 和支路信息。若
页面没有下游异常判定或阈值，工具只能陈述“关灯时段存在电流记录”，不能自行断言漏电、偷电或
设备故障。

如果页面的时间段来自运行策略，结果必须返回该时间段的来源和边界。查询跨越多个策略日期时，
不得用某一天的开关灯时间解释整个范围。

### 5.5 设备履历暂缓结论

页面探索确认 `RTU替换`、`PLC单灯替换`和`集中器替换`是设备执行流程，不是替换历史列表。
仅打开页面就能看到“开始执行”“失败重发”等控制入口。四期没有调用这些动作，也没有将其包装为
`smartlight:read`。后续只有发现独立、纯查询的替换记录或设备日志接口后才重新评估设备履历。

### 5.6 巡检日志与检修记录

`smartlight_inspection_log_list` 与已经上线的“计划中的巡检任务”分开建模。真实接口
`inspectionLog/getInspectionLog` 返回巡检组维度的应巡、实巡、正常、异常和等级统计，
没有逐人、逐设备巡检事件，因此工具名称保持“巡检日志”，输出口径明确标记为巡检组统计。

`smartlight_maintenance_record_list` 回答“后来怎样维修”，优先返回检修时间、对象、问题、措施、
结果、复核状态和附件摘要。只有下游明确关联巡检或告警时才返回关联关系，不根据时间接近自行猜测。

检修列表详情按钮实际请求只传 `type + deviceId`，没有传列表中的检修记录 ID。它不能证明返回的
就是用户所选的那一条历史记录，因此 `smartlight_operation_record_detail` 没有注册；列表结果返回
可核对的记录 ID、设备、时间、人员和道路，并明确 `stableDetailAvailable=false`。

## 六、接口探索与证据固定

### 6.1 探索原则

实现前使用已经登录的照明系统页面逐项打开目标菜单，通过浏览器网络记录核实接口。探索只执行
页面查询、筛选、分页和只读详情，不点击处置、提交、读取设备、导入、删除或控制按钮。

每个页面必须固定以下证据：

1. 页面菜单、路由和用途；
2. 请求方法、路径和内容类型；
3. 页码从 0 还是 1 开始，页面大小字段和总数字段；
4. 日期是否闭区间，时间字段使用设备时间还是服务器时间；
5. 关键词、设备、工区和状态筛选是否由服务端真正执行；
6. 服务端排序字段和并列项顺序；
7. 成功、空结果、未登录、无权限和业务失败的响应码；
8. 列表、详情和导出字段的名称、单位与空值形式。

探索结果使用脱敏响应生成测试夹具，不保存 Cookie、JWT、密码、验证码、完整人员隐私或临时链接。

### 6.2 `RTU用电量读取` 的判定

该页面必须单独观察：

- 如果打开页面和普通查询只读取已存数据，可以作为能耗数据的补充来源；
- 如果点击“读取”会向设备下发抄表、巡测或采集命令，则属于设备动作；
- 即使动作不修改配置，也不能放进 `smartlight:read`；
- 需要该动作时，应另做 `prepare → authorize → commit → verify` 的受控写入设计。

## 七、实现落点

### 7.1 AgentBridge

主要修改位置：

- `agentbridge/adapters/smartlight.py`
  - 增加能力常量、调用分派和标准化函数；
  - 复用已有设备消歧、日期解析、分页和登录刷新；
  - 为能耗、漏电和运维记录增加独立业务语义；
  - 不把页面标题直接当作字段含义。
- `agentbridge/mcp/central.py`
  - 注册八项经证据确认的工具；
  - 全部映射 `smartlight:read`；
  - 用工具描述明确“巡测/巡检”“单灯告警/RTU漏电”的区别。
- `agentbridge/core/central_service.py`
  - 注册能力规格和登录后自动续办；
  - 保持 `userSubject + systemId` 会话隔离；
  - 保留当前任务中的设备和筛选上下文，不承诺不存在稳定记录 ID 的详情追问。
- `agentbridge/core/report_exports.py`
  - 扩展现有报告类型；
  - 保留筛选条件、单位、数据质量和截断说明。

### 7.2 OpenClaw 与 Workspace

- 同步 `integrations/openclaw-agentbridge/lib/agentbridge-tools.json`；
- 增加少量、明确的自然语言路由提示，不把所有页面名塞进系统提示词；
- “用电、耗电、能耗”进入能耗能力；
- “单灯巡测、单灯历史数据”进入单灯巡测，不进入巡检任务；
- “支路漏电、漏电电流、关灯后还有电流”进入新的 RTU 漏电能力；
- “巡检日志”和“检修记录”分别进入对应工具；
- “上面这台”通过任务上下文解析；“第一条详情”只有存在稳定详情能力时才执行。

### 7.3 兼容与迁移

- 不改变现有十六项正式读取能力的工具名；
- 旧 `smartlight_leakage_summary` 和 `smartlight_leakage_analysis` 继续标记为单灯告警兼容入口；
- 新的 RTU 漏电工具上线后，OpenClaw 不再把任何普通“漏电”请求路由到旧入口；
- 报告类型增加新名称，不复用旧 `leakage_analysis` 的错误标题；
- 当前 Token 已有 `smartlight:read` 时无需再次扩权。

## 八、测试策略

### 8.1 自动化测试

1. 请求参数测试：日期、分页、关键词、设备精确标识、工区和排序字段正确映射。
2. 范围测试：默认范围、最大范围、500 条分析与导出上限生效。
3. 能耗测试：单位保留、累计读数回绕、换表、缺失点和负差不会被错误汇总。
4. 单灯巡测测试：设备时间与接收时间分开，不把巡测写成巡检。
5. 漏电语义测试：新工具只使用 RTU 支路漏电来源，旧单灯告警入口不会被选中。
6. 关灯时段测试：没有阈值时不自动判定故障。
7. 设备替换安全边界测试：不会把带执行按钮的页面注册为读取能力。
8. 运维记录测试：巡检组统计、检修记录和巡检任务语义分离。
9. 空结果与错误测试：空、未登录、无权限、超时和响应结构变化分别处理。
10. MCP 合约测试：八项工具均为只读提示，只要求 `smartlight:read`。
11. OpenClaw 路由测试：自然语言和连续追问选择正确工具，同一轮不重复拉取相同列表。
12. 报告测试：筛选、单位、截断和中文标题与源查询一致。
13. 文档测试：工具数量、导航、状态说明和链接一致。

### 8.2 真实只读验证

实现后先在 AgentBridge MCP 层验证每项工具，再在 Agent Workspace 走完整自然语言链路。真实验证
只查询和导出，不点击任何下游写按钮。Workspace 步骤见
[照明系统读取四期工作台验收方案](../../验收记录/照明实验室系统/照明系统读取四期工作台验收方案-2026-08-20.md)。

## 九、实施顺序

### 9.1 甲波次：能耗、巡测和真实漏电

1. 固定五个目标页面的接口和字段证据；
2. 实现用电记录、用电分析和单灯巡测；
3. 实现 RTU 支路漏电列表、分析和关灯时段电流；
4. 迁移自然语言“漏电”路由；
5. 完成适配器、MCP、路由和报告测试。

### 9.2 乙波次：设备和运维履历

1. 核对设备替换页并固定其写操作边界；
2. 实现巡检日志统计和检修记录；
3. 核对详情请求是否携带稳定记录 ID；
4. 对无法安全实现的设备履历和统一详情作明确暂缓记录；
5. 完成跨页面设备上下文测试。

### 9.3 发布收口

1. 执行 Python、Workspace、OpenClaw 和文档测试；
2. 对八项能力做真实 MCP 冒烟；
3. 在 Workspace 执行核心轮、深入轮和边界轮；
4. 更新总体适配说明、项目状态和正式工具数量；
5. 提交、推送、部署，记录 Release、插件版本和真实验收证据。

## 十、完成标准

- 八项经证据确认的正式工具全部可用，两个暂缓项不进入工具目录；
- 用电结果保留单位、统计周期和数据质量，不误算累计读数；
- 单灯巡测、巡检任务、巡检日志三种语义完全分开；
- RTU 支路漏电具有正式列表和分析入口，旧单灯告警兼容入口不再被主动调用；
- 设备替换和不稳定详情保持暂缓；巡检统计与检修记录可以按页面真实支持的条件有界查询；
- 连续追问可以复用上一条设备或记录，不要求用户输入内部 ID；
- 登录失效后完成可信登录，原查询自动续办；
- 所有能力只要求 `smartlight:read`，没有设备动作或业务状态变化；
- 自动化测试、真实 MCP 冒烟、Workspace 验收和部署健康检查全部通过；
- 文档明确区分“已设计、已实现、已部署、已真实验收”，不提前宣称完成。

## 十一、后续路线

四期完成真实验收后再评估读取五期。建议优先级为：

1. 光敏和气象站历史数据，补齐外部环境与照明运行的关联分析；
2. 智能锁状态与开锁记录，只做状态和审计读取，控制能力另行治理；
3. 计划、策略和参数的只读快照，用于解释设备为何在某时段开关；
4. 跨域综合分析，例如“某道路能耗升高是否同时伴随告警、换表或检修”。

这些候选项只有在接口语义、权限边界和真实使用价值确认后才进入正式能力，不以菜单数量作为开发
完成度。
