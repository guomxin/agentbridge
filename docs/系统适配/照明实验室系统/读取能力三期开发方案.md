# 照明实验室测试系统读取能力三期开发方案

## 一、建设目标

三期不再继续堆叠页面级列表，而是补齐智能体判断设备当前运行情况所需的“运行态读取层”，
并纠正二期中已经确认的告警语义偏差。完成后，用户应当可以直接询问：

- 照明系统现在整体运行怎么样；
- 哪些 RTU 或单灯控制器离线；
- 最近有哪些单灯告警；
- 某台 RTU 在指定时段的电压、电流和漏电电流如何；
- 最近是否存在真正的 RTU 支路漏电报警。

本期全部能力仍为只读，只复用现有 `smartlight:read` 权限，不增加设备控制、告警处置、
参数修改或其他下游写入。

## 二、现状问题

### 2.1 告警语义需要优先纠正

当前 `smartlight_leakage_summary` 和 `smartlight_leakage_analysis` 调用的接口是：

- `/lHisHitchAlarm/getDataByCondition`
- `/lHisHitchAlarm/getCountDataByCondition`

目标系统将这组接口用于“单灯报警记录”。实际记录中会出现“异常亮灯”等普通单灯告警，
因此不能把该接口的全部数据称为漏电记录。继续沿用旧语义会让智能体把普通单灯故障错误
表述为漏电事件。

真正的漏电信息应从两个来源读取：

1. RTU 告警中的支路漏电报警；
2. RTU 巡测记录中的漏电电流字段。

### 2.2 静态资产与运行态口径混在一起

现有 `smartlight_asset_search` 读取登记在册的控制柜、RTU 和灯杆，适合回答“有哪些设备”，
但不能稳定回答“设备现在是否在线”。目标系统的运行状态页面使用独立接口和筛选口径，
例如当前登记 RTU 数量与运行状态页面统计的照明用途 RTU 数量并不相同。

三期必须在结果中明确返回 `scope`、`observedAt` 和筛选条件，不允许把资产总数与运行态总数
直接相减或拼接成一个未经验证的结论。

## 三、能力包

三期包含五组业务能力，对外形成六个 MCP 工具。

| 能力组 | MCP 工具 | AgentBridge capability | 主要用途 |
| --- | --- | --- | --- |
| 运行总览 | `smartlight_runtime_overview` | `smartlight.runtime.overview` | 汇总 RTU、单灯控制器和灯具当前运行状态 |
| RTU 运行状态 | `smartlight_rtu_status_list` | `smartlight.rtu.status.list` | 查询在线、离线、停电、告警和工作模式 |
| 单灯运行状态 | `smartlight_lamp_status_list` | `smartlight.lamp.status.list` | 查询控制器在线状态、灯具开关和当前电气数据 |
| 单灯告警 | `smartlight_lamp_alarm_list` | `smartlight.lamp.alarm.list` | 分页查询单灯告警明细 |
| 单灯告警分析 | `smartlight_lamp_alarm_analysis` | `smartlight.lamp.alarm.analysis` | 对单灯告警做有界趋势和排行分析 |
| RTU 巡测记录 | `smartlight_rtu_survey_records` | `smartlight.rtu.survey.records` | 查询指定 RTU 的电压、电流、温湿度和漏电电流 |

所有工具只要求 `smartlight:read`。本期不增加新的 Token 权限范围。

## 四、工具契约

### 4.1 运行总览

`smartlight_runtime_overview` 不接收业务筛选，返回当前用户可见范围内的运行快照：

- RTU 总数、在线、离线、停电、禁用和告警数量；
- 单灯控制器总数、在线和离线数量；
- 灯杆、单灯、双灯、三灯及其他灯杆数量；
- 当前开灯和关灯数量；
- `scope`、`observedAt`、`timezone=Asia/Shanghai`；
- 每个数据块的来源和筛选口径。

已验证接口：

- `/rRtu/getRtuStateCountDataByConditionNew`
- `/lLamppost/newGetTotalStatus`

总览只陈述接口返回的当前快照。不能根据“控制器总数减在线数”等方式自行推导一个下游未
明确给出的业务状态。

### 4.2 RTU 运行状态列表

`smartlight_rtu_status_list` 支持：

| 字段 | 说明 |
| --- | --- |
| `keyword` | RTU 名称、编号等页面支持的模糊条件 |
| `state` | `all`、`online`、`offline`、`power_off`、`disabled` |
| `alarm_only` | 仅返回当前有告警的 RTU |
| `work_area` / `group` / `model` | 按工区、分组和型号筛选 |
| `page` / `size` | 分页，单页最多 100 条 |

返回 RTU 的精确 ID、名称、型号、控制柜、分组、运行状态、最后在线时间、是否告警、当前
开关状态和工作模式。已验证列表接口为 `/rRtu/getRtusByConditionNew`。

工具结果必须标明运行页面使用的用途范围，不能冒充全部登记资产。需要查看登记信息时，
智能体继续调用 `smartlight_asset_search` 或 `smartlight_asset_detail`。

### 4.3 单灯运行状态列表

`smartlight_lamp_status_list` 支持：

| 字段 | 说明 |
| --- | --- |
| `keyword` | 灯杆、控制器、道路或控制柜关键词 |
| `controller_state` | `all`、`online`、`offline` |
| `lamp_state` | `all`、`on`、`off`、`abnormal` |
| `street` / `cabinet` / `work_area` | 页面允许的范围筛选 |
| `page` / `size` | 分页，单页最多 100 条 |

已确认页面列表接口为 `/lLamppost/getLampDetialList`。返回字段以真实响应为准，首批标准化：

- 灯杆和单灯控制器标识；
- 所属道路、控制柜和 RTU；
- 控制器在线状态和最后活动时间；
- 灯具开关状态；
- 响应中确实存在时返回电压、电流、功率等实时字段。

缺失的实时字段返回空值，不从状态名称或相邻设备推断。

### 4.4 单灯告警列表与分析

`smartlight_lamp_alarm_list` 和 `smartlight_lamp_alarm_analysis` 复用现有
`/lHisHitchAlarm/...` 接口，但使用正确的“单灯告警”语义。

共同筛选条件：

- 显式 `start_date` / `end_date`，或 `last_days`；
- 告警状态、告警类型、道路、工区、控制柜和灯杆关键词；
- 日期按 `Asia/Shanghai` 闭区间解释。

列表返回分页明细；分析最多读取 500 条并返回：

- `downstreamTotal`、`analyzedCount` 和 `truncated`；
- 日期趋势、告警类型、灯杆、道路和状态排行；
- 最近告警；
- `alarmSource=single_lamp`。

单灯告警中出现“漏电”字样时，只能陈述该条告警的原始类型，不能把整个结果集称为漏电
数据。

### 4.5 RTU 巡测记录

`smartlight_rtu_survey_records` 通过 `/rHisCoplogPhase/getDataByCondition` 查询设备遥测历史。

输入：

| 字段 | 说明 |
| --- | --- |
| `rtu_id` | 精确 RTU ID，优先使用 |
| `rtu_keyword` | 未给 ID 时用于查找唯一 RTU；多项命中必须先返回候选 |
| `start_time` / `end_time` | 查询时间范围，默认最近 24 小时 |
| `page` / `size` | 分页，单页最多 100 条 |

首批标准化字段包括：

- RTU 时间和数据接收时间；
- A、B、C 三相电压和电流；
- 支路或继电器电流；
- 温度、湿度和功率因数；
- 下游返回的漏电电流结构；
- 开关量和告警内容。

默认时间范围为最近 24 小时，单次最长 7 天，最多分析或返回 500 条。范围过大时要求智能体
缩小范围，不能执行无界扫描。

## 五、告警语义迁移

### 5.1 保留兼容入口

现有工具不能立即删除，否则已部署的 OpenClaw 工具目录和历史提示词可能失效：

- `smartlight_leakage_summary`
- `smartlight_leakage_analysis`

首个兼容版本采取以下策略：

1. 新增正式的单灯告警工具并优先暴露给智能体；
2. 旧工具保留服务端调用能力，但说明中明确标记“兼容旧入口，实际数据为单灯告警”；
3. 旧结果增加 `deprecated=true`、`canonicalTool` 和 `alarmSource=single_lamp`；
4. OpenClaw 协调器不再把自然语言“漏电”路由到旧工具；
5. 下一稳定版本观察无旧调用后，再从公开工具目录隐藏旧入口，服务端继续保留一个兼容周期。

### 5.2 报告类型迁移

报告导出的正式类型新增 `lamp_alarm_analysis`。旧的 `leakage_analysis` 暂作兼容别名，但：

- 文件名和标题改为“单灯告警”；
- 元数据标记已弃用和正式替代类型；
- 自然语言“导出漏电记录”必须先走 RTU 告警或 RTU 巡测数据，不能生成旧单灯告警报告。

### 5.3 现有 RTU 告警说明

`smartlight_alarm_list` 和 `smartlight_alarm_analysis` 当前读取 RTU 告警。为降低歧义，本期先
完善描述和输出字段，增加 `alarmSource=rtu`，但不立即改工具名。后续是否迁移为
`smartlight_rtu_alarm_*` 单独评估，避免本期同时扩大兼容范围。

## 六、实现落点

### 6.1 AgentBridge

主要修改：

- `agentbridge/adapters/smartlight.py`
  - 增加能力常量、调用分派、查询方法和标准化函数；
  - 修正单灯告警与漏电语义；
  - 对运行态和巡测记录实施分页、日期与字段边界。
- `agentbridge/mcp/central.py`
  - 注册六个 MCP 工具；
  - 所有工具映射到 `smartlight:read`；
  - 更新旧工具的兼容说明。
- `agentbridge/core/central_service.py`
  - 注册新的能力规格和调用编排；
  - 保持登录后自动续办和错误语义不变。
- `agentbridge/core/report_exports.py`
  - 增加正式的单灯告警报告类型及兼容迁移字段。

### 6.2 OpenClaw

- 同步 `integrations/openclaw-agentbridge/lib/agentbridge-tools.json`；
- 为“运行情况、离线 RTU、单灯状态、单灯告警、巡测记录、漏电”增加简短路由提示；
- 明确“巡测记录”不是“巡检任务”；
- 明确“漏电”优先进入 RTU 告警或 RTU 巡测，不进入单灯告警兼容工具；
- 保持一轮任务只调用一次相同列表工具，连续追问复用当前任务上下文。

### 6.3 文档

实现完成后同步：

- 总体适配说明和能力数量；
- 工具目录、字段口径和兼容周期；
- 项目当前状态；
- Workspace 真实验收结果。

## 七、测试范围

### 7.1 自动化测试

1. 适配器单元测试：查询参数、分页、日期、状态映射、标准化和空值。
2. 语义回归测试：`异常亮灯` 必须归为单灯告警，不能标为漏电。
3. 口径测试：资产列表数量与运行状态数量不一致时，结果仍分别保留各自 `scope`。
4. 遥测边界测试：默认 24 小时、最长 7 天、最多 500 条。
5. MCP 合约测试：六个新工具只要求 `smartlight:read`。
6. 兼容测试：旧工具仍可调用，但返回弃用和正式替代信息。
7. OpenClaw 测试：自然语言“漏电”不选择旧单灯告警入口。
8. 文档测试：工具清单、导航和能力数量一致。

### 7.2 真实只读验证

部署前直接调用 MCP 验证：

- 运行总览能取得 RTU 和单灯当前快照；
- RTU 运行状态列表能返回最后在线时间；
- 单灯运行列表能返回真实状态或明确空字段；
- 单灯告警列表中可以观察到真实告警类型；
- 选择一台有历史数据的 RTU，读取一个有界时间段的巡测记录；
- 全程没有照明写能力调用和下游状态变化。

Workspace 端到端步骤见
[照明系统读取三期 Workspace 验收方案](../../验收记录/照明实验室系统/照明系统读取三期工作台验收方案-2026-08-20.md)。

## 八、实施顺序与完成标准

### 8.1 实施顺序

1. 先交付告警语义修正、新的单灯告警工具和兼容层。
2. 交付运行总览、RTU 状态和单灯状态。
3. 交付 RTU 巡测记录及时间范围保护。
4. 同步 MCP、OpenClaw、报告类型和文档。
5. 执行全量自动化测试、真实 MCP 冒烟和 Workspace 验收。
6. 测试通过后提交、推送并部署服务器，最后记录 release 和验收证据。

### 8.2 完成标准

- 六个新工具均可由第一用户通过 `smartlight:read` 调用；
- 单灯告警、RTU 告警和真实漏电数据来源不再混淆；
- 运行态结果明确统计口径和观察时间；
- 巡测查询有时间和数量上限；
- 旧调用在兼容周期内不崩溃，智能体不再主动选择旧入口；
- Workspace 中的自然语言请求能得到单一、按序、可恢复的结果；
- 自动化、真实只读和部署健康检查全部通过；
- 没有任何照明业务写入。

## 九、实施结果

本方案已于 2026-08-20 完成开发、部署和真实只读验收，线上 Release 为
`5f5a653f8165`，OpenClaw 插件版本为 `0.4.49`。

交付结果：

- 六个新工具已进入 MCP 和 OpenClaw 工具目录，统一使用 `smartlight:read`；
- 旧漏电入口保留兼容调用，但正式语义和报告标题已迁移为单灯告警；
- RTU 告警、单灯告警和 RTU 巡测漏电电流已经分开建模；
- RTU 巡测字段按真实页面响应完成映射，包括三相电压、电流比、回路电流、相位回路、继电器、漏电电流和告警内容；
- 列表查询严格限制返回条数，名称筛选在有界结果内完成，不把页面名称误传为下游 ID；
- 发布脚本的必需工具检查和 MCP 冒烟入口已覆盖六个新工具。

验证结果：Python 测试 612 项通过、3 项跳过，并通过 392 个子测试；Workspace 前端测试
21 项通过；OpenClaw 插件测试 138 项通过；插件打包检查通过。真实 MCP 与 Workspace 证据见
[读取三期工作台验收结果](../../验收记录/照明实验室系统/照明系统读取三期工作台验收结果-2026-08-20.md)。
