## 1. 一期目标

以泰华日志系统作为[只读数据库深度分析能力设计](../../架构设计/只读数据库深度分析能力设计.md)的第一个业务样板，完成“发现数据 → 选择指标和范围 → 受控读取 → 多步分析 → 核对数字 → 交付报告”。

业务范围建议定为：日志登记工时统计、项目投入分布、团队日志分析，以及带原文依据的工作内容归纳。数据来源是员工登记的工作日志，指标统一称为“登记工时”；不能自动解释为考勤、实际工作时长、生产效率或绩效结论。

现有 API 适配继续承担本人/团队日志查询、项目搜索与受控创建。新增数据库分析入口，明确标记数据来源，不在现有 API 读取失败时静默改走权限更宽的数据库。

## 3. 数据集建设清单

以下名称为拟议逻辑数据集。四个业务对象现已对应到 `work_log`、`user`、`dept`、`project`；下表保留初始盘点需求，逐项核验结果见实际映射文档。一期先做四个业务数据集，加一套权限映射；关注组关系已发现，按业务规则确认结果决定是否纳入首批发布。

| 数据集或配置 | 一期必需字段与规则 | 当前缺口 |
| --- | --- | --- |
| 工作日志事实 | 稳定日志 ID、用户 ID、日志日期、登记工时、项目 ID、正文；有效记录规则 | 物理表、软删除/草稿/作废规则、类型字典、字段完整性 |
| 人员维度 | 用户 ID、用户名、显示名称、部门关联 | 是否覆盖离职人员，身份映射与部门历史 |
| 部门维度 | 部门 ID、名称、父子关系、统计层级 | 当前归属与日志发生时归属的区别，历史调整 |
| 项目维度 | 项目 ID、编码、名称、状态及枚举 | 停用/归档项目是否保留，重名、编码变更与可见范围 |
| 数据权限映射 | 中央用户 → 日志系统用户 → 可读数据域 | 权限来自数据库、应用规则还是经确认的试点授权名单 |
| 关注组，条件项 | 组、所有者、成员关系及有效范围 | 现有接口选项不足以证明完整关系和授权语义 |

日志正文按权限单独投影，普通工时查询不抽取正文。认证表、密码散列、Token 和会话数据不进入数据集发布目录。

如果数据库缺少人员或部门历史，一期按“当前组织归属统计历史日志”，报告显式说明；不得声称还原了日志发生时的组织结构。离职人员的历史日志不能因为当前人员表筛选而无意消失。

项目为空的日志保留为“未关联项目”。有项目 ID 但找不到项目记录的日志归入“项目关联异常”，不与无项目日志混为一类，也不静默丢弃。

## 4. 一期指标及口径

全部指标基于同一授权范围、有效记录集合和业务日期窗口。数据库字段映射、类型含义与状态规则确认后才能正式发布。

| 指标 | 建议口径 | 易错点 |
| --- | --- | --- |
| 日志条数 | 按日志 ID 去重计数 | 同人同日可以有多条日志 |
| 登记工时合计 | 对有效数值工时求和，保留原始精度 | 关联部门、项目或关注组时不得重复累加；缺失/非法值另报 |
| 有日志人数 | 窗口内不同用户 ID 数 | 不等于应填人数或在岗人数 |
| 有日志人日数 | 不同“用户 ID + 日志日期”组合数 | 不等于考勤出勤人日 |
| 平均登记工时/有日志人日 | 登记工时合计 ÷ 有日志人日数 | 分母为零返回不可计算；报告工时缺失覆盖情况 |
| 项目工时分布与占比 | 按项目分组；分母为相同范围内有效登记工时合计 | 未关联项目与关联异常均单列，使工时分布可对账 |
| 未关联项目工时占比 | 项目 ID 为空的有效登记工时 ÷ 有效登记工时合计 | 允许不选项目，不把未关联自动判为违规 |
| 登记工时期间变化 | 同口径的本期、上期工时差额；可计算时返回变化率 | 完整周/月与未结束期间不得混比，基期为零时单独说明 |

上述指标支持日期、人员、部门和项目维度，以及趋势、排名和贡献分解。参与某项目的人数按该项目独立去重，多个项目的参与人数不能直接相加作为团队总人数。

`typeCode` 可先作为待确认枚举保存，不直接映射为研发、实施、运维等工作类别。若业务需要这些类别，先确认系统字典；没有字典时，模型主题标签只能作为单独的派生分析结果。

## 5. 三个一期业务样板

### 5.1 项目登记投入分析，必做

示例问题：“上一个完整月，各项目登记了多少工时，哪些项目占比最高，主要由哪些部门和人员参与？”

执行：确认范围 → 项目工时聚合 → Top 项目下钻 → 部门/人员分布 → 合计复核。

交付：项目工时及占比、参与人数、分布表、未关联项目情况和可回查的日志依据。部门权限有限的用户只看到授权范围内的项目投入，不能把这一结果称为项目全公司总投入。

### 5.2 团队登记工时变化分析，必做

示例问题：“最近两个完整周，团队登记工时的变化主要来自哪些项目和人员？”

执行：明确两个窗口 → 统计登记工时、有日志人数与人日 → 项目贡献分解 → 主要变动下钻 → 检查补录及缺失数据的影响。

交付：两期对照、贡献明细、每日趋势、数据质量说明。识别的是登记数据的变化；不自动下结论为效率下降、工作不足或考勤异常。没有历史变更记录时，无法精确重建当时尚未补录的报表。

### 5.3 带证据的团队工作周报，必做；主题量化为条件项

示例问题：“根据上周日志形成团队工作摘要，列出主要事项、涉及项目、明确记录的阻碍及对应日志。”

执行：先汇总数字 → 按允许范围读取正文 → 逐批归纳并保留日志 ID → 合并事项、去重 → 对照原文核验 → 输出摘要和证据引用。

完整周报需要覆盖目标集合的全部有效日志；预算不足时缩小明确范围，或标为抽样摘要，不把样本当作全量结论。正文可交给哪个模型处理，作为数据源策略提前配置。

正文可能描述“推进中”或“待处理”，不能改写为“已完成”。多个事项共用一条日志的总工时时，不按模型猜测拆分主题工时；只有可信分类或明确分配数据时才发布主题工时占比。模型归纳保存模型/提示版本和证据，但不承诺重新生成相同文字。

## 6. 工程建设包与完成条件

| 建设包 | 必须交付 | 完成条件 |
| --- | --- | --- |
| A. 数据源与只读盘点 | 单一真实方言适配、密钥引用、连接测试、白名单、规模/索引与只读权限报告 | 能在批准网络和预算内读取指定对象；实际权限已核验 |
| B. 语义映射 | 四个数据集、八项指标、字段字典、粒度与关联规则、Schema 版本 | 业务负责人确认，未知字段不编造含义 |
| C. 用户与数据权限 | 中央身份映射、行列范围、正文策略、导出权限 | 两个不同范围用户无法越权，跨用户缓存与文件隔离 |
| D. 受控查询 | 时间、部门、成员、项目、关键词筛选；聚合、比较、排名、明细下钻 | 查询参数绑定、字段白名单、稳定分页和结果完整性标记 |
| E. 分析任务 | 固定算子、多步结果引用、小规模授权快照、进度与取消 | 完成三类样板，取消到实际执行端，故障不误报空结果 |
| F. 报告与证据 | Markdown/HTML 分析报告和受控明细导出；查询 ID、口径、时间与来源 | 每个关键数字可追溯到计算结果，文字结论可追溯到日志 |
| G. 运行治理与验收 | 数据源预算、任务预算、摘要脱敏、缓存隔离、保留期、对账记录 | 真实数据正确性、权限与负载均有核对证据 |

控制面复用现有能力注册、中心身份、MCP、Task 与 Operation；本轮新增数据库执行、数据语义、分析预算和结果生命周期。正文归纳由宿主在允许的数据流出策略内完成，数字计算由确定性算子完成。

一期通用能力使用前述架构设计的 `database.dataset.*`、`database.query.*`、`database.analysis.*`、`database.result.*` 和 `database.report.export`。注册数据源为泰华业务域时必须做数据源级授权；不能只获得通用查询 Scope 就可访问任意 `source_id`。

建议新增 `taihua:analytics:read`，正文和导出可分别使用 `taihua:analytics:content`、`taihua:analytics:export`，均为拟议名称。现有 `taihua:read` 不自动获得数据库分析权限；即使发放分析 Scope，仍需独立计算用户实际可读数据范围。

## 7. 日志系统必须专项处理的细节

1. **日期双视角。** 当前团队接口提供 `submittedAt` 和 `logDate` 视角，有日期条件时适配器强制 `logDate`；输出字段中有 `createdAt`、`updatedAt`，没有独立归一化的 `submittedAt`。数据库一期默认按日志日期分析，创建时间与正式提交时间的关系待确认。
2. **完整性。** 当前个人读取默认取 100 条、最多 500 条，代码截取结果且未给出显式截断标记；团队默认每页 20 条、最多 100 条，`totalElements` 缺失时会以当前页条数作为 total。现有单次调用不能直接作为全量统计依据。
3. **部门关联。** 当前日志归一化保留部门名称，没有保留部门 ID；数据库分析应使用稳定 ID 和明确的归属时间，不能只按部门名称连接。
4. **关注组。** 关注组是筛选集合，是否具有授权含义尚未确认；不能因为属于关注组就扩大用户数据权限。多人多组关系用去重成员集合或半连接，避免日志工时倍增。
5. **工时阈值。** 当前创建入口限制单条工时 0.5—16 小时、步长 0.5。这只是当前写入入口约束，不能推导历史数据均遵守，也不能作为所有人员日合计异常标准。
6. **权限权威。** 成员/部门选项可以用于 API 对照，但不天然构成完整授权模型。必须确认部门层级、个人例外、跨部门项目、离职人员和历史日志的访问规则。
7. **摘要与异常脱敏。** 当前通用读取 Operation 摘要保留请求参数，数据库关键词和正文分析请求需采用能力专属脱敏；结果、错误和文件同样遵循分类策略。
8. **快照变化。** 日志可补录或修改。报告记录抽取时间、业务窗口和可得的数据水位；保留相同快照才能复算当次数字。只有当前状态时不宣称支持历史任意时点查询。

## 9. 接入前待补资料

无需现在提供凭据。开始数据库盘点时，通过受控配置接收连接信息，并补齐：

1. **数据库与网络：** 产品、版本、主库或副本、连接位置、TLS、只读对象与允许的查询负载。
2. **结构与规模：** 日志、人员、部门、项目及权限相关表/视图的数据字典、关联键、索引、记录规模和历史范围。
3. **状态与时间：** 日志类型、有效/草稿/删除规则、工时单位、日志日期、创建/提交/更新时间及补录规则。
4. **权限与使用：** 试点用户与可读范围、权威权限来源、正文可使用的模型环境、是否可导出。
5. **组织与项目：** 当前与历史归属、离职人员处理、归档项目保留、关注组是否为首批需求。
6. **验收样本：** 一个明确部门或项目、两个可对照的完整时间窗口、权威页面/API/SQL，以及业务核对人。

## 10. 验收与实施顺序

先完成 A、B、C，冻结数据与权限契约；随后完成 D 及数值对账，再完成 E、F 和运行验收。组织历史、工作日历等缺失项不阻塞基础分析，但必须限制对应指标发布。

验收至少包含：

- 以同一用户、范围、日志日期、有效状态和数据时间，对比数据库与原系统的日志 ID 集合、逐条工时和正文样本；API 对账需完成全分页并验证总量，无法证明完整时用所有者确认的权威 SQL/报表。
- 验证同日多条、无项目、项目失联、部门变更、离职历史、修改或补录、缺失/异常工时等边界；没有真实样本的边界使用合成数据验证并明确标记。
- 三个业务样板的合计、分组、人数去重、变化贡献与原文归纳均能核对。
- 两个真实授权范围的身份在明细、聚合、正文、缓存和导出方面保持隔离；权限撤销阻断后续访问。
- 大时间窗口、长关键词查询、并发任务和取消均受预算控制，超时不解释为无日志。
- 报告清楚显示授权范围、数据时间、口径、完整/抽样/截断状态与证据引用；相同快照可复算关键数字。

一期完成的判据是“用户能就真实日志提出多步分析问题，并获得可核查的结果”，连接成功和能够执行一条 SELECT 只是接入起点。
