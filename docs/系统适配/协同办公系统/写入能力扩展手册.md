# 协同办公写入能力扩展手册

> 状态：当前实施指南
>
> 所有探索和执行均使用中心受控会话。安全边界遵循
> [受控写入模型](../../架构设计/受控写入模型.md)，覆盖情况记录在
> [事项能力矩阵](./事项能力矩阵.md)。

本手册把一次性的页面探索提升为可重复的新流程写入能力。适用于新增审批流程、发起模板或会议
等特殊模块，不适用于开放任意页面点击和任意 HTTP 请求。

## 一、提升前必须回答的问题

每个准备公开的写动作必须回答：

1. 用户表达的业务意图是什么？
2. 哪个页面或后台接口初始化该动作？
3. 执行前需要哪些字段和标识？
4. 哪个请求真正越过写入边界？
5. 哪个权威回读能证明业务成功？
6. 可能出现哪些失败，系统应在哪一步停止？
7. 该动作是否可逆，补偿能力是什么？
8. 需要哪项独立权限，现有 Token 是否应当扩权？

公开能力保持业务层表达。页面按钮、接口名、隐藏字段和表单内部结构只是适配器实现细节。

## 二、探索顺序

不要从“点提交”开始，按以下顺序收集证据：

1. 通过稳定业务标识、待办、模板或固定模块入口定位目标；
2. 读取当前页面或初始化接口，只保存不含秘密的结构证据；
3. 区分用户可填写字段、系统只读字段和系统自动计算字段；
4. 找出目标系统自己的前置检查或可用性校验；
5. 如果存在正文 iframe 或隐藏正文，找出正文保存步骤；
6. 找出最终保存、发送或提交请求；
7. 找出能够证明结果的列表、详情或状态接口；
8. 判断是否还需要渲染页面级验证；
9. 记录失败响应、业务拒绝原因和结果未知边界；
10. 评估是否存在撤销、删除草稿或其他补偿路径。

协同办公系统的流程工具栏与真实业务表单可能位于不同 frame。高层详情字段为空时，应先检查
业务 iframe，不能据此认定表单没有必填字段。

## 三、契约固化

从探索证据中固化以下契约：

- 模板 ID、表单 ID、节点类型和动作类型；
- 标题族和事项类别；
- 可编辑字段 Schema、枚举值、长度和条件字段；
- 必须只读展示的业务字段；
- 初始化、预检、正文保存、提交和回读顺序；
- 成功、失败、冲突、登录失效和结果未知的判据；
- 可逆性、补偿动作和权限范围。

不得把某个用户的 `ownerId`、`spaceId`、时间戳、临时正文 ID 或隐藏 CSRF 值写成跨用户常量。

## 四、实现生命周期

正式能力按以下步骤实现：

1. 先实现零写入探针或 dry-run 契约检查；
2. 实现业务级 `prepare` 入口；
3. 需要字段时创建可信字段卡，并根据用户对话预填；
4. 重新读取实时目标，运行目标系统自己的前置检查；
5. 冻结不可变计划并创建独立授权卡；
6. 授权后再次校验目标、会话和字段版本；
7. 正文型模块先保存正文，再发送且只发送一次最终写请求；
8. 使用权威列表、详情或状态接口回读；
9. 返回结构化结果、业务失败原因和后续检查所需的不透明标识；
10. 记录脱敏审计，不保存完整意见、秘密和内部表单数据。

只得到“HTTP 200”不能提升为正式能力，回读必须证明业务状态按预期改变。

## 五、填写卡与授权卡

字段卡：

- 只允许业务契约声明的字段；
- 用户已提供的日期、时间、地点、事由等信息应预填；
- 系统计算字段保持只读；
- 枚举使用选项，不让用户填写可能不匹配的自由文本；
- 目标系统实时不可用时不提前诱导用户授权。

授权卡：

- 展示用户能理解的业务目标和影响；
- 冻结表单关键字段、目标身份和回读基线；
- 保存草稿与正式提交使用不同授权；
- 批量事项逐项创建独立计划和授权，不共用一张模糊卡；
- 新卡替代旧卡时，旧卡进入 `superseded`。

## 六、真实验证

提交代码前：

1. 定向测试覆盖授权门禁、正常顺序、失败阻断、幂等和回读；
2. 运行中央服务、CLI、MCP、可信卡和宿主相关回归；
3. 使用中心受控会话和 `CentralBrowserWorker` 做一次真实安全验证；
4. 中文内容使用 UTF-8 JSON 或已经验证的编码路径；
5. 同时核对后台回读和用户页面可见状态；
6. 可撤销流程在用户授权下完成“提交、核验、撤销、再核验”；
7. 真实验证失败时停止，不提交未完成验证的写动作。

没有合适真实待办时，可以完成契约、模拟器、零写入探针和自动化测试，但必须把真实 commit 验收
明确标记为待完成。

## 七、参考样板：会议创建

会议模块不是普通协同提交，完整链路是：

1. `meetingInfo` 初始化表单并返回临时正文模块 ID；
2. 复用会议室读取能力的 `roomListInfo` 快照，查询目标时段的会议室可用性；
3. `validateRoomApps` 校验所选会议室；
4. `content.do?method=saveOrUpdate` 保存标准正文；
5. `meetingAjaxManager.send` 创建并发送会议；
6. `roomListInfo` 回读会议室占用；
7. `meetingInfo`、`meetingView` 和查看页共同核验主题、时间、会议室和正文。

只创建会议外壳是不完整的。前端在发送前会把正文保存到临时模块，后台适配也必须保持该顺序，
否则查看页可能出现正文数量错误。

会议室目录、时段占用和“我的申请”属于独立只读能力，详见
[OA 会议室读取能力](./会议室读取能力.md)。查询快照只用于候选展示，会议创建仍须在字段提交、授权前和
进入写边界前复检，避免把过时的空闲状态当成提交依据。

会议室模块自己的申请与撤销不能复用会议创建的 `send` 路径。独立申请按
`roomListInfo -> validateRoomApps -> applyRoom -> getMyApps` 执行；独立撤销按
`getMyApps -> cancelRoomApp(operation=0) -> getMyApps` 执行。两者的字段、冻结计划和授权卡均与
“新建会议”隔离，详见 [OA 会议室申请与撤销能力](./会议室申请与撤销能力.md)。

## 八、参考样板：待办接收处理

普通待办不按按钮名称各做一套命令，而是按事项流程组织：

- `approve` 只在详情页契约确认存在可执行 `ContinueSubmit` 路径时使用；
- 补签、效能数据、差旅费、劳动合同续签、知识产权、加班、离职、工作交接和考勤确认分别拥有专用契约；
- 普通知会与审批分开表达，不把“已阅”伪装成“同意”；
- 业务表单预填只在证据证明该流程需要时实现；
- `archive` 在归档目标、验证和补偿尚未完成前保持不可执行。

当前 15 类待办共用 `seeyon_pending_execution`：提交前创建独立核验页，原提交页保留并持续处理浏览器事件。
成功必须同时取得完整待办中的目标消失和同一 `affair_id` 已办记录，并核对冻结的摘要、流程标识。
列表不完整、已办缺失、标识冲突或读取失败均不得判成功；越过提交边界后只重试读取，不重复提交。
待办主页未取全时，从该主页实际提供的“更多”入口读取已核验的全部待办列表：每页 50 条、最多 100 条，
核对分页元数据与唯一身份，多页读取后复查第一页锚点；补读在独立页面进行，不导航原办理页。
独立核验页也须保留通过原 owner 创建受控补读页的能力，不能仅在根 Worker 测试完整列表。
嵌套页分别关闭，沿用同一受控会话、同源限制和读取预算；相关回归见
[结算单提交后核验修复](../../验收记录/业务结算单提交后核验修复-2026-10-29.md)。
超过上限、总数或条目变化、身份异常、超时或其他部分返回仍不能证明完整；提交后核验据此保留结果未知，不能仅提高 limit。
Workspace 可以展示合法的部分结果及覆盖提示，但不开放选择或准备；准备入口的完整来源校验保持不变。
合同和零写入验收见 [待办完整读取与部分结果展示修复](../../验收记录/协同办公待办完整读取与部分结果展示修复-2026-10-29.md)。
页面提示、脚本错误和请求异常按限量脱敏证据记录，HTTP 200 和调度成功均不代表办理成功。
会议、草稿、已发撤销和归档类
动作必须使用各自的权威回读，不能套用通用判据。

## 九、批量处理

跨系统的持久化父任务、状态机、自动推进、停机与恢复契约以
[批量受控任务编排设计](../../架构设计/批量受控任务编排设计.md)为准。本节只说明协同办公系统的业务约束；
已登记的 15 类待办可以使用通用批次，流程差异仍由各自冻结计划和字段契约约束；未登记流程不自动获得批量能力。

“处理所有补签申请”等批量意图应：

1. 先读取并冻结候选列表；
2. 按待办日期和 `affair_id` 的稳定顺序逐项 prepare；
3. 每项显示独立卡片和当前序号；
4. 一项完成后继续下一项，不因第一项成功就结束；
5. 已失效旧卡标记为 `superseded` 或明确终态；
6. 任一项失败、拒绝、过期或结果未知时保守停止，不静默处理剩余项；
7. 最终汇总成功、失败、跳过和未处理数量。

批量处理仍不能绕过逐项授权，也不能把一项的流程契约、意见或目标复用于另一项。
智能体面对“所有补签申请”时只调用一次 `oa_missed_punch_approval_batch_prepare`；目标列表由中心端读取和
冻结，公开工具不接受 `affair_id` 数组。当前项权威成功后由已有 `interaction_resume` 直接返回下一张卡，
不要求用户说“继续”，也不新增模型可见的批量 commit。
