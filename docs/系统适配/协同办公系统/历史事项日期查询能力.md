# 历史事项日期查询能力

更新日期：2026 年 11 月 9 日。

## 完整历史报告与续读

查询全部已办/已发及提交日期、当前状态、流程节点，使用 `oa.workflow.history.query`，
MCP 对应 `oa_workflow_history_query`。旧 `done.list`/`sent.list` 的兼容口径见后文，不能用其首屏证明全历史。

```json
{"collection":"done","keyword":"业务结算单","temporal":{"kind":"all"},"limit":50}
```

`collection` 为 `done` 或 `sent`。`limit` 是每个输出页的条数上限，不是扫描范围；同时受完整行字符预算限制。
已办按事项身份保留个人处理记录；同一流程多次处理不按标题合并，以免丢失处理日期，匹配条数不能直接称为唯一单据数。
返回 `next_cursor` 时通过 `oa_workflow_history_next(cursor)` 继续同一查询，不能修改日期、集合或关键词。
`scanning`/`details` 只返回进度；`complete`/`partial` 返回结果页。源读取完成与报告交付分页分别判断：
即使 `coverage.status=complete`，仍可能有下一页；最后一页不能证明调用者读过前页。

| 时间意图 | temporal 示例 |
| --- | --- |
| 起止日期（含两端） | `{"kind":"between","start":"2026-10-01","end":"2026-10-31"}` |
| 开始日期以来，至原请求当日 | `{"kind":"since","start":"2026-10-01"}` |
| 截至结束日期 | `{"kind":"until","end":"2026-10-31"}` |
| 全部历史 | `{"kind":"all"}` |
| 上月、本月至原请求日 | `{"kind":"previous_calendar_month"}`、`{"kind":"current_calendar_month"}` |
| 最近 N 天（含原请求日） | `{"kind":"rolling_days","days":30}` |

兼容 `absolute_range`、昨天、前天、上周。所有范围以可信受理时间、上海时区编译一次并保存，精度为天；
续读不重新计算“今天”。已办默认 `date_basis=processed_at`，已发默认 `initiated_at`。
按提交/发起日期查询已办时显式使用 `date_basis=initiated_at`，中心遍历后筛选，不能把处理日期替代提交日期。
已发不支持按本人处理日期筛选。日期条件不是对历史某时刻流程状态的快照查询。

结果分别保留 `initiated_at`（提交/发起）、`processed_at`（本人处理）、`workflow_state`、
`current_handlers`、`current_nodes`、`observed_at`、`unavailable_fields`。
当前节点由同一业务身份的流程图、最新节点状态和当前工作项共同核实；
列表中的本人历史节点不作为当前节点，处理人不作为节点名称。流程结束只表示 OA 流程结束，不代表款项已经支付。
跨页及逐项核对不是冻结快照，保留每项读取时间，不能宣称所有状态在同一秒一致。

每次最多读取 1,000 源行、核对 5 个需详情的事项、执行 20 秒；累计最多 10,000 源行、500 个详情、300 秒执行时间。
重查分页锚点也计入读取预算。游标与用户、OA 会话和下游身份绑定，固定保留 30 分钟；重复游标返回原回执。
来源总数/分页/锚点变化、字段无法核实或累计预算耗尽会明确标记部分结果及原因，不省略已收集的行。
工作台提供继续读取、结果前后翻页和刷新恢复；权限/身份失效后清除结果和游标。

计划中的历史报告使用 `oa_history_report.v1` 只读引用投影；不能把报告一页绑定到旧合并转换或业务写入。
模型收到的是紧凑引用；终态计划先用 `replay_cursor` 调用同一续读工具取得当前已缓存页，再按该页 `next_cursor` 取下一页。
即使只有一页且没有下一页，也必须读取当前页；缓存回执不推进查询或重读业务来源。内部完整投影和工作台展示不受模型传输精简影响。
规划目录默认分页摘要，选定条目后按名称和修订读取完整输入、输出、规划契约，不依赖被截断的全目录。

## 一、业务口径

| 能力 | 页面对应 | 日期含义 | OA 查询字段 | OA 返回日期 |
| --- | --- | --- | --- | --- |
| `oa.workflow.done.list` | 已办事项 | 当前用户的处理日期 | `dealDate` | `dealTime` |
| `oa.workflow.sent.list` | 已发事项 | 流程发起日期 | `createDate` | `startDate` |

同一申请上午发起、下午处理，已办应显示下午的处理时间，不能回退成发起时间并声称日期已核实。
跟踪事项是另一集合，本次没有为其新增日期下推。

## 二、统一调用

两项能力接受 `start_date`、`end_date`、`keyword`、`limit`。日期格式为 `YYYY-MM-DD`，上海时区，
两端包含当天，允许只给下界或上界。参数在普通原子查询、CLI/MCP 调用、持久计划中完全相同。

```json
{"start_date":"2026-09-01","end_date":"2026-09-01","limit":1000}
```

日期条件自动下推，只有命中结果需要分页。`keyword` 保留原有“公开字段包含关键词”的语义，
在日期筛选结果中匹配，不能偷偷改成只按标题搜索。`limit` 默认 50、最多 1000，是结果输出上限。
不提供日期时仍只读加载页，不承诺全历史。没有新增按标题或排序参数，未核实的服务端能力不对外宣称支持。

能力 Schema 的 `x-agentbridge-query` 和规划目录的 `sourceContract.queryContract` 提供同一机器可读合同。
外部宿主理解用户日期需求后传公共参数，不需要知道 OA 私有字段。组合计划的昨天、前天、上周分别使用
`previous_day`、`day_before_yesterday`、`previous_calendar_week`，由中央根据原任务受理时间编译；
月份或其他明确范围使用 `absolute_range`。这不是靠提示词关键词触发的专用工作流。

## 三、完整性与预算

- 最多 20 页、每页 50 条、筛选查询循环最多 20 秒；页面加载有独立既有超时。
- 返回 `coverage.serverFilterApplied`、`sourceQueryTotal`、`sourceQueryPages`、`pagesFetched`、`scanBudget`。
- 总数为 0 且元数据有效时，空结果也能证明完整；此时页数可以为 0，但已完成一次查询请求。
- 总数/页数变化、重复事项、日期不符、页长不符、网络中断或预算耗尽均不能证明完整。
- 输出被 `limit` 截断仍为 `partial`，即使服务端命中结果已经全部读取。
- 不依赖“第一页日期看起来有序”推断查全，不自动退回全历史遍历。
- 后续若要生成业务内容并写入，来源必须 `complete`；授权不能替代完整性证据。

## 四、人工核对

1. 在 Workspace 发“看看9月1日我处理过哪些OA事项”。应使用已办按处理日期查询，不读已发/跟踪替代。
2. OA 左侧进入“已办事项”，查询条件选“处理时间”，起止都填相同日期，再查询；核对条数、标题和处理时间列。
3. 在 Workspace 发“9月1日我在OA发起了什么”。OA 左侧进入“已发事项”，选“发起时间”查询同一天。
4. 发“把前天的OA已办和已发合起来看看”。应生成一个只读计划，结果按已办/已发区分，显示完整性。
   如果宿主先误走原子调用，中央要求转入计划时应自动建立补救计划，不要求用户重发。
5. 发“看看7月到8月底我处理过的OA事项”。超过 50 条时应分页读取筛选结果；如最终回答较长可以摘要，但不得篡改工具总数或完整性。
6. 发“把前天的OA已办和已发整理成昨天1小时的工作日志，先让我核对，不提交”。可到可信填单阶段；不授权，不应创建日志。
