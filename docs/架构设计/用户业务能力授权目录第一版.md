# 用户业务能力授权目录第一版

日期：2026-09-23。状态：作为授权改造第一版设计基线，已开始接入运行时；生产部署和真实验收以发布记录为准。

本目录配套[整体设计](./用户能力授权与令牌动态管理整体设计.md)。权限只授予用户，令牌不再保存独立权限。本文冻结业务分组和映射，实施时允许修复映射错误，但新增能力、扩大已有权限的业务含义必须更新目录版本与迁移差异。

## 1. 结论与覆盖范围

第一版共 **54 项用户业务权限**：OA 30 项、照明 11 项、日志系统 4 项、语雀 1 项、独立数据库 8 项。这些是管理员授权单元，不是 54 个新工具，也不意味着每次都要逐项勾选。

静态核对覆盖 110 项注册执行能力、103 个智能体公开工具，以及 39 个未列入公开清单的 MCP 工具（含直接写入口、宿主协议与交互恢复）。独立数据库通过两个动态工具分派，另纳入 8 项可授权能力及下载动作。辅助入口与动态分派均显式列出，不将其错误计为业务权限。

机器可读对照：[用户业务能力授权目录映射](./用户业务能力授权目录映射.json)。该设计附件同时生成运行时权限目录快照；两者必须保持一致。公开工具按实施前 Scope 清单提取，注册能力来自四个纯注册函数，私有工具来自 MCP 装饰器差集。梳理不连接 OA 或数据库，不读取生产凭据，不修改真实授权。

## 2. 划分依据与明确取舍

| 决策 | 原因与边界 |
| --- | --- |
| 流程列表、详情、意见合成流程查询 | 同一业务查询的连贯步骤；不按待办/已办机械拆权限，仍受下游可见性限制 |
| 组织通讯录与私人通讯录分开 | 私人联系人与组织目录的数据用途不同，已有独立执行入口 |
| 查询、下载/导出分开 | 允许查证照不自然等于允许取扫描件；通讯录、数据库与照明导出均有独立授权 |
| 审批按现有 14 类业务区分 | 请假、费用、人事等授权对象不同；通用审批 Scope 太宽，prepare/commit 两阶段则不拆 |
| 草稿按业务类型与提交分开 | 出差、请假、补签已有独立动作；补签没有独立提交能力，不编造一个 |
| 创建会议与申请/取消会议室分开 | 创建会议会产生会议业务记录，会议室申请与取消是不同动作 |
| 照明分 6 类读取、1 项导出、4 类写入 | 列表与分析合并；巡检和维修分开，避免查询巡检就开放维修明细 |
| 照明运行状态包括电测 | 实时状态、召测记录和关灯时段电流属于同类运行诊断；能耗统计单列 |
| 日志系统的本人日志、团队日志、项目检索、创建分开 | 团队数据明显扩大范围，项目检索也可独立使用 |
| 语雀保留 1 项内容读取 | 书库、目录、搜索、正文构成同一使用链；以后可靠支持书库范围时通过资源约束细化 |
| 数据库保持现有 8 项 | 保留 source_id、正文/统计/内容/评论/自由 SQL/导出边界，不重新发明目录 |
| 不新增“批量审批权限” | 批量是执行方式；必须逐项满足对应业务审批权限和原批量确认机制 |

管理界面建议使用“流程查询”“人事审批”“费用及出差审批”“照明查询”等预设，展开为明确权限列表。预设不形成永久通配符；新增业务审批类型不自动进入旧授权。

写权限允许执行该动作必需的目标读取、状态核验和确认摘要，但不授予任意列表/全文查询。若流程显式调用公开查询工具，则必须另外具备该查询权限。预设可把常用查询一起选中，界面必须展示依赖而非后台偷偷扩权。

未授权私人联系人时，不能通过导出、组参数或附件交付取得私人联系人数据。已核实 group_type 支持 private/personal/system/project，private 使用私人联系人行结构，其他三类为组织成员行结构。组列表和组成员入口均动态分派：private 要求私人通讯录读取，其余要求组织通讯录读取。组列表未指定类型时现有适配器会读取全部四类，因而必须同时具有组织和私人两项读取权限；只有其中一项时应显式传入获准的 group_type。不能先读取全部再在模型端过滤。

### 4.3 数据库导出、下载与原文

database.report.export 只能使用当前允许的 query_capability：database.free.read、database.logs.query、database.logs.analyze，并同时要求该原查询能力。database.report.download 归同一导出权限，还需复核原查询能力、source_id 和所有者，不增加一个“下载权限”。

原文读取现有规则为 database.logs.query 或 database.logs.content_analyze 二者之一，按相同 source_id 检查，继续保留。评论分析本身含关联日志正文，这属于该权限已声明的内容范围。

database.free.read 允许数据源全部开放对象，可能取得日志、评论与目录数据。因此这些语义权限不是数据隔离墙：撤销评论分析但保留自由 SQL，不能声称用户看不到评论。需要禁止某类数据时，应调整源开放对象/数据库视图或撤销自由 SQL。界面必须标明这项高级能力的范围。

### 4.4 批量审批、类型识别与模板

oa.workflow.pending.batch.prepare 不单独授权。选择前要求流程查询；冻结候选后，对每项要求该业务类型审批权限。任一选中项未授权则整批准备失败，说明缺失类别，不悄悄跳过后宣称全部完成。提交每个子项前再次检查。

oa.missed_punch.approval.batch.prepare 同属于补签审批；若内部列举待办，还需流程查询。批量次数和参数限制继续沿用受控任务机制。

当前批量选择包含标题识别逻辑。新权限不能把标题当作可信业务类型证明；必须从实际表单/流程契约核验类型，并在准备和提交时一致检查。普通协同审批只用于适配器支持的普通协同契约，不能作为未知表单或其他审批类型的授权兜底。这是拆分审批权限的实施门槛。

oa.template.list 是辅助能力：必须按用户拥有的草稿/提交能力过滤其对应模板。没有可用创建能力时不暴露模板列表；不能因模板入口原为 oa:read 就一并开放其他查询。第一版不增加模板管理权限。

本轮完成的是静态覆盖和业务分组。实施前不必继续泛化探索，但以下改造不能遗漏：

2. 证照、导出文件、缓存 ready 文件、重发及 HTTP 下载都接入来源权限复核。

4. 模板过滤、通讯录组类型及参数分派必须落到真实资源，禁止空泛 Scope 回退。
5. 注册能力 effect=read 不代表低风险：导出仍需独立授权。自由 SQL 的数据范围须明确展示。
6. 使用两用户、同用户两有效令牌、不同资源和跨入口调用验证权限一致；不把代码清单当作线上安全验收。

第一版业务粒度可据此实施。若某个已有入口无法落实上述边界，应阻止该入口切换并记录具体缺口，而不是扩大权限绕过。新增能力必须显式归类，不能按名称前缀自动继承。

## 8. 迁移与验收补充

旧 oa:read 展开为流程查询、证照查询/下载、会议室查询；模板入口改为按实际创建权限过滤，这一行为收紧要进入迁移差异，不能宣称完全等价。oa:read:addressbook 展开为组织读取、私人读取和导出；其他 Scope 按第三节逐项展开。

同用户不同旧令牌 Scope 仍按整体设计处理差异，不自动并集。依赖新增造成的行为差异必须列明，例如旧只具备审批权限却可由批量入口内部读取待办的情况；不能自动补授全部流程查询。

验收重点：只有组织通讯录权限无法导出私人联系人；只有请假审批无法借批量或普通协同审批费用；只有照明导出无法选择未获准领域；只有证照查询无法通过旧下载链接取得文件；撤销后缓存/历史结果不能绕过；数据库自由 SQL 的高级范围与界面描述一致。

运行策略已实现：46 项非数据库权限按用户配置，数据库保持原有独立授权；模板按固定模板与表单标识过滤，普通协同要求明确的 HTML 正文类型及无表单标识。下载按证照、通讯录、照明报表分别检查来源权限；原凭证续期不变更密钥。生产迁移与真实验收以发布记录为准。
