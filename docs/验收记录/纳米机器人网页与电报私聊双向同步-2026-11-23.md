# NanoBot 网页与 Telegram 私聊的双向同步

## 范围与起点

第一账号希望在 NanoBot 网页与绑定的 NanoBot Bot 两端看到同一轮普通问答。15:27，独立 Bot 收到该用户的私聊并成功回复，中央聊天时间线没有这两个角色的消息。15:29，NanoBot 网页完成一轮问答，两个 Bot 的聊天投递均为零。15:30，OpenClaw 网页的一问一答则由原 OpenClaw Bot 成功送达。两套 Bot 使用各自的端点与消费者，NanoBot 私聊的发送者、Bot 和 Web 绑定匹配。

15:34 起核对生产账本及部署代码，发现 NanoBot 入站对话只记录在 Bot 与 SDK 的本机账本，未写入 Workspace 读取的中央时间线。反向链路中，中央未为 NanoBot 普通聊天建立出站投递，消费者只处理原私聊任务的终态。用户已确认对今后的普通问答启用双向同步。改动涉及中央时间线、通知队列、已配对的个人端点和 NanoBot 消费者。

## 验收场景

- 第一账号从 NanoBot 网页或其 Telegram 私聊发起一轮普通问答，对端按用户、助手角色各出现一次，刷新、重复更新或重启不会造成重复回复、投递或模型调用。
- 只使用经过核验的本人、同一宿主实例、同一 Bot 私聊。原 OpenClaw Bot 保持原路由，第二账号没有 Telegram 端。撤权、失效、换绑与来源不符均阻止投递。
- 只镜像本次启用后的普通公开聊天文本。原任务、登录卡、业务授权、私有链接、文件和发送结果未知的处理仍按原专用流程。普通消息不唤起新一轮模型，不回补双方既往聊天。
- 隔离环境通过真实 Workspace 页面和合成 Telegram 收件方核对两个方向、身份边界和重试。正式发布后以真实网页回执、Telegram 官方消息回执和中央账本交叉核对。

## 隔离验证

15:42–15:44，Chrome 扩展连接真实 Workspace、中央 MCP 和 NanoBot SDK，Telegram API、模型及下游为本机模拟。没有发过私聊消息的已绑定测试账号在网页提问后，专属 Bot 分别收到“你”和“智能体”两条记录。再从该 Bot 普通私聊发问，网页实时显示一问一答。重送同一更新、重启消费者并刷新网页后，两轮问答的四条记录各出现一次，SDK 只有两次运行；另一个账号和切换至 OpenClaw 的页面均没有这四条内容。

15:50 又从隔离私聊触发一条含中文及 emoji 的长答复，模拟 Telegram 收到两段并分别确认，网页收到一条有完整首尾的答复。专项覆盖发送前撤权、同一账号重新配对、领取时版本兼容、第二段应答丢失、确认一段后重启，以及受保护的卡片或文件。普通文本沿用中央聊天单条 50,000 字符的上限，Telegram 出站以每段最多 4,096 个 UTF-16 单元处理。
