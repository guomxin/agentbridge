# 工作台同步第三批中央与图片定向验证（2026-11-27）

## 范围与约束

本记录对应[四批实施方案](../后续规划/工作台与电报同步分批实施方案-2026-11-27.md)第三批的中央与 Pi 资源子项，覆盖 D08 / S08 并配合 D14 / S14。独立分支 `codex/workspace-sync-batch3-common-pi` 从第二批公共层 `93faafd5` 开始；前两批满足各自验收后才允许审查合入。

- 用户问题：图文问题、附件和公开终答应在本人同宿主两端独立同步，逐件可追溯；不能因一个附件失败而隐藏其余公开文字。
- 已确认原因：Workspace 有附件的准入把整轮排除在文字配对固定和新出站账本之外；Pi 原图结算始终要求当前配对，发送后撤配时原次回执无法补账。
- 待验证：Telegram 入站资源只留文字是否导致原件无法在本人 Workspace 查阅；现有文件授权、类型/大小、期限、顺序和逐件回执是否在双向路径一致执行。
- 预期行为：公开文字与受控资源分别投影；资源按原请求、用户、宿主实例及配对代次固定；发送前核对原件、期限和权限；未知不重放；原次迟到确认只补账不授权新发送。
- 模块：中央 Workspace 准入、文字投递与资源引用；Pi 专属原图发送与回执；原有产物权限检查。共享 NanoBot/Pi handler 的文件修改先协调，避免覆盖第二批正在进行的历史/文字修正。
- 安全边界：技能草稿/试用、可信材料及接续授权仍隔离；不公开受保护 CSV；不延长原资源期限；不按模型文本猜测文件来源；保留 `prepare -> authorize -> commit -> verify`；不操作真实 TG、OA、配对或发布环境。
- 验收：三宿主公共文字隔离，Pi 图文/纯图/多图/顺序，已发送/未知/部分失败、撤配后迟到回执、过期/越权/错误内容摘要、正文与附件独立；文档与其他产物类型逐项写明支持策略和未测边界。开发阶段使用独立 home/数据库/端口及合成资源。

## 执行与证据

反向媒体接口已与共享消费者负责人划分：中央模块、存储、Workspace 附件映射与渲染以及 Pi 私有包装由本分支负责；共享 `telegram_media` / `telegram_timeline` / 消费者和 Nano 私有入口由另一分支负责。依赖第二批独立接收事实，首次接收先固定原消息、原配对及平台时间，下载和模型接纳不能替换该身份。每件按原消息与序号固定摘要、类型、名称、大小和七日期限，caption 单独投影；明确不支持、读取失败、过大、过期有固定占位。原次响应丢失只取得相同回执，撤配后不接受新件；已成功与失败件互斥、不可替换。文档类型仅沿用宿主已有允许类型，下载强制附件，不内联可执行文本，不触及业务产物授权。

已实现的独立子项如下，均未合入主候选或发布。

1. Workspace 附件问题使用原准入事务固定当前文字目的端；caption、公开终答和安全运行终态独立入文字账本。图片过期不吞掉文字，文本中不拼接资源地址。技能试用、可信材料及接续隔离保持。
2. Pi 中央原图账本在新记录中固定个人令牌标识和端点键。只有原用户、实例、端点、配对代次、投递及次数均匹配的 ACK 可以在撤配后结算；读取、认领和发送许可仍要求当前配对。旧记录不回填新身份，不获得撤配后补账权限。
3. Pi 实际私有 claim 入口持久保存原网页路由、私聊绑定及个人凭据摘要；原次 ACK 通过单独只结算入口处理，不查询当前配对、不返回图片、不发起新的发送。消费者本地冻结原次平台回执和绑定，重启后可在恢复函数中补账。该函数每轮至多处理四条，失败下次最早五秒后尝试。
4. 中央反向媒体先固定原私聊消息、个人身份、当前配对和平台接收时间，再逐件接收原字节或固定失败占位。相同消息与序号的元数据不可替换；原回执可在撤配或过期后补取，不恢复文件、不新增原件。首次消息不能早于个人令牌或明确配对授权生效时间（按 Telegram 秒精度比较），端点懒创建时间不当作授权起点。
5. 图片及既有宿主白名单内的文档按原接收时间保留七天；单件 6 MiB、每条消息 12 MiB、最多四件。工作台图像预览与文档下载分别呈现，失败占位固定文案，文档不内联 HTML 或 PDF。收到的私聊原件只能从登录后的工作台下载并复核原配对，不能借匿名图片路径读取。
6. 三宿主统一 `workspace_media_v2` 出站：领取时显式协商 `include_workspace_media_v2`；每件固定原请求、原消息与序号、名称、类型、字节摘要及期限，单独 issue / begin / ACK。issue 返回认证通道内原字节、许可截止和资源截止；begin 再验当前配对、期限和原字节。原图作为文件发送，未知不重放、明确限流按服务端时刻重试，失败不吞后续原件与文字。只接管从未认领的旧项；旧 Pi 认领过的原图仍由旧消费者处理，旧 OpenClaw 多图通知认领过后不猜测其中剩余原件。未新增自动迁移旧历史。

扩大到三宿主时，首轮 65 项中 Pi 新场景失败（其余 64 项通过）。原因是旧 Pi 夹具的 FakeGateway 只有占位网页令牌，而私聊另发了有效合成身份；新的附件准入要求同一网页身份，门禁正确拒绝。通过正常端点登记为夹具网页绑定同一有效合成身份后，三宿主专项通过，产品门禁未放宽。定位阶段的失败收据保留，包括 `native-test-c2102b64516e4d48ad7de8d9b7f14178.json`。

`validate --changed` 按核心及身份链路影响返回 `full_required`。以上均为独立分支的开发验证，未生成正式发布资格；集成候选仍须走既有 Full、wheel 和实际版本登记门禁。

仍需完成的第三批子项及边界：

- 在共享 Telegram 消费者的首轮读取及当前配对发现前接入 `pi_workspace_images.recover_receipts(pilot)`。此处由共享消费者负责人在第二批收尾后接入；当前直接恢复函数已验证，不把它算作启动自动恢复完成。
- 中央反向媒体与工作台映射已实现；共享消费者及 Pi 私有挂接仍待独立分支集成。未把中央定向等同于三宿主双向附件完成。
- Workspace 原图仍遵守 JPEG / PNG / WebP 的既有上传策略。反向用户自行发送的文档仅沿用宿主已有白名单；受保护 CSV 和业务生成产物继续使用原业务授权，不自动进入上传原图队列。
- 宿主已冻结成功下载的原件元数据、中央却始终未接收，直到原七日期限结束时，只保留本地过期状态、清理暂存原字节及独立 caption；不能把同一原件改为另一失败元数据，也不能虚构中央已接收附件。该边界尚无额外中央状态事件。
- 图片 begin 成功但本地发送日志尚未落盘即崩溃，仍保守按未知处理并停止重发；没有把这段窗口声称为零丢失。
