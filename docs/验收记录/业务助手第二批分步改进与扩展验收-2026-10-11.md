## 第一步：按模式贯通评测和审批

服务端统一计算当前修订和内容哈希的发布依据。新报告完整核对每个样例、重复次数与断言结果，输出检查按模式归属，触发检查是共享门槛。旧报告仍保守使用整体结果，不拼接多份报告。明确失败不能被人工样例覆盖；仅人工样例的申请模式要求审批人说明验证方法，即使别的模式已有独立报告也不例外。申请冻结本次所选模式和证据，审批不读取之后的新评测。

Chrome 扩展在独立 Workspace 登录合成账户，实际输入“整理成周报：完成联调，计划下周上线。”，分别评测 preview 和 fill。preview 检查“联调、计划、未说明”；fill 故意要求无关的“验收失败标记”，用于验证失败门槛，不能把它记为模型业务能力缺陷。四次真实 `openai/gpt-5.5` 无工具调用完成。候选 preview 通过，fill 失败；无助手 preview 未包含约定的“未说明”，本次也未通过。仅说明这组具体断言结果，不推导总体质量提升。

页面禁用 fill、只勾选 preview；用“先发布预览，填单稍后完善。”提交。扩展登录独立管理控制台，核对完整方法、使用范围和四项输出，批准仅 preview 的合成申请。服务端只读复核申请和最终发布包的模式均只有 preview，状态 published、版本 1.0.0。此发布只作用于本地隔离合成账户，非生产部署。

实际查看发现同题结果缺少模式标签会混淆，已补充 Workspace 和审批页的每项模式标签，并重新通过扩展查看。截图：`step1-mode-publication.png`、`step1-review-evidence.png`、`step1-published.png`。Workspace 未记录前端 JavaScript 错误。

## 第四步：把一次纠错变成可复用验收

复用现有评测任务的 cases/repeats，不增加样例平台或新的评测服务。“用上次样例重测”仅恢复题目和断言，明确标注原修订，不带入旧通过结论。真实试用可转成可编辑样例，反馈只显示为参考，不自动填成验收条件；用户启动评测后，样例才随任务保存。

反馈支持从自己的试用或历史绑定确定原模式、版本、修订和内容哈希。没有来源的目录反馈必须明确选择可用模式；旧反馈的未知模式不猜测。原七列 skill_feedback 表保持不变，来源信息置于附属 context 表，兼容旧写入方。

Chrome 扩展在修订 2 的真实样例上选择“结果有误”，填写“完成项也标明日期未说明。”，再点“转成验收样例”。页面保留原材料“完成联调，计划下周上线。”和 preview 模式，期望内容仍为空，由人工填写“联调”“计划”“完成日期：未说明”。

修订 2 候选为 0/1，不使用助手为 0/1：实际候选已写“联调（日期：未说明）”，但未满足约定的具体字段格式。这里检验的是文字格式约定，不能据此认定总体语义错误。已有人工样例没有覆盖这次明确失败，发布模式被禁用。

将方法改为明确要求“完成项必须单独列完成日期；未给日期时写‘完成日期：未说明’”，保存为修订 3。点击“用上次样例重测”，页面显示来自修订 2；同一材料、同一组断言和重复次数，重新运行后候选 1/1、不使用助手 0/1，preview 重新满足本次发布条件。旧反馈仍准确属于修订 2。没有实际发布此修订。

只读 DB 核对六项一致性均通过：试用来源、原修订/模式/哈希、两轮输入相同、两轮结果分别归属；报告本身不额外保存 feedback_id，转样例动作由扩展记录证明。证据：step4-feedback-regression-evidence.json、step4-before-fix.png、step4-after-fix.png。目录反馈未选模式时真实提示选择具体模式；选 preview 后可填写，本次没有保存额外目录反馈。
