# 工作台并列宿主与 NanoBot 试点验收

本记录跟踪[工作台并列智能体宿主与默认实例设计](../架构设计/工作台并列智能体宿主与默认实例设计.md)的五批实施。开发起点为 2026 年 11 月 23 日的主线 `49ca538`，在独立工作树保护原有用户草稿。主线已有 OA 每日简报、事项关注、任务搜索和历史核验，相关入口须保留原账号与任务归属。

## 第一批试验范围

目标是用真正的 NanoBot 0.4.2 SDK 连接隔离的中央 MCP，验证两名合成用户的权限、宿主私有材料的交付和运行恢复。待验证的是 SDK 公开接口能否在模型外分离私有交互，并在调用方掉线后保留原受理记录。涉及独立宿主适配器、测试模型、合成下游和仅回环可访问的验收页面。生产下游、真实消息渠道与生产凭据均不参与首批试验。

验收入口为 Chrome 扩展。通过页面实际提交请求，核对工具调用记录、公开结果及属于本人端点的私有展示；切换测试身份、刷新、模拟受理回执丢失和重启后核对原运行及执行次数。浏览器操作、真实 SDK 与 MCP、模拟模型、合成业务各自记录证据。后续涉及真实业务写入时仍走针对该事项的授权与核验流程。

11 月 23 日 10:17 起，基线核验、Chrome 扩展连接、隔离宿主安装与测试夹具准备并行。已通过扩展列出标签页，在独立 Python 3.12 环境导入 NanoBot 0.4.2 的 `from_config` 及 `run_streamed`。批次结果以实际页面与账本验收为准。

11 月 23 日 10:25，Chrome 扩展在回环验收页核对实际 SDK 和中央 MCP。甲的页面故意丢弃接单响应（503），重试原键取得同一条运行，SDK 启动一次、待办查询一次，返回两项合成业务记录。暂停观察、刷新后结果仍在。乙查询甲的运行得到 404，本人查询显示未授权，中央待办执行计数为零。两人各自的私有标记只到本人绑定的合成接收器，模型请求、磁盘与重开的历史通过隔离检查。第二次甲查询在 SDK 已返回、账本仍为 accepted 时重启协调器，终态进入 unknown；再次重试原键后 SDK 启动次数仍为 1，甲的累计待办查询次数仍为 2。页面用于核验合成私有接收器的投递记录，生产卡片呈现留在第三批核验。

## 第二批实施范围

本批实现管理员登记的实例、按主体开放和账号默认设置、原请求及历史的实例归属、Workspace 发起及恢复。沿用 SQLite 事务、原中央端点和旧会话；分别覆盖两个账号、双标签并发、重试、撤权和实例失联。经用户确认，生产灰度向现有两个具体 Workspace 账号开放，维持两人现有默认选择与业务权限。以 Telegram 专用 Bot 验证渠道纵切，微信延期。

11 月 23 日 10:33–10:38，Chrome 扩展在隔离管理台看到了两个具体主体的开放范围和独立绑定。在两个实际 Workspace 页面，甲默认 OpenClaw，乙默认 NanoBot。甲在另一标签页更改设置后，旧页发送得到版本冲突，提示更新宿主并保留草稿。相同的 OA 待办表达曾进入写死 OpenClaw 的快捷路径，修正后由实际 NanoBot SDK 处理，甲看到采购和验收两项合成待办，乙收到权限不足。旧 OpenClaw 路径使用隔离 Gateway 应答器。另以候选事务测试覆盖旧键切换后仍找回原派发、不同载荷冲突、按端点隔离历史，以及继续任务使用原实例。

## 第三批可信交互

目标为私有凭据卡、业务输入卡、执行授权、权威回读与原任务续办。11 月 23 日 10:46–10:48，在 Chrome 中发送过期会话的待办查询，页面出现“打开可信卡”，刷新仍可恢复。乙在隔离入口访问甲的挑战得到 404。甲通过回环验收桥打开对应挑战的真实可信办理表单，用合成材料登录，页面显示“认证完成”，原 NanoBot 运行继续返回两项合成待办。SDK 探针核对挑战只续办一次，模型输入和宿主状态文件均未含私有卡 URL。隔离浏览器本次通过回环验收桥进入表单；部署域名下从按钮直接打开 HTTPS 签发页仍待核验。此记录覆盖凭据卡。

## 第四批 Telegram、技能与文件

11 月 23 日 10:42–10:44，通过 Chrome 扩展分别操作两人的合成 Telegram 私聊。真实渠道消费器、真实 NanoBot SDK 和中央 MCP 处理同一问题，甲收到两项待办，乙收到权限不足；双方分别尝试读取对方的原运行均被拒。重复 Telegram 消息并重启渠道后，已送达的两条甲消息各只有一次 Bot API 发送；一条受理未知的消息发送次数为零，另一条投递未知的消息发送次数保持一次。此处 Telegram API、模型和业务数据均为隔离替身。真实 Telegram 仅完成官方 Bot 身份和现有 webhook 状态的只读核对。

## 第五批运行预检与故障演练

11 月 23 日 10:48 起在隔离管理台检查 NanoBot 实际就绪，通过页面停止新接单；另一宿主仍返回答复，随后从管理台恢复接单。第一次演练发现停止实例时历史补充会提示错误，已将该路径改为读取原账号公开的本地历史，11:05 通过浏览器复验。用独立模型身份在受管 Mac 上完成 NanoBot 原生 OAuth，官方模型服务对无业务数据、无工具请求以 3.71 秒返回预期固定答复。Linux 的独立模型访问预检被提供商以地区错误拒绝。生产候选拟将独立宿主部署在项目受管的 Mac 上，中央仍在 Linux，沿用正式发布入口。上述预检与演练均在生产启用前完成。

11 月 23 日 11:03–11:04，另开隔离受控写环境。甲经真实 Workspace 请求保存请假草稿，刷新后原卡仍可恢复；乙访问甲的办理入口为 404。甲在合成可信表单填入未来同日的起止时间与事由，预览明确显示“仅保存待发草稿”。点击确认后，页面先显示“已授权，等待执行”，随后原 Workspace 展示“业务结果已核验”及草稿保存成功。额外协议试验在越过写入边界后丢弃回包，中央保留 outcome_unknown，同键重试仍是原 run，隔离下游账本仅一笔。此轮没有创建真实 OA 草稿或发起真实审批。

11 月 23 日 11:04–11:05，两个隔离主体经真实 NanoBot SDK 与 OpenAI 兼容模型传输各自的一张合成 PNG。模型端逐字节核验红、蓝像素，两次同键重发均找回原运行，各自下一条纯文本请求未夹带旧图；宿主生成的图片暂存和 SDK 内联图像副本已清理。中央仍管理原附件的到期和下载。浏览器复测停止接单时，NanoBot 历史仍展示原会话的公开答复与宿主名；旧 OpenClaw 消息未进入该会话，恢复接单成功。

生产模型授权已由用户在官方页面完成。受管 Mac 实际用于启动服务的解释器已通过无弹窗的钥匙串读入与 Bot 身份核验；运行服务与原有 OpenClaw Bot 凭据独立。中央生产只读盘点确认两个活动账号中，一个已有可核验的原 Telegram 私聊绑定，另一个需要在登录 Workspace 后关联本人的试点私聊。

## 跨端复验与运行恢复

11 月 23 日 11:08–11:24，甲的隔离 Workspace 复用现有私聊身份，乙在本人 Workspace 发起关联、在合成 Telegram 私聊领取验证码，再回 Workspace 完成确认。乙通过自己的私聊查询时得到与中央权限一致的拒绝。真实的 NanoBot SDK 另以合成 Telegram 发起请假草稿，中央原任务记录的起点为该 Telegram 端点，甲通过同实例的本人 Workspace 授权；原私聊得到权威回读后的结果，下游仅一笔草稿。

11:17–11:26 的 Chrome 复测覆盖同一会话连续两轮工作日志技能、私有草稿试用和图片预览。两轮均按固定版本的预览模式返回合成待办，尝试变更模式被拒绝。短试用按原修订保存独立样例，页面提示待人工复核。新上传的 69 字节 PNG 可在历史中放大，模型返回与原图一致的字节数及摘要。期间修正了试用请求携带多余私有字段、隔离验收页的媒体地址，以及测试模型跨轮复用工具调用标识的问题。生产宿主遇到模型错误时，也已通过真正的 SDK 验证普通对话不显示提供商诊断正文。

11:09–11:24 在 Chrome 对两种中断分别重启原宿主与工作进程。中央已有权威回读的一笔草稿在原 Workspace 恢复为已核验；写后丢回执的一笔在进程确实停止、重新启动并再观察后，中央仍记未知，合成账本仍仅一笔。首次未知用例的模拟模型在同会话重复使用调用标识，未按预期停机；最终复验使用修正过的夹具，并实际核对端口离线、进程重启、中央状态及写入数。

试点模型与 Telegram 身份配置、数据库结构迁移和正式备份同时只读预检。候选隔离启动只变更中央业务数据库，另外三库结构保持一致。已有一份恢复包重算校验和与清单相符；生产发布时仍须生成本次发布的恢复点。

11:32–11:38，从真实 SDK 查询产生的 NanoBot 原任务选择一项合成待办。即使账号已切回 OpenClaw，中央仍在原端点给 NanoBot 创建准备命令和协调租约。同一选择重复返回原任务：一份待确认材料、零笔下游写入。Chrome 显示该事项由“可新办”转为“已有办理，等待确认”，原结果卡的“重新查询待办”另行受理。真实 CLI 的装配测试还核对原 Gateway 与追加的宿主连接同时进入工作台。

生产 Workspace 的 HTTPS 首页已在 Chrome 通过现有登录打开。此为发布前基线，实例下拉框及 NanoBot 的生产页面验收须在正式事务完成后另行核对。
