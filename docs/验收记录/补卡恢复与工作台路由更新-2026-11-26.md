# Pi 自动补卡与 Workspace 路由更新

11 月 26 日 13:26，合并 Pi 的两项修复，适配器从 0.1.1 升至 0.1.2，沿用 SDK 1.6.0、两个个人网页绑定和第一账号的 Telegram Bot。核对到生产前驱为 `e33706b8df54`，Pi 目录已启用，修订为 4。

## 缺陷与修复

0.1.1 的消费者先保存普通答复的送达状态，再尝试取一次结果卡。签发响应超时后，记录中没有待补卡事项，后续轮询或进程重启都无法继续。旧候选的隔离实测曾在中央签发后延迟 10.25 秒返回时复现；生产第一次漏卡没有传输错误码，具体触发原因仍未确定。[上一版生产与复现记录](./第三宿主生产结果卡修复-2026-11-26.md)

0.1.2 在保存普通答复前持久登记取卡请求。消费者在原任务上重新核对绑定和来源有效期，在五分钟期限内最多尝试四次。Telegram 发送结果未知时保留原投递记录。已有历史答复沿用旧记录，用户仍可按原任务找回有效结果。[补卡实现](../../integrations/nanobot-agentbridge/nanobot_agentbridge/telegram_result_cards.py) · [中断和去重用例](../../tests/test_pi_telegram_result_cards.py)

此前长时间运行的 Workspace 缓存了启动时的 Pi 路由。切换版本后，中央目录和宿主已更新，但网页查询仍可能按旧版本发起。新版本在派发与恢复时按当前账号绑定解析部署路由；受理结果不明的任务保持原幂等键对账。[路由实现](../../agentbridge/workspace/nanobot_gateway.py) · [正向切换、回退和未知受理用例](../../tests/test_pi_workspace.py)

## 验收范围

先在隔离中央延迟一次取卡响应，用第一账号真实 Telegram 桌面端观察同一查询的普通答复和补发卡，对照原任务、签发次数及唯一投递回执。再保持同一 Workspace 进程运行，用 Chrome 扩展核对两个独立账号在旧版本的就绪状态，并在切换后各发一条新的本人待办查询。候选通过后由原生发布入口部署。生产只读查询按账号串行，验收结束恢复原默认宿主。

13:31–13:41，第一轮 Full 发现发布测试将 Pi 的临时路由环境变量留给了下一条中央 CLI 测试，导致后者多发现一个宿主。按原顺序可复现，隔离两种宿主的环境变量后，35 项相关测试通过。修正后的候选 `02961f92048a` 通过 Full、11 组正式 Pi 契约探针、L3 归档及独立真实模型调用。归档轮询演练在隔离中央把第一次签发响应延迟约 50 秒；重建消费者后同一任务取卡两次，合成 OA 读一次、普通答复一次、结果卡一次，另有一条独立状态通知。此轮 Telegram 传输为模拟。

用户已批准为 0.1.2 打开独立维护窗口。现有桌面验收仅能在生产 Pi 以正式入口停用后独占原 Bot。回退会暂时撤销两枚宿主凭据；桌面实测后先恢复已上线的 0.1.1、签发两枚新凭据，核对原网页绑定与首账号配对，再用实际目录修订固定 0.1.2 的升级输入。两次版本活动均需保留原投递账本和未知结果。

13:42–13:54，核对到 GitHub 主分支已在生产提交之后增加一项纯文档提交，旧的常规发布入口在恢复宿主后还会尝试把旧提交推向主分支。生产保持运行期间验证了同版本恢复入口。独立旧源码的 Full 通过，重建 wheel 与已安装 wheel 的全体成员（含 RECORD）、类型与内容相同，ZIP 打包时刻不同。恢复使用已上线的原 wheel，并以原 L3 资格、中央部署摘要及隔离启动该制品的真实 worker 交叉核对。
