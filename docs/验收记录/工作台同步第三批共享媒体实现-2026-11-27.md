# 工作台同步第三批共享媒体实现

## 实现范围

对应[第三批计划](../后续规划/工作台与电报同步分批实施方案-2026-11-27.md#第-3-批图文附件和逐件文件)。本子项处理 NanoBot/Pi 共享 Telegram 入站的公开 caption、完整请求摘要和受控原附件；中央逐件媒体账本与 Workspace 资源类型策略由并行公共层子项负责，两个工作树文件范围独立。没有操作真实 Telegram、浏览器或生产运行环境。

代码确认 NanoBot 完整请求摘要含附件身份，历史比较却只计算纯文字摘要，导致有效媒体 caption 无法通过原 run 校验。共享媒体入口还在附件成功读取后才排队文字，下载失败可连带丢失 caption。当前反向时间线只保存说明文字，没有原件受控引用。

预期行为是独立记录原私聊接收的公开文字，完整请求幂等摘要继续覆盖 caption、附件类型、字节及顺序；模型接纳不作为接收事实前提。每件获准媒体进入中央受主体校验的资源存储，保持原接收时间和材料期限。图片、文档、失败占位分别遵守既有策略；可信卡和受保护业务 CSV 不借此扩大访问。

涉及共享 `telegram_media`、`telegram_timeline`、`telegram`、新增媒体私有源/回执 helper、NanoBot server/run ledger 与定向测试。Pi 专用 channel Delivery 和中央 `telegram_media_receipts` 由另一子项维护。旧在途记录不补造新证明；未知宿主/配对/凭据不得回退。

## 安全与验收门槛

- 仅原私聊已验证 sender；拒绝转发、引用命令和来自附件内容的授权指令。
- 下载固定 Telegram 文件来源，不跟随重定向、不从 caption 抽取 URL。
- 下载前固定原 message、配对代次与接收时间；字节就绪后固定 ordinal、类型、名称、大小、摘要和原期限。同 slot 异载荷冲突，失败与成功不可互换。
- caption、原件和终答独立。撤配后原凭据只补已有回执；未接收的字节不重新建立授权，不延长时效。
- 分别验证同附件不同 caption、同 caption 不同附件/顺序、Unicode、空 caption、混合类型、超限/到期/撤权、丢回执、重启及一个附件失败后的公开答复。隔离完整链通过后再安排固定候选真实双端验收。

## 实现与隔离证据

共享入站新增原消息来源与逐件回执私有路由。`agentbridge_host_telegram_media_source` 固定原私聊、平台秒级时间和配对证明；`agentbridge_host_telegram_media_append` 只按冻结 manifest 保存或补原回执。caption 在下载之前独立排队；下载失败、模型接纳未知和进程重启都不重做模型请求。已落地但丢失回执的原件先探原 manifest，再决定是否补同字节。每件最多 24 次有界恢复；到期清除暂存字节，不重新下载、不续期。

NanoBot 新 run 在完整请求摘要之外保存独立的公开文字摘要，用于原 caption 的历史核验。完整摘要继续校验原文字、附件字节、名称与顺序。旧媒体 run 不补造文字证明。实际 Nano HTTP 接口、run ledger 和历史私有 handler 联合测试通过；该测试替换了未调用的 SDK/card 导入和模型执行，不代表真实 SDK 资格已经完成。

共享出站接入 `workspace_media_v2`：新 `telegram-workspace-media-v2` 私有路由复用现有 claim、原凭据回执、唯一 begin 和持久发送账本；逐件验证原名称、类型、尺寸、摘要及期限后通过 `sendDocument` 投递。明确 429 可按原等待期和新 attempt 重领，明确拒绝停止，未知发送不重放。旧 Pi 原图在途仍走原协议；其仅补回执钩子在发现当前配对之前执行。现有 Workspace 上传只含 JPEG/PNG/WebP，受保护业务文件不自动进入此上传队列。
