# 图文入队源端身份修复

日期：2026 年 11 月 27 日。基线：`5f72623e7ad9`。本记录只覆盖一次产品缺陷修复，不替代四批总验收。

## 范围与安全边界

生产本人 NanoBot 的 Workspace 图片请求及公开答复已经完成，但图文入队选择记为 `unpaired`，原件和两条文字均无投递；同一 Web 端点此前普通 OA 查询正常。只读对账确认 Web 端点使用工作台身份，Telegram 端点使用当前已登记的个人 MCP 身份。媒体专用候选预检错误地要求前者匹配宿主注册；普通文字后续校验则使用正确的目标身份。

预期行为：保持 Web 原账号、实例和部署绑定验证，在原 Telegram 目标上校验当前受信宿主注册和配对，再冻结新图文请求的目标。不得将 Web 身份提升为 MCP 身份，不更改配对、凭据或路由，不补发旧 `unpaired` 样本，不重放已确认或未知投递。

修改范围为 `workspace_query_delivery` 的媒体候选选择及独立专项。测试以两个主体、独立临时数据库、真实 Workspace HTTP 登录和公开上传接口覆盖 NanoBot/Pi，模型与平台使用明确替身。验证原件、caption、原公开答复独立入账；跨主体、错误目标令牌、撤配、源绑定变化和旧请求不追认。保留中央发送许可及回执协议。

## 验证记录

修复仅将候选阶段的注册检查限定到原主体和实例，不再使用 Web 端点令牌；之后仍由原 `_pin_destination` 检查精确 Telegram 端点的已登记令牌，并由 `pair` 检查当前原绑定。没有修改数据库结构、身份、配对或发送协议。

新增真实回环 HTTP `/api/login` → `/api/chat/send-stream` 测试，认证、CSRF、原始上传校验与原子入队全部使用产品实现，仅停止模型执行及等待流。NanoBot/Pi 正例在修复前均因零投递失败（2.53 秒）；修复后新增 12 项通过（10.11 秒）。覆盖每条原件和两条文字的独立唯一发送许可/正回执、重复原请求、第二 Workspace 主体、未登记与其他主体令牌、撤销目标、发送前源绑定变更，以及旧未配对请求不追认。平台回执是测试输入，不是真实 Telegram 回执。

此前专项将 Pi 的 Web 令牌重写为宿主 MCP 令牌，NanoBot 旧配对夹具也共用同一令牌，因而漏掉了正式工作台身份与宿主身份分离的情况。本次新专项保留 Pi 正常部署产生的 Web 占位身份，并使 NanoBot 旧夹具按同样语义分离；不修改旧夹具来隐藏差异。

`validate --changed` 于北京时间 21:46:45 正确判定 `full_required`。随后官方定向入口覆盖新增专项、逐件媒体、带图文字、查询投影、NanoBot 普通镜像、Pi 旧原图消费者和文档，于 21:47:11 完成：63 项、2,075 个文档子项通过，19.05 秒。开发测试不作为 Full 收据。

生产 Pi 后续对照也在原请求入队时记录 `unpaired`，与同一公共代码路径吻合；两个旧生产样本保持原状。正式候选 Full、实际 Chrome 及发布后新的受控样本由主任务串行验收；本记录不预记通过。
