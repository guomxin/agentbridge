# Pi 办理与同步性能分批优化

## 范围与生产基线

用户要求按办理启动、Telegram 同步、确认后续办三个优先级分批优化，每批使用 Chrome 扩展及第一账号 Telegram 桌面验收，比较同场景前后耗时，通过后发布并做生产只读复验。相同范围的短维护沿用现有持续授权。

起点为 Pi 0.1.4，生产提交 `8416b6d19edb`，开发基线为 `10964bfee150`。第一账号 21:14 的业务结算从 Telegram 结果卡发起，21:16 的补卡从 Workspace 发起，两笔均在 Telegram 确认授权。两笔引用同一网页待办查询，各执行一次审批并在第一次独立回读核实业务结果。

| 中央事件区间 | 业务结算 | 补卡 |
| --- | ---: | ---: |
| 任务创建至准备开始 | 11.70 秒 | 14.65 秒 |
| 首次准备执行 | 6.03 秒 | 5.15 秒 |
| 材料提交入账至审批执行开始 | 16.65 秒 | 6.96 秒 |
| 审批执行至核验成功入账 | 11.07 秒 | 9.34 秒 |
| 成功事件至 Telegram 投递确认 | 10.69 秒 | 7.73 秒 |

原查询的结果卡入队至投递确认耗时 17.89 秒。材料从创建到提交的区间包含用户阅读、操作和服务端处理。生产未持久化客户端点按、绘制与各次 MCP 往返的精确时刻，逐步优化须补充同条件隔离计时。

## 批次与安全边界

第一批精简固定办理命令接收与启动。检查 Pi 个人控制连接、共享 CommandQueue、受控协调器的冷启动及工具目录枚举。复用 NanoBot 的隔离会话池和当次身份响应，保持原主体、实例、端点、会话、配对代次、受控契约、原命令及协调租约核验。模型工具目录按实际调用者需要保留。

第二批缩短 Telegram 通知等待。对照单轮入站、领取、静默事件确认、可见发送及可选附件的串行成本，优先复用既有通知唤醒、持久发件箱和消息回执。发送前实时身份与配对复核、单一 Bot 发送顺序、原投递与尝试次数绑定、已知成功去重和未知发送结果不重放继续生效。

第三批缩短确认后续办。参照 OpenClaw 对完整原任务证据的复用，仅在同次权威回包具有完整匹配的任务版本、操作与交互集合时减少重复观察。等待结束或绑定变化后重新核验，保持原子授权消费、材料有效期、原协调租约、提交前占用与权威业务核验。

## 验收与发布安排

每批先进行定向测试和隔离页面验收，再固定干净候选完成 Full、wheel、Pi L3 与真实端点资格，走唯一发布入口。共用实现的变更追加 NanoBot 和 Reference-Host 回归。每批独立记录开始、结束及返工原因。

代表性场景覆盖网页与 Telegram 结果选择后的原任务办理、字段与授权确认、登录恢复、空结果、第二账号隔离、撤权或换绑、超时和恢复、未知结果不重放。合成 OA 用于完整办理与前后耗时比较。真实生产只读复验核对本人查询、唯一问答和卡片、原任务来源、零勾选及账号隔离。

每批记录请求受理、准备命令接收、准备启动、材料确认、业务启动、权威核验、Telegram 发送回执与中央确认。比较时固定网络延迟、账号范围、输入及下游行为，区分首次连接和已有连接。真实生产业务办理耗时从用户已授权的原业务记录观察。

相关依据见[此前结果卡修复](./第三宿主网页待办卡与电报送达延迟-2026-11-26.md)、[NanoBot 与中央性能优化](./纳米机器人与中央底座性能优化-2026-11-25.md)和[发布操作手册](../部署运维/发布操作手册.md)。

## 第一批开发记录

候选版本为 0.1.5。网页固定命令使用按个人、端点、会话和凭据划分的控制连接。Telegram 领取命令后在同一连接重新读取当前身份、凭据指纹及完整配对，再读取原任务和取得原协调租约。Pi 固定命令的侧车省去主动加载整个模型工具目录，保留 SDK 自身的协议和输入 schema 校验。NanoBot 的默认命令入口及自由模型任务不变。

以真实 Pi SDK、隔离中央与合成 OA，每次 MCP 请求注入 100 毫秒延迟，逐项完整办理的同条件比较如下。每笔均执行一次合成业务写入并完成原业务核验，重复同键批准未增加写入。

| 原任务创建至首次准备开始 | 0.1.4 | 0.1.5 |
| --- | ---: | ---: |
| 网页首次连接 | 2.503 秒 | 2.448 秒 |
| 网页已有连接 | 2.510 秒 | 1.780 秒 |
| Telegram 首次连接 | 3.426 秒 | 2.717 秒 |
| Telegram 已有连接 | 4.628 秒 | 3.815 秒 |

本批授权至提交变化很小，不把它算作本批收益。原 Telegram 命令已领取但回包尚在途中时撤销配对的反例，在 275 毫秒内识别原配对失效，原命令未 ACK、准备与业务副作用均为零。开发态 L3 的 H01–H29 全部通过，版本与路由定向测试 48 项通过。原始私有证据保存在本机 `pi-performance-20261126/batch1`，独立对比索引为 `independent-ab-review.json`。

隔离 Chrome 基线两种原来源均完成选择、保存意见、单次确认及办理完成页。第一轮夹具因观测 SQL 错用字段在建立准备后退出，尚无授权或业务写入；修正为真实字段表后重新启动独立环境，第二轮两笔完成。此为验收夹具返工。页面使用原票的回环映射，模拟 Bot 不等于真实 Telegram 桌面；正式候选与生产证据另记。

候选开发 Chrome 同样完成网页与 Telegram 原结果来源的两件独立合成事项，均保存意见后单次确认，显示办理完成。原账本核对两次合成效果、第二账号零 Telegram 投递。共享控制、恢复、结果卡定向回归 60 项全部通过。

第一批 0.1.5 已于 2026-11-26 22:09（北京时间）由正式入口发布 `bd962f4c13f7`。Full、wheel、29 项 L3、归档协调器及真实 Codex 独立模型均通过，GitHub 独立检查随后通过。实际首账号 Telegram 新答复、新原卡实点及合成事项授权核验完成；第一次桌面夹具在业务完成后提前退出、未等待最终通知，记录为未通过，修正门禁后用新标记重验。重验核对字段卡下新增唯一终态气泡、本机持久发送回执及同一投递首次中央 ACK，原 Bot 已恢复且 Pi worker 与隧道进程未变。第二账号生产只读查询完整返回 33 项、无业务写入或 Telegram 目的地，并恢复原 NanoBot 默认宿主。第一账号保留的普通 Chrome 标签出现扩展未附着，已请求恢复其既有登录连接；此时尚未把第一批生产只读复验标为完整通过。

## 第二批开发记录

第二批候选为 0.1.6，在独立工作区以第一批固定候选为基线并行开发，正式部署仍等待第一批上线和复验完成。Pi 唯一入站 `getUpdates` 使用专用只读连接；消息接收处理、持久位点推进、所有业务发送及数据库仍由原主线程串行执行。任何时刻只允许一个入站请求，上一页处理落账后才能开启下一页。关闭时先结束只读请求，再释放原 Bot 独占锁。NanoBot 默认消费路径不变。

中央领取仅为当次个人身份、实例和原配对均有效的 Pi 消费者确认白名单静默事件。校验持久事件、原任务来源和冻结命令，保留逐投递尝试数与审计。文件、卡片、终态和用户文字仍走原可见投递。全静默满页后有界继续领取，避免后页的可见卡再次等待。旧中央忽略专用元数据并按原路径工作。

15 模块定向回归 116 项通过、无跳过。合成 Bot 的 500 毫秒入站等待下，唯一消息开始发送由 509.67 毫秒降至 1.05 毫秒。每次 MCP 注入 25 毫秒、两种来源共八条静默事件和一条可见终态时，可见结果返回由 338.888 毫秒降至 36.250 毫秒，RPC 从九次降为一次；八条原静默事件各自获得持久确认。本组无业务写入，真实 TLS、客户端和生产时延另行验收，不将此结果直接等同于生产节省。

第二批交叉审查发现静默确认可能先于审计提交。已把本次确认、尝试次数和两条审计放入同一 SQLite 写事务；在两处审计插入前分别注入故障，混合页的全部领取及审计均回滚，恢复后可见终态仍正常返回。另验证新旧重试各记本次尝试，防止继承前次失败结果。修复后的 107 项回归及八项子测试通过，原性能样例复测为 341.430 → 32.683 毫秒。适配器契约字节未改变，正式候选仍以修复后的中央代码完成 Full 和 L3。

第二批开发 Chrome 扩展在独立中央及合成 OA 完成网页和 Telegram 原结果卡两种来源的选择、意见保存、单次确认与办理完成页。第二笔卡仍将第一笔已办理事项禁用，未重复发起原事项。此轮使用模拟 Bot，计时及终态回执另存本机 `batch2/dev-chrome`，正式桌面验收仍须使用固定 wheel、第一账号及本轮随机标记。

该轮原账本确认两件各一次合成授权和提交、均经适配器回读成功；原完成通知各获唯一模拟 Bot 回执、本机持久已送达状态及中央首次确认，入队至确认分别为 0.2715 和 0.2177 秒。第二账号无 Pi Telegram 目的地与投递，真实 OA 写入为零。`sealed-metrics.json` 同时绑定启动源码指纹和两份 Chrome 完成收据。

第二批固定候选 `1d0feaa9a281` 的 Full 已通过，Python 4568 项通过、14 项跳过，Workspace Node 689 项及 OpenClaw 400 项通过。跳过项为九项缺少开发环境 aiohttp 的用例、四项后台 Chromium opt-in 用例和一项 pypdf 用例；相关宿主引擎定向与 L3 另列，不将跳过写成已测。正式 wheel、29 项 L3、归档协调器与真实 Codex 模型均通过；实际 Chrome 双账号资格分别核对原查询认证恢复和权限拒绝，第一人一读、一次前置恢复，第二人零业务读取与私聊目的地。此时尚未执行第二批原 Bot 桌面维护和生产发布。

固定候选随后在受管 Pi 引擎补跑上述九项准确用例，九项通过、零跳过、源码与工作树均未变化。测试使用独立临时 HOME、密钥和数据库，不安装依赖；收据及原 Full 测试名对应关系保存在 `batch2/post-full-engine-nine`。另外四项后台 UI 与一项 PDF 的跳过保留原边界。

第二批在第一批生产网页等待重新附着期间，依持续维护授权独立完成了原 Bot 候选验收，随后恢复准确的生产 0.1.5，原凭据、配对及 worker/隧道进程保留。发布仍等待第一批完整生产只读复验。Chrome 同一原查询在原生 Telegram 实见问题、答复及唯一办理卡；专属接收线程保持等待 23.552 秒期间，三项均取得不同的正数 Bot 回执。真实问答入队至确认分别 1.383 / 1.934 秒，卡签发至确认 1.826 秒。本次实测未人为延迟 Telegram 上游网络，持续等待发生于实际候选接收线程的受保护入口。

同窗口的原生查询出现卡先于答复的合法顺序；验收按本轮唯一问题、原回执及两者之间的唯一按钮核对，实点原 Mini App 入口后以同票的本机映射完成合成办理。原字段卡出现后先捕获无本次完成通知的基线，再单次确认；新增完成气泡、同一子任务、唯一 Bot 回执、一次中央确认及一次合成业务核验全部对齐。合成 `.invalid` 页面仍以原票映射验证，生产 HTTPS 内嵌页须另做只读实测，不能把本轮映射算作生产内嵌页通过。

## 第三批开发记录

第三批候选为 0.1.7，基于第二批固定提交。仅固定单项 Pi OA 准备使用逐次随机标识请求私有观察回包；中央续办后按原观察入口重新认证并核对协调租约，客户端检查原任务主体、端点、会话、版本下限及完整操作和交互集合。终态须无后续动作，当前交互须明确为空或为本次原交互。缺少、不匹配或超出有界完整遍历的证据一律使用原观察流程。批量、计划和其他宿主保持既有路径，最终快照及权威业务核验继续执行。

最终回包判据及共享流程 11 模块定向回归共 197 项、11 项子测试通过，无跳过；第三批开发态 H01–H29 全部通过且源码稳定。源于 0.1.5 基线的早期测量仅保留为历史证据，正式收益使用 0.1.6 对照。首组网页授权至提交包含一笔略慢样本，已追加交替顺序的配对测量；同时补足夹具末尾的原快照回包门禁，不把仅发出最后一个 RPC 算作观察完成。

第三批开发 Chrome 也完成两种原结果来源的各一件合成事项：意见保存后单次确认、原卡已办项禁用及办理完成页面均实见。原账本两次授权、两次合成效果均独立核验，完成通知各唯一送达且首次确认，入队至确认分别 0.2677 / 0.2497 秒。第二账号零目的地与投递，真实 OA 零写入。

第三批在相同 Pi SDK、独立模拟接收连接（1 秒入站等待）和每次 MCP 100 毫秒延迟下完成三组配对，每种来源均包含首次和已有连接。以下为每对差值的中位数，正数表示节省；保留了所有慢样本。

| 原授权至业务启动 | 首次连接节省中位数（范围） | 已有连接节省中位数（范围） |
| --- | ---: | ---: |
| Workspace | 98 毫秒（-18～131） | 210 毫秒（134～263） |
| Telegram | -21 毫秒（-33～305） | 74 毫秒（-44～251） |

每项确定减少字段续办后和已核验提交回包后各一次远程观察；中央原权威观察保留。TG 冷连接三对中两对略慢，终态通知也受轮询相位影响，不能据此承诺 TG 明显变快。额外的字段至授权呈现值是连续办理批准后的后台区间，与授权至提交重叠，不相加、不当作客户端按钮绘制时间。严格补组的 TG 核验至模拟 Bot 入账约 0.31～0.34 秒，新旧基本相同。

严格尾验另对新旧两版本、两种来源各两笔共八项核对：原授权、唯一提交操作、快照当前操作、权威操作回读、终态模拟 Bot 回执全部一致，并在同一 sidecar 本地事件账本核对原终态 eventId、sequence 与已推进序号，证实客户端已解码。错版本回包的两次续办均走原观察；未知业务回包保持未知、仅一次物理提交，后续轮询不重放。第二账号写入为零。

计时夹具曾错误要求字段和授权续办使用同一连接，以及把 timeline 序号当作 task_events 列，分别导致工具门禁失败；均保留失败记录，没有重放原办理。修正后使用现有 TaskStore 只读事件投影，并逐项核对实际隔离库及协调账本 schema。前三组有效阶段计时保留，缺失的客户端尾部证据由上述严格组补验。最终原始统计、全部样本与返工索引在 `batch3/final-batch2-baseline/final-integration-review.json`。
