# 电报原生终答同步修复（2026-11-27）

## 问题与范围

用户要求 TG 与 Workspace 双向同步。首批候选 `1f0f3aec830182d27b2351060bc09f834375d9f0` 在原生 OpenClaw 2026.7.1 隔离 Gateway 中收到一条合成私聊后，实际候选插件成功执行合成 OA 待办查询；SDK 发送了原始 HTTPS 双按钮卡和公开终答，但中央历史只有用户文字，没有助手终答。

根因是原生入站 hook 的 `conversationId` 为 `telegram:<peer>`，成功发送 hook 使用裸 chat ID。插件按目标逐字匹配私聊，未找到会话时跳过历史发布。旧测试两边都使用裸 ID，未覆盖 SDK 的真实表示差异。

本次仅在查找既有投递会话时规范化这一种已知 Telegram 正整数私聊前缀；不改保存的路由，不恢复或注册身份，不修改 SDK。保留账号匹配、多个候选会话时拒绝、不同收件人和未知前缀拒绝。其他宿主行为不变。

## 验证计划与边界

- 定向验证原生前缀与裸 ID、重复成功回调、异账号、异收件人、未知前缀和歧义私聊；运行插件专项和文档检查。
- 固定独立提交后，使用实际 SDK Gateway、原生 Telegram polling 与持久 spool、候选插件及真实 MCP 传输重验。平台 API、模型和 OA 均使用本机隔离合成服务；不得记为真实 Telegram 验收。
- 使用官方已持久接纳的入站及成功发送 hook 观察公开内容，不调用第二次业务操作来补历史。
- 本修复恢复终答进入既有发布器；持久镜像与 ACK 丢失后的补账依赖第二批持久 Publisher 及中央严格回执子项。它不能把 fire-and-forget hook 宣称为平台确认之前的同步事务。
- 不操作生产 Gateway、原 offset、原 spool、真实 TG 或业务系统。原状态的跨命名空间隔离尚未证明，真实入站交接的 apply 不开放。
