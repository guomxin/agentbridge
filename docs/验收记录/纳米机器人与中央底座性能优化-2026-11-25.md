# NanoBot 与中央底座性能优化三批实施与验收

## 范围与起点

2026 年 11 月 25 日 13:15（北京时间），生产基线运行候选 `27158ab8f2d9`。在完成一笔真实补签批量审批后，用户反馈 NanoBot 网页端与 Telegram 私聊的消息同步和环节衔接偏慢（不计 OA 下游接口耗时），并希望核对 OpenClaw 是否同受影响后分批优化、独立验证并正式发布。

只读诊断核查了中央运行日志、本地宿主端点耗时与 14 天通知投递账本，定位到四类叠加瓶颈：

1. **中央底座写放大与历史表膨胀（OpenClaw 与 NanoBot 共同受影响）。** 每次 MCP 鉴权与宿主协商均同步写库更新 `last_used_at` / `last_seen_at` 并追加信号；每 30 秒按秒级时间戳写入 `runtime_slo_rollups` 造成 733,219 行累积，`agent_host_runtime_snapshots` 累积 240,273 行且未纳入周期清理，导致中央空载 CPU 持续在 47.5%–53.7%，本地单次只读 MCP 往返 618–1,322 ms。
2. **NanoBot 宿主与 Python MCP SDK 隐式目录风暴。** 宿主控制路由每次请求均新建 `ClientSession`；在 `mcp 1.23.2` 中，新会话首次调用结构化输出工具时会隐式拉取全量 181 项工具（约 230 KB）以填充输出 Schema。叠加 Telegram 消费者串行调用路由解析与绑定核验，本地控制端点实测 `/v1/telegram-mirror-peers` 4,237 ms、`/v1/telegram-route` 5,992 ms、`/v1/telegram-binding` 2,821 ms。
3. **NanoBot Telegram 端同步节奏与终态 60 秒租约等待。** `TelegramAPI` 每次调用新建短连接 TLS；消费者未缓存已配对路由且每次轮询全量遍历；任务终态若在模型答复尚处 `working` 状态时到达，原实现未暂存而直接跳过，只能等待中央 60 秒租约超时重投。14 天账本显示 NanoBot Telegram `timeline_message` 均值 20.25 s（最大 39.27 s）、`task_event` 均值 30.77 s（最大 105.5 s，4 次重试），显著慢于 OpenClaw Telegram（`timeline_message` 均 3.68 s、`task_event` 均 4.87 s、0 重试）。
4. **Reference-Host 协调器短连接与轮询、Worker 起步冗余。** 协调子进程每次 MCP 调用新建连接、以 0.35 s 短轮询等待可信卡完成、起步同步阻塞并重复发送运行态快照；NanoBot Worker 起步额外拉取 54 KB `agentbridge_server_profile` 且重复执行 Telegram 绑定核验。

本次改造分为三批按依赖顺序实施、各自在干净固定候选完成全量验证并通过唯一正式入口 `scripts/agentbridge-native publish` 滚动发布。

## 必须保留的安全边界

- 跨用户、跨端点、跨会话与跨宿主通道严格隔离；MCP 会话池键包含主体、端点、实例、地址、TLS 凭据与通道，并每次校验实时 Token 摘要。
- Token 状态、有效期、吊销与权限范围保持每次实时只读核验；Telegram 撤权即时拦截，换绑后旧在途消息仍按 `binding_changed` 阻止投递。
- `TelegramAPI` 仅允许对幂等读/状态接口在复用连接断开时单次重连，非幂等 `sendMessage` 严格禁止自动重发。
- `prepare -> authorize -> commit -> verify`、一次性授权消费、`unknown` 不重放以及 Reference-Host `unsafe` 操作单次尝试策略保持不变。
- 发布事务不自动执行全库 `VACUUM`，留待低峰运维窗口按需执行。

## 分批实施、验证与发布

### 批次 1：中央底座写节流与留存治理（候选 `66dd292209c2`）

- **改动内容**：
  - `agentbridge/core/mcp_identities.py`：`verify()` 保持每次实时只读核验状态、过期与权限范围，仅在 `last_used_at` 为空或距上次更新超过 60 秒时写库。
  - `agentbridge/core/host_contract.py` 与 `agentbridge/core/central_service.py`：`require_registration()` 对 `last_seen_at` 做 60 秒节流写；`negotiate_with_change()` 在配置未变且 60 秒内跳过冗余写库和协商信号；新增基于既有复合索引 `(user_subject, host_instance_id, observed_at)` 的有界分批 `prune_runtime_snapshots(retention_days=14, batch_limit=5000)`，同时始终保留每实例最新一条快照。
  - `agentbridge/core/runtime_governance.py` 与 `agentbridge/mcp/central.py`：`refresh_slo_rollups()` 改为按 UTC 整点小时桶 upsert；`prune()` 采用 5,000 行有界分批清理并逐步回收 7 天前的旧非整点历史滚动行，同时联动清理宿主运行态快照。
  - 补充 `tests/test_mcp_identities.py`、`tests/test_host_contract.py`、`tests/test_runtime_governance.py` 边界用例。
- **验证与返工**：
  - 首次候选 `d2869fde8570` 在 Full 中被 `tests/test_central_storage.py::test_frozen_constructor_attributes_schema_and_restart_contract` 拦截（新增索引触碰冻结 Schema 契约）。改为直接复用既有 `(user_subject, host_instance_id, observed_at)` 复合索引后，未改动数据库结构。
  - 修正后干净候选 `66dd292209c2` 通过全部 10 个 Full 阶段（收据 `08a0d57f81454281887cedfc764017c7`，Python 4,366 通过 / 0 失败 / 4 按既定规则跳过，Workspace Node 687 通过，OpenClaw 400 通过，wheel 隔离校验通过）。
- **正式发布与独立 CI**：14:37–14:40 通过 `scripts/agentbridge-native publish --reuse-validation --apply` 从 `27158ab8f2d9` 升级至 `66dd292209c2`，业务写入 0、近期错误 0、双账号 L3 核验通过。GitHub 独立检查运行 `45562278454` 通过。
- **阶段发现**：批次 1 使未池化的 NanoBot 控制调用提速 2.3–4.4×，但因轮询频率随之提高，暴露出 Python MCP SDK 新建会话每秒触发约 1 次隐式 230 KB `ListToolsRequest`（使中央空载 CPU 短暂升至 108.7%），进一步确认批次 2 会话池的必要性。

### 批次 2：NanoBot 宿主隔离会话池与 Telegram 同步优化（候选 `4cc288ed4a13`）

- **改动内容**：
  - 新增 `integrations/nanobot-agentbridge/nanobot_agentbridge/session_pool.py`（`McpSessionPool` 与 `open_host_session`），每个池化槽由独立 `asyncio.Task` 持有以严格满足 `anyio` 同任务取消域要求；按 `(subject, endpointKey, instance, mcpUrl, caFile, coordinator, card_origins, lane)` 隔离，每次获取均实时校验 Token 文件 SHA-256，支持 120 s 空闲 / 300 s 最大存活 TTL、64 槽 LRU 上界、异常即时剔除与停机回收。
  - `server.py`、`telegram_routes.py`、`telegram_timeline.py`、`notifications.py`、`commands.py`、`enrollment.py`、`recovery.py`、`artifacts.py` 接入 `open_host_session`（`telegram-notifications` 独立走 `notifications` 通道避免阻塞控制面），并发探测 `mirror_peers` 与路由，开放 `waitSeconds`（上限 15 s）长轮询透传，并在运行处于 `accepted` 阶段即允许查询已落盘的 `hasResultView`。
  - `telegram.py` 与 `notifications.py`：`TelegramAPI` 启用 HTTP/1.1 Keep-Alive（对非幂等 `sendMessage` 在空闲 >= 40 s 时主动建新连接且断连绝不重试）；`TelegramPilot._binding()` 缓存已配对路由但每次仍实时调用 `verify_telegram_binding()`，撤权即时驱逐、宿主重启单次重解；`mirror_peers` 增加 10 s 缓存并在配对/登记时立即失效；`TerminalMessages` 在原消息处于 `working` 态时于租约期内暂存终态事件（上限 50 s / 64 条），待 `reconcile()` 完成普通回复后立即按第 1 次尝试投递并回执；`reconcile()` 在 `accepted` 阶段提前投递待办结果入口卡并按 `result_view:{sourceTaskId}` 幂等去重。
  - 新增 `tests/test_nanobot_session_pool.py` 覆盖池隔离、Owner 任务一致、Token 轮换、异常剔除、TTL/LRU、`TelegramAPI` 不重放 `sendMessage`、路由缓存/撤权/重启恢复、终态延迟刷写与早投递去重。
- **验证**：
  - 干净候选 `4cc288ed4a13` 并行完成正式 `validate --full`（收据 `54c3659fd32b4bc0afb1a477bc192a6f`，Python 4,371 通过 / 0 失败 / 4 跳过，Workspace Node 687 通过，OpenClaw 400 通过）与 NanoBot 0.4.2 SDK 共享契约套件 H01–H29（11 组隔离合成探针、29/29 项通过，报告摘要前十六位 `f2d0cdbc11039a9f`）。
- **正式发布与独立 CI**：15:06–15:09 通过 `scripts/agentbridge-native publish --reuse-validation --apply` 升级至 `4cc288ed4a13`，业务写入 0、近期错误 0、双账号 L3 核验通过。GitHub 独立检查运行 `45565941945` 通过。

### 批次 3：Reference-Host 协调器复用/长轮询与 NanoBot Worker 起步精简（候选 `2f7bd8a7d64d`）
