# 电报可信卡关闭状态补齐

## 范围与原因

2026-11-27 实际 S03 登录续读确认：原登录链接已完成且不再显示表单，原结果另行送达，但 Telegram 历史卡仍显示发送时的“等待操作”。最终候选 `f7175f6cb5f1` 的三个宿主均没有编辑原 Telegram 消息的实现；共享消费者按交互 ID 首次发送去重，完成事件默认静默。旧链接的服务端保护有效，不能代替历史卡关闭状态的反馈。

本次在独立工作树中补齐原四批设计要求，不改变旧冻结候选、既有文档分支或生产状态。复用中央可靠公开状态投递，给已确认送达的原可信卡追加一次安全关闭说明；原结果独立投递。涉及中央交互事实、原卡发送回执、三宿主实际消费者和专项测试，不引入 Telegram 历史消息编辑、业务调用、模型调用或私有材料镜像。

## 必须保留的边界

- 仅原主体、实例、目标、配对与原交互一致且原卡已确认送达的关闭修订可产生通知。未发、未知、原端自处理和不同交互不得借用回执。
- 每次原关闭事实固定独立身份，重复观察、重启和迟到回执不增加通知；发送未知不重发，撤配或换绑不泄漏。
- 完成、失败、过期、替换及拒绝使用固定安全文案，不包含凭据、字段、授权内容、标题或可信链接。登录完成明确无需再次输入，不宣称业务已经成功。
- 新协议仅前向生效；旧路径只为已有实际支持的原卡关闭接入，不能扫描旧事件补授或重放历史通知。
- 与任务完成及原结果交付分别计账，不把原卡关闭通知误判为已被查询结果覆盖。

## 验收计划

真实中央与宿主消费入口覆盖成功、失败、过期、替换、多个交互、重复与重启、关闭先于发送回执、未发送和发送未知、撤配换绑、其他主体/实例、原端自处理及结果独立性。只使用隔离 home、数据库、回环传输与合成材料；真实 Chrome/TG、正式 Full 与发布由主任务针对新固定候选统一验收，未取得证据前不写通过。

## 实现与兼容边界

新增两张中央表：`telegram_interaction_card_watches` 仅在新的可信卡 `begin` 成功时登记原投递 ID；`telegram_interaction_closures` 将关闭投递关联到原卡、交互类型及终态，同一原卡与终态只能一条。没有历史回填。已确认的原卡进入关闭投递；尚未结算的唯一发送只保存 `awaiting_card_receipt`，确切迟到正回执才释放。原发送未知不重新发送。

现有 `host_notification_v2` 和宿主接口不变：关闭说明使用 `notificationKind=public_status` 与独立原事件 ID，正文无卡片链接或私有材料。登录完成文案为“此前发送的登录卡已完成登录，无需再次输入。请以原任务的当前状态和结果为准。”填写、授权、失败、过期、替换和拒绝各用固定准确措辞；卡的完成不冒充业务成功。原结果投递不能把关闭说明判为已覆盖。

真实续读专项暴露了原调用顺序的另一处缺口：登录后原查询可继续完成，但不一定再次观察旧交互。现在受控资源通过原身份核验后，仅为已登记的原卡记录终态；当前合格通知领取最多检查 16 个相关原资源，不调用模型、续办或业务。失配记录不会长期占住队首；已有关闭事实的卡（包括等待原回执的卡）停止轮询，重复读取相同终态不再进入任务写事务。旧交互关闭不改变任务当前交互，不重开已结束任务。

三宿主本轮 Workspace→Telegram 原卡都走上述可靠协议，复用其平台回执与发送账本。Telegram 原生 direct 卡和旧协议只有布尔确认的历史记录不能提供相同证明；本次不将其提升为新授权，也不声称它们已获得本关闭通知能力。旧按钮仍由原受控服务拒绝失效材料。这是明确的兼容边界，不以历史气泡已被编辑或全部旧卡已回填描述。

## 验证结果

- [中央关闭专项](../../tests/test_telegram_interaction_closures.py)覆盖各终态、原任务和查询结果独立、迟到正回执、未知不重发、未发送、上线前未登记旧卡、其他主体/实例/令牌/配对、旧卡与新当前卡、多次观察、任务结束后关闭、超过一轮旧配对记录的公平性及无人打开的自然过期。原发送资格失效后仍可发安全关闭说明；已有关闭事实连续三轮不加载原资源或更新观察时间。
- [共享宿主实层专项](../../tests/test_telegram_card_closure_channel.py)分别通过 NanoBot/Pi 的实际私有处理程序、真实 MCP 序列化和身份校验、中央账本、生产 `TerminalMessages` 消费器及回环 HTTP Bot API。原可信卡的完整双按钮发送后，真正认证资源完成产生独立公开关闭说明；消费者重建与重复领取没有重发。身份、凭据、认证结果和平台均为隔离合成材料，未接触真实 Telegram 或 OA。
- [OpenClaw 专项](../../integrations/openclaw-agentbridge/test/trusted-card-closure.test.js)新增 6 项，覆盖实际 Coordinator、可靠消费者和持久文件的领取/签发/开始/发送/回执，独立关闭与结果、多交互、重启、ACK 丢失、发送未知和信封隔离；MCP 与平台边界使用明确替身，不代替真实 SDK/桌面证明。
- 最后集中回归包含新专项、旧通知、任务与状态序列、查询投影、Pi 通知、宿主隔离、存储和文档：**156 tests、2,103 subtests 通过，32.48 秒**。此前两轮官方 `validate --test` 均通过；OpenClaw 官方 `validate --plugin`（全插件测试及打包检查）于北京时间 18:39:05 通过，与 Python 集中回归并行。均为开发证据，不是发布收据。私有摘要保存在 `card-closure-development-final.json`。
- `validate --changed` 按共享中央行为变更判为 `full_required`，新固定候选必须重新 Full。定向阶段的两次环境准备失败分别为直接调用 pytest 缺少隔离会话密钥，以及临时解释器链接未加载测试依赖；已改用正式 `AGENTBRIDGE_TEST_PYTHON` 和官方 `test_environment`，未改依赖、测试门禁或生产设置。
