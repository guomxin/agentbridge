# 工作台同步第二批共享适配与通知验证

## 范围与边界

本记录对应[四批实施方案](../后续规划/工作台与电报同步分批实施方案-2026-11-27.md)第二批的 NanoBot/Pi 共用适配器，以及三宿主共用的通用通知账本。实现位于独立工作树；第一批固定候选和真实 Telegram 交接由主任务串行维护，本子项没有修改线上运行环境或发送真实消息。

已确认的问题包括：普通 Telegram 入站历史依赖模型接纳，终答历史依赖全部平台发送成功；通用通知把明确限流和回执丢失统一处理，平台发送前后缺少独立的中央许可与主动补账。预期是独立保留原私聊接收事实与原宿主结果，用有限的明确错误分类恢复尚未发送的片段，并让新通用事件使用原配对和原事件的持久发送账本。

涉及共用 `telegram_timeline`、`telegram_direct_replies`、`notifications`、`workspace_query_delivery`、Workspace 私有 gateway，以及新增中央 `telegram_notification_delivery` 和 task event/claim/MCP 窄钩子。必须保留 L3 精确登记、原端点与凭据校验、可信卡原治理、未知不重发、撤配只补账、原任务和原角色不改写。旧队列不迁移，新协议只作用于消费者明确启用之后生成的事件。

验收覆盖独立接收和结果投影、超过 50,001 字符、200,000 Unicode 字符共同上限、分片冻结、429 有界重试、永久拒绝、丢回执、重启主动补账、配对失效、私密终答和私有链接拒绝、可信交互与公开文字分离、旧队列兼容，以及未知后权威观察产生新事件而保留旧 unknown 和回执。

## 已实现

普通入站先保留原私聊的不可变接收事实，再独立投影历史；模型接纳和模型执行的语义没有改写。完成、停止和未知结果都保留原 run 来源，公开终答投影不再依赖 Telegram 所有片段送达。投影校验中央持久回执的 entryId、messageKey、角色、端点及 UTF-8 摘要；历史正文被正常清理后只核对回执，不重建旧正文。

新普通终答冻结正文分片和平台格式，发送意图与回执持久保存。只有明确的 429 和合法 retry_after 可以重新取得新尝试；未知结果不重发。当前绑定核对位于发送预留之前。独立历史故障不阻塞其他消息，重试到期有明确元数据终态。

通用通知使用 `host_notification_v2`。消费者通过私有 claim 的 `include_notification_v2` 登记当前精确实例、凭据和配对；后续事件在生成事务中冻结原事件 UUID、任务、主体、来源 Workspace、目标 Telegram、配对和协议。旧通知仍留在既有 outbox；文件、watch、digest、组合结果及 Telegram 自身任务的专用路径不改为通用协议。

新增 `agentbridge_host_notification_delivery` 的 issue、begin、ack 复用有限错误结算规则；begin 每个 attempt 只成功一次。公开状态只含固定短说明，不采集任务标题、业务字段、异常详情或可信链接。可信交互仍通过原认证、字段和授权呈现服务签发，发送前再次核对原卡与当前配对，不触发业务执行。两宿主复用原持久发送日志与原凭据恢复路由。

后续权威操作观察生成新的 task event，取得新的 deliveryId；去重按 sourceEventId，不按 taskId。它不会修改原 unknown 发送记录、旧角色、旧消息键或回执，也不擅自改变业务账本的粘性未知状态。

静默回归要求同任务、同原端点、同配对、同终态且现有 query/text 可靠记录通过原来源校验，才把通用事件记为 `covered` 并关联 `covered_by`。领取、签发和发送许可都复核；可靠正文在签发后到达也会停止多发状态。分片证据不完整不会错误静默。原有 quiet companion 类型不进入新通用状态白名单，可信卡、恢复和权威核验事实不因 taskId 相同而合并。
