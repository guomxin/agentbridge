# 工作台消息与未知待办恢复修复（2026-10-23）

用户在效能回归修复发布后报告：输入的查询文字不显示，对话顶部出现全局 OA 按钮，原效能未知结果事项无法继续。本轮在 Release `58603683770e` 上继续修复；本文件随实现、独立 Workspace 验收与正式发布更新，未完成阶段不作上线结论。

## 原因与第一批修复

固定文字查询直接进入只读 API 时，原实现只保存查询意图，没有保存聊天消息，前端受理后又清空输入框，导致原话消失。现在在同一事务中先保存用户原话，再创建闭集查询任务；HTTP 回执和 SSE 使用同一条消息去重，刷新后仍存在。原始文字不进入模型或可执行参数，后端也验证固定表达；同一请求键改变文字会被拒绝，超时恢复保持原请求，不将正在修改的新文字误当成已发送。

全局“查询 OA 待办”按钮已从通用对话顶部移除，卡片内重新查询入口保留。点击卡片按钮只表示查询动作，不伪造一条用户聊天消息。已丢失的历史查询原文无法可靠还原，本轮不会编造历史消息。

独立 Chrome 扩展 Workspace 使用 `output/workspace-recovery-20261023/message-home/`，真实 Central/Auth/Workspace 和数据库，OA 下游为隔离合成材料。输入 `查询 我的 ＯＡ 待办。` 后原文保留，刷新仍存在，顶部仅有刷新，卡片重新查询有效。账本为 **0 模型 dispatch、0 草稿决定、0 执行授权、0 下游写入**；两条新查询任务均成功，只有一条实际输入的用户消息。浏览器 warning/error 为空。

验收同时发现微秒时间戳被截为毫秒：同一毫秒内创建的查询卡，刷新后可能排在用户原话前。已保留 ISO 时间戳的微秒精度，刷新后原话位于对应查询卡之前。Node 定向 **82/82**，Python 查询及页面结构 **28 项、49 子测试**通过。证据 `message-refresh-dom.txt`、`message-refresh.png`、`message-ledger.json`；这是消息/入口独立验收，不代替后续恢复流程及正式 Full。

独立审阅另发现旧 Gateway 历史按相同文字和五分钟时间窗去重，会把从未进入 Gateway 的新闭集查询误当成旧消息。已在历史先到、后到两条路径排除这类消息，跨 Workspace 端点也保留其 message key；同 entry ID 仍去重，普通 Gateway 去重保留。新增五项回归并通过定向验证。

## 第二批：原结果未知事项的恢复

原第 40/41 周效能任务仍为 `outcome_unknown`，原授权已经消费；只读查询仍发现待办，不等于能证明上次提交从未生效。原任务、原 commit 和原决定保留，不能直接重放原授权或改判成功。

本轮新增显式恢复路径：先只读核对原事项；确认已完成时显示核验结果，仍可办理时明确说明旧结果未知并要求用户确认重新核对材料；只创建全新办理任务，重新查看材料、填写意见并最终确认。读取失败、身份不一致、待办与已办冲突等状态阻止新一次办理。具体合同、测试及生产验收结果在完成后补记。

首次独立 Chrome 扩展 Workspace 已通过正常恢复链和两个拦截场景：隔离真实 Central/Auth/草稿/授权连接合成 OA，三个原任务都先形成一次消费后的 unknown。只读核对已完成事项不给新办，待办与已办同时存在时阻止；仍可办项只有勾选风险确认后可准备新空意见表单，填写新的合成意见并单次确认后，新任务成功，三个旧任务仍为 unknown，各自原 commit/消费授权关联及一次决定保持。总计四次决定、四个消费授权、四次合成写入，其中三次为种子原尝试，一次为明确确认的新尝试；浏览器 warning/error 为空。`recovery-initial-success-dom.txt`、`recovery-initial-success.png`、`recovery-initial-ledger.json` 留证。该首次链路早于最终审查加固，后续冻结版本仍须重验。

恢复接口 Node/HTTP 已验证身份、CSRF、请求字段、端点绑定、私密字段投影、未确认不可准备、双视图去重、超时恢复和新意见为空。材料准备临时失败可在同一新任务受控重准备，不会再建第二个任务；只有服务端明确的准备失败可保留恢复请求，其他身份/证据冲突清除旧证据。已办仅部分覆盖时明确提示“未找到不能证明上次未提交”。

独立审查发现的授权换 task、同主体重新绑定后的 generation 校验、恢复事件 timeline/SSE 投影问题均已修复。新授权从 prepare operation 的唯一任务关联取恢复合同，不能用普通任务或空 task 绕过；permit 同时绑定旧操作、原冻结计划、当前主体/会话 generation、精确事项与能力、当前材料 hash、核对记录和明确风险确认，并以两端服务端事件验证。原 Skill 有绑定时继承并重新验证治理。提交先独立核对旧结果，再执行原完整材料/身份/正文就绪检查并消费；消费事务再次校验 permit/session。原始 OA 提交函数及其原生字段校验不变。

私有完整核对证据保留于 TaskHub 事件；Workspace task summary 仅公开原任务 ID，timeline/SSE 恢复事件只公开事件类型及 task ID，专门回执只提供允许的状态/opaque ID/期限/覆盖范围。HTTP 实际 GET timeline 和真实 SSE wire 均检查没有泄漏私有绑定。

冻结代码后的第二个全新 home `output/workspace-recovery-20261023/recovery-final-home/` 已独立重验三态、新空意见表单、一次新确认成功、旧 unknown/消费授权/commit 保留及新查询指向新任务；固定查询原话刷新可见，零模型 dispatch。账本仍为三次种子原尝试加一次新明确确认，即 **4 决定 / 4 消费 / 4 合成写入**。最终定向 Python **55 项、1587 子测试**通过（含文档），共享前端组合 **98/98**；15 个核心恢复案例覆盖并发、过期、预建伪任务、材料漂移、旧授权重放、最终确认/提交前新完成证据及 task/session 更换，4 项 HTTP 恢复测试通过。最终源码仍须通过干净候选正式 Full 及发布后生产只读验收。
