# Pi 网页待办卡与 Telegram 送达延迟

11 月 26 日 16:59 开始复查。用户在 Pi Workspace 发起本人 OA 待办查询，第一账号的 Telegram 私聊中文字到达慢，未看到待办结果卡。上次验收核对了网页来源的问答文字，也单验过从 Telegram 发起查询的结果卡；两条证据没有覆盖从网页发起并在 Telegram 收到可打开的同一批待办。

本轮先对照同一原运行的 OA 查询结果、结果来源端点、普通文本发件箱、专用卡投递和 Telegram 桌面实收。代码检查覆盖中央结果视图、原 Workspace 运行与 Telegram 目标配对、Pi 的通知领取与确认，以及 NanoBot 和 OpenClaw 的同方向实现。待验证的是网页来源的结果是否能在专用渠道签发给本人当前配对，以及通知循环的排队与重复远程复核分别耗时多少。

预期是第一账号从网页发起一条有完整可选结果的查询后，在原私聊各收到一次问题、原答复和待办卡。卡在用户本人私聊打开，选项应与原读取相符。直接读取和登录后续办使用同一项验收。核对第二账号、解绑或换绑、过期、空结果、来源不完整、返回超时、进程恢复和发送结果未知。历史消息不自动重放，卡链接不进入普通聊天、模型或日志，查询不触发办理或消耗写授权。

分段记录中央入队、领取、Telegram 发送与中央确认，并在同一网络条件下比较旧版与修复候选。隔离样本、真实原生客户端和生产只读复验分别取证。生产切换与判定依据遵循[原生维护](../部署运维/苹果系统原生维护.md#固定候选的端点实测)。

## 生产原请求与旧版对照

第一账号 16:55:02 发起的原查询完成一次 OA 待办读取，返回完整的五项来源，未经过凭据续办。Telegram 原生桌面和账本对应同一问题、任务状态及答复。问题 16:55:21 获中央确认，从入队到领取约 9.55 秒，领取到确认约 9.99 秒。答复 16:55:44 确认，分别为 9.12 秒和 10.98 秒。领取时间由首次成功投递的 60 秒租约反推。领取后的时间包含发送前检查、Telegram 传输及中央回写。

原任务的结果视图签发数及 Pi 本地待补卡记录均为零。旧版从 Telegram 入站消息的运行记录建立补卡项，中央结果视图也要求原查询端点与收到卡的 Telegram 端点相同。网页查询有自己的端点和会话。普通问答镜像及任务状态通知各自成功送达，均没有发起办理卡签发。NanoBot 与 Pi 共用这段入站逻辑，OpenClaw 的原结果视图也要求原 Telegram 端点。

17:05，在 Chrome 扩展中从 Pi 0.1.3 工作台查询一项合成、完整且允许选择的待办。按每次中央 MCP POST 增加 120 毫秒延迟，实际 SDK 及渠道消费者完成一次读取，模拟 Bot 收到问题、任务状态、终答，选择卡为零。问题和终答入队到确认分别为 3.80 秒和 7.65 秒。

## 修复与隔离复验

Pi 0.1.4 在保存成功网页答复时，同时为符合条件的原查询登记一条专用投递。中央只接受同一主体、原端点和原任务里的唯一成功 OA 读取，固定其内容摘要、完成时间和原配对。消费者在本人的当前私聊单独领取、签发并发送结果卡。选择或显式刷新沿用原有受控办理流程，并在后续请求复核来源、配对、权限和有效期。文本、模型和发送账本不保存卡片明文链接。已知送达的卡按原 Telegram 消息号回写，发送结果未知时终止重发。

领取、发送前校验及确认各自复核当前身份和原配对。Pi 复用了同一次远程请求中已通过校验的会话，把三项操作热路径各自的中央 MCP 往返从六次降到三次。普通通知在同轮可选图片查询之前领取。两条路径独立处理可恢复错误，后台签发的等待不会占住入站与文字发送。新增的网页结果卡复用 Pi 原结果卡的 45 秒网络等待上限，发送前仍核对原领取租约、来源和页面期限。

17:12–17:17，Chrome 扩展分别从两个隔离网页核对。首账号使用原话「查看OA待办」，直接读取和登录后续办分别得到一项可选择的合成事项。两轮均只读取一次、签发一张，问题、答复和双按钮卡各有一条首次投递回执。打开所签视图得到同一任务的一项待办。第二账号按本人权限被拒，无业务读取和 Telegram 投递。两轮的普通问答入队到模拟 Bot 确认分别为 1.49/2.36 秒和 2.23/2.83 秒，办理卡为 5.79 秒和 6.12 秒。这组观测发生在最终调整通知与图片领取次序之前。

最终顺序另以相同的真实 Pi SDK、中央 MCP 和模拟 Bot 做前后对照。每次中央请求增加 120 毫秒、Bot 增加 300 毫秒。无在途登录时，问题和答复的入队至确认从 5.98/7.99 秒变为 3.70/4.86 秒；有一张等待用户登录的卡时，从 6.58/8.68 秒变为 4.16/5.49 秒。两组文字的排队领取等待分别由约 3.35 秒降至 2.02 秒、4.54 秒降至 2.91 秒。

17:20–17:22，从 Chrome 再发一次「查看OA待办」。本次使用最终消费顺序，在中央已完成签发并释放事务后人为延迟 HTTP 响应 10.25 秒，超过普通请求的八秒上限。从签发到模拟 Bot 发送为 12.10 秒，中央只签发一次、原 OA 只读一次、办理卡只发送一次，问答在卡片之前送达。普通文字和卡都在第一次投递取得确认。开发 L3 的 12 组探针覆盖 H01–H29，包含网页来源结果卡和换绑拒绝的新增项目。
