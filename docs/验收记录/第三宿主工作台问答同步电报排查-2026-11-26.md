# Pi 工作台问答同步 Telegram 排查

11 月 26 日 15:27，第一账号在 Pi Workspace 提交 OA 待办查询。中央即时为问题建队列，Telegram 第一次发送成功，从入队到中央确认耗时 22.17 秒。原网页途中显示 OA 登录卡，随后同一任务完成一次 OA 待办读取，该读取从建操作到账本成功耗时 2.98 秒。网页收到最终答复，公开文本可通过现有筛查，中央没有为它创建投递。14:26，第一账号另一笔无需登录的 Pi 网页待办查询已将问答各投递一次，入队到确认分别耗时 20.69 秒和 24.00 秒。

0.1.2 采用 NanoBot 的普通聊天镜像规则。一轮出现可信交互进度时，规则一律拒绝将最终答复加入 Telegram 队列，即使独立的 OA 登录已经成功。Pi 已复用 NanoBot 的消费者和发送账本，控制路径仍在反复建立中央 MCP 会话。领取、发送前核验、发送确认各自经过绑定校验和通知处理，每次都重新协商身份和读取工具目录。实际生产样本有入队和确认两端的时间，无法逐个还原中间调用耗时。

上一轮生产验收分别从 Telegram 和 Workspace 发起 OA 查询，核对了各自的终答与只读账本。这次回查才核对无卡场景的跨端回执及耗时。上一轮遗漏了「在网页发起并完成 OA 登录，Telegram 收到同次最终答复」，也漏记了生产确认延迟。后续按同一原任务核对网页、投递队列与 Telegram 桌面，并分别记录业务完成、入队、发送和确认。[上次发布记录](./补卡恢复与工作台路由更新-2026-11-26.md) · [固定候选的端点实测](../部署运维/苹果系统原生维护.md#固定候选的端点实测)

中央修复只接受原 Pi 网页普通查询的最终公开文本。中央核实 OA 登录挑战属于同一任务、主体和会话，且挑战已在唯一待办读取发起前成功完成。原任务及读取都须成功，问答仍归到原配对。业务表单、执行授权、短期链接和其他私有内容继续走专用路径。撤权、重绑、结果未知与旧消息继续按原规则处理。

隔离环境从 Chrome 扩展中的原网页串起固定 Pi SDK、中央 MCP、合成登录与 OA、以及运行实际消费者的模拟 Telegram。两轮都加入每次 MCP POST 120 毫秒的延迟，均确认原问答各一条和原 OA 读取一次。中央入队修复相同，旧连接路径从入队到确认耗时 5.30 秒（问题）和 16.39 秒（终答），复用连接后为 2.60 秒和 4.56 秒。领取接口样本中位数从 3.37 秒降至 1.92 秒，发送前核验从 2.32 秒降至 1.25 秒，回执从 2.30 秒降至 0.91 秒。进一步加入同一 OA 登录挑战的直接核验后，复验的问题和终答确认用时分别为 3.12 秒和 3.62 秒。此隔离样本反映同一注入延迟下的对照，生产网络和 Telegram 桌面耗时需按候选重新取证。
