# 原图双队列顺序保护

## 范围与原因

Pi 正式资格的实际 SDK 合成传输探针在 `9e869e65b970` 重复发现两张原图反序。旧消费者已把第二张蓝图送达为回执 101，新消费者随后把第一张红图送达为回执 102；对应旧表第一项为 `superseded`、第二项为 `sent`，新表第一项为 `sent`、第二项仍 `pending`。这是逐件接管后两个消费者竞争造成的实际发送顺序缺陷，不是页面排序问题。

本次只处理中央原件队列的所有权交接与同一原问内的顺序，不改附件内容、配对授权、宿主协议、数据库结构或发布门禁。资格探针的 API 兼容修正由另一独立提交承担。

## 预期与边界

- 同一原问的旧组全部未开始时，新消费者首次领取在同一事务接管整组，旧消费者不能抢发后件。
- 旧组任一项已经领取或发送时，保留旧消费者责任，不将已开始或结果未知的原件转移给新消费者。
- 对升级前已经部分交接的组，两条路径的领取及发送许可均等待前序活动项，保留各自原投递身份和正回执。
- 旧库没有新队列表、没有新行、其他原问和其他主体不受新增等待影响；结果未知仍不重发，原正回执只补账。

定向验证覆盖两个领取顺序、旧在途、升级前半交接、begin 前竞争、未知终态和无新表。实际 SDK 两图探针在合入独立探针修正的隔离工作树运行；未操作真实 Telegram、生产数据库或业务能力。

## 验证记录

- 新增顺序专项在原实现上为 10 失败、2 通过；修复后 12 项通过，耗时 1.94 秒。首次编写时发现测试调用的关键字与内部 claim 参数名不一致，先纠正夹具后才记录上述产品失败。
- 正式定向入口执行顺序专项、共用原件投递、Pi 原件及补账、文档检查：42 项及 2,077 个文档子项通过，耗时 5.77 秒；收据 `native-test-b1a8c0aa8a4b423288ee924b22b45ef5`。
- 实际 Pi SDK 1.6.0 加合成模型、合成 Telegram 的原两图探针通过，耗时 11.343 秒。两原图顺序、SHA、大小、两协议互斥所有权、4 个唯一物理回执及中央/本地 ACK 均核对；没有真实 Telegram 平台操作。
- `validate --changed` 判定为 `full_required`，本地定向结果不充当正式发布资格。正式固定候选 Full、正式客户端资格和发布由主线另记。
