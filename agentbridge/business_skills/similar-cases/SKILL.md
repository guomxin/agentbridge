# 相似案例检索

1. 先明确用户问题边界、数据源和日期。将问题转为少量检索词组：用户用词、常见状态表达、设备或项目别名。例如离线问题也可能写成无法连接、连接异常、上线异常、通信中断。先宽检索再读全文判相关，不能只查用户原词。记录实际使用的词组和返回数量，简要说明覆盖范围。首次查询前读取所用能力的 input_schema；keywords 当前每次最多8个，超过时按事件线索拆组，不截掉其余词。每组从首页独立读到 has_more=false，仅沿该组的 next_cursor 续页，不能换词后复用游标。日期、人员等用户指定范围在各组保持一致。

2. 阅读全文、拆开同篇不同问题，将同事件连续记录归并。先按项目、设备或故障对象建立事件线索，再按日期整理处理过程。同一故障的排查、升级、修复和回访合为一个案例，在一行保留多条日期与来源，不能按日志条数充当案例数。仅项目相同不足以合并；缺少对象或延续依据时明确标为关联待核对。按直接相关、相邻、不确定、不相关分类。

3. 对每个准备进入主表的案例，再核对日期范围内的后续记录：用项目、设备标识、作者或处理技术等稳定线索检索，去掉“掉线/离线”等故障状态词限制。恢复日志可能只写“增加机制后恢复正常”，不能因没有再次写故障词而漏掉。读取匹配记录全文后再决定是否属于同一事件；仅技术相似不足以并入。按 source_id + 日志 id 维护两组已读记录：首轮候选 A、后续核对 B；跨词组或跨页重复只计一次，同一日志内多个段落不增加日志数。记录补查词组与读完状态，不能把首轮数量写成全部读取数量。若后续核对未执行或范围不完整，写“后续尚未核对”，不能写“未见恢复结果”。

4. 主表只列直接相关案例；相邻或不确定项单列并说明差异，不能凑数量。

5. 输出问题、措施、原文明示结果、适用条件、差异和来源。仅已处理不写恢复正常；无时长不称快速；缺后续不能认定当前未解决。

6. 交付前核对概览与表格状态一致。最终回答须有一行检索覆盖说明：“首轮候选 A 条；后续核对 B 条，其中新增 C 条；共核对 D 条日志，归并为 E 个直接相关案例。”A、B分别为两阶段去重日志数，C为B中不在A的记录数，D=A+C，E按事件而非日志计数；重叠日志可在A、B各计一次但总数只计一次。未读完则标为“已读”，无法可靠计数就明确说明，不估算或编造；另用一句话交代实际检索词组。无命中不虚构，读全候选不代表语义全量。本次已随主说明加载 references/evidence.md，按其核对来源，不另行调用文件读取。
